## ねらい

T9のReactと、T8の検証を組み合わせ、G12〜G14のAPIにつながる画面（一覧・詳細・登録）を作る。画面がAPIと通信する以上、「読み込み中」「失敗した」「もう一度」の3つは、機能ではなく前提になる。閉域の現場では、APIが止まることも、ネットワークが途切れることも珍しくない。そのときに画面が白くならず、何が起きたかを人に伝え、復旧したら再読み込みなしで戻れることを、このユニットのゴールにする。あわせて、主要なコンポーネントをTesting Libraryでテストし、APIなしでも画面の動きを確かめられるようにする。

## このユニットで身につけること

- APIを呼ぶ処理をReactから切り離したモジュールにまとめ、トークンの付与と検証を1か所で行う
- 画面の状態（読み込み中・成功・失敗）を判別可能ユニオンで表し、状態ごとに描き分ける
- `useEffect` の中で `fetch` を呼び、途中で不要になった応答をクリーンアップで捨てる
- 一覧・詳細・登録の3画面を、ルーティング用のライブラリなしで切り替える
- 通信の失敗、エラーのステータス、壊れたレスポンスを区別して画面に出し、再試行できるようにする
- APIを止めても画面が壊れず、再開後に再読み込みなしで戻ることを確かめる
- トークンをフロントエンドに渡す方法を決め、ビルド結果にどう残るかを確かめる
- Testing Libraryで、`fetch` を差し替えて主要コンポーネントをテストする

## キーワード

- **APIクライアント**：APIの呼び出しをまとめたモジュール。画面のコードから、URLやヘッダの詳細を隠す
- **画面の状態**：読み込み中・成功・失敗のように、画面が今どの段階にあるかを表す値。T6の発展で型にした
- **競合（レース）**：先に送ったリクエストの応答が、後に送ったものより遅く届き、古い内容で画面が上書きされること
- **再試行**：失敗した処理を、もう一度実行すること。手で押す場合と、自動で行う場合がある
- **環境変数（Vite）**：`VITE_` で始まる名前の値を、ビルド時にコードへ埋め込む仕組み
- **Testing Library**：コンポーネントを「利用者が見て、操作する」形でテストする道具。要素は見た目の文字や役割（ロール）で探す
- **DOM環境**：ブラウザなしでDOMを模して動かすもの。Node.jsの上でTesting Libraryを動かすために要る
- **モック**：テストの中で、本物の代わりに置く偽物。ここでは `fetch` を偽物に差し替える

## 準備

T9の設定と、T8の検証関数を持ち込む。GoのサーバーはG14のものを、別のシェルで動かす（トークンはダミーの値で `API_TOKEN` に入れる。G14の準備を参照）。

```sh
cd ~/offgrid-log/drills/ts/T10-react-api
cp ../T09-react-basics/{package.json,package-lock.json,tsconfig.json,vite.config.ts,index.html} .
cp ../T09-react-basics/<ESLintの設定ファイル> .
npm ci
mkdir -p src && cp ../T08-type-guards/src/<検証関数のファイルとテスト> src/
```

APIの呼び出しは、T7の課題8で試した2つの方法（Viteのproxy、G14のCORS）のどちらかで通す。どちらにしたかと理由を `notes.md` に書く。Testing Libraryは、Reactに対応したパッケージと、`user-event` を入れる。DOM環境のパッケージは、Testing Libraryを動かすための部品として入れてよい（どれが要るかは、Vitestの「Test Environment」で調べる）。ルーティング用のライブラリは使わない。

## 課題

1. G14のサーバーを起動し、`curl` でトークンなし（401）とトークンあり（200）を確かめる。Viteを起動してページを開き、Consoleで `fetch` を直接打ち、ヘッダなしで `/items` を呼んだ結果と、`Authorization` ヘッダを付けた結果を比べる。Networkタブで、送られたリクエストヘッダを見る。CORSで通している場合、リクエストはいくつ出るか（T4の課題10、G14の課題9）
2. `src/api.ts` を作り、一覧・1件取得・登録の3つの関数を書く。Reactは使わない。すべての関数は、T6の課題8の成功・失敗の型を返し、成功のときは、T8の検証を通った値だけを持つ。トークンをヘッダに付ける処理は、1か所にまとめる。失敗の種類として、少なくとも「通信そのものの失敗」「エラーのステータス（本文はG13の形）」「本文が期待した形でない」を区別できるようにする
3. 課題2の関数に、Vitestでテストを書く。`fetch` を偽物に差し替える方法を、Vitestの「Mocking」と `vi` のリファレンスで探す。ケースは、200で正しい本文、200で壊れた本文、401でG13の形の本文、500で本文がHTML、`fetch` が失敗する、の5つ以上。偽物の `fetch` が「どんな引数で呼ばれたか」を確かめて、ヘッダが付いていることをテストする
4. 一覧画面を作る。画面の状態は、T6の発展で作った判別可能ユニオンで表す。`useEffect` の中で課題2の関数を呼び、状態に応じて「読み込み中」「一覧」「エラーの文」を描き分ける。StrictModeの下で、ページを開いたときにNetworkタブにリクエストはいくつ出るか。それは問題か。「Synchronizing with Effects」のデータ取得の項を読んで、`notes.md` に書く
5. Goのハンドラに一時的に `time.Sleep` を入れて応答を遅らせ、応答が届く前に画面を切り替える（課題6の詳細画面に移る、または一覧を非表示にする）。Consoleに警告や、古い応答で画面が上書きされる現象は出るか。同じ項にある、不要になった応答を無視する方法を読み、クリーンアップで実装する。確かめたら `time.Sleep` を外す
6. 詳細画面を作る。一覧の1件を押すと、その `id` で1件取得し、表示する。どの画面を出しているかは、stateで表す（選択中の `id` を持つ、など）。存在しない `id`（一覧を取ったあとに `curl` で削除しておく）を開くと、画面には何が出るか。G13で決めたエラーレスポンスの、人が読むメッセージを画面に出す
7. 登録画面を作る。T9の制御されたフォームで `name` と `value` を入力し、POSTする。G13の検証エラー（項目ごとのエラーの一覧）が返ってきたら、該当する入力欄のそばにメッセージを出す。成功したら、一覧に反映する。反映のしかたを2通り考え（一覧を取り直す、返ってきた1件を配列に足す）、どちらにしたか、もう一方だと何が違うかを `notes.md` に書く
8. **本題（その1）**：失敗を画面に出し、再試行できるようにする。次の5つを起こし、それぞれ、課題2の関数がどの種類の失敗を返すかを先に予想してから確かめる。どの場合も、画面にメッセージが出て、Consoleに未処理のエラーが残らず、「再試行」のボタンで、ページを再読み込みせずにやり直せること
   - トークンを間違える（401）
   - 存在しない `id` を開く（404）
   - 検証に通らない値を登録する
   - Goの構造体タグを一時的に変えて、壊れた形の本文を返す（T8の課題9。確かめたら戻す）
   - サーバーを Ctrl+C で止めてから、操作する
9. **本題（その2）**：APIを止めても画面が壊れないことを確かめる。画面を開いたまま、サーバーを止める。一覧の再読み込み、詳細を開く、登録する、の3つの操作をする。それぞれ何が起きるか。proxy経由の場合と、CORSで直接呼ぶ場合で、ブラウザに届くものは同じか（Promiseが失敗するのか、ステータスコードが返るのか。Networkタブで見る）。サーバーを起動し直し、「再試行」だけで一覧が戻ることを確かめる。起きた現象と、直した箇所を `notes.md` に書く
10. トークンの渡し方を決める。Viteの環境変数（`.env` に `VITE_` で始まる名前で書く）で渡す方法と、画面の入力欄で受け取る方法の、両方を試す。環境変数の方法で `npm run build` したあと、`.env` に書いたトークンの値を `grep -r` で `dist/` から探す。何が見つかるか。この結果から、「ブラウザで動くコードに埋めたトークンは、誰に見えるか」を `notes.md` に書き、このユニットではどちらを使うかを決める。`.env` は `.gitignore` に入れ、ダミーの値だけを書いた `.env.example` を残す
11. **本題（その3）**：Testing Libraryで一覧画面をテストする。`fetch` を偽物にした状態で、少なくとも次を確かめる。要素は、`getByRole` や `getByText` のように、利用者に見える手がかりで探す
    - 最初に「読み込み中」が表示される
    - 応答が届くと、一覧の項目が表示される（`findBy` を使う。`getBy` との違いを、失敗の出力で確かめる）
    - 失敗の応答では、エラーの文と「再試行」のボタンが表示される
    - 「再試行」を押すと、偽物の `fetch` がもう一度呼ばれる
12. 登録画面をテストする。`user-event` で入力と送信を行い、偽物の `fetch` に、打った値がJSONの本文として渡されることを確かめる。検証エラーの応答を返したとき、メッセージが入力欄のそばに出ることも確かめる。`fireEvent` と `user-event` の違いを、Testing Libraryのドキュメントで読み、どちらを使うべきかを `notes.md` に書く

### 発展（任意）

- 一覧の取得に失敗したとき、一定の間隔で自動的に再試行する。再試行の回数と間隔を画面に出す。サーバーを止めて再開し、手で押さなくても戻ることを確かめる
- エラーの表示に、レスポンスの `X-Request-ID`（G14）を含める。G14のサーバーのログから、そのIDの行を `grep` で探せることを確かめる。利用者が「この番号で問い合わせる」流れは、閉域の運用でどう役に立つか
- 応答に時間がかかりすぎるとき、途中であきらめる処理を足す（T4の発展の `AbortController`）。クリーンアップと組み合わせる
- 削除のボタンを付け、押す前に確認を求める

## 詰まりやすいところ

- トークンを付けたのに401になる → Networkタブで、実際に送られた `Authorization` の行を見る。proxy経由なら、`curl -H` で `5173` を経由して呼び、ヘッダが中継されているかを確かめる
- CORSで、`Authorization` を付けたとたんに失敗する → Networkタブでプリフライトの応答を見る。G14の課題9の、ミドルウェアの順番を確かめる
- テストで `document is not defined` と出る → Vitestの「Test Environment」を読む。設定を、ファイル単位で指定する方法と、全体で指定する方法のどちらにしたか
- `findBy` が時間切れになる → 偽物の `fetch` が、本当に決着するPromiseを返しているか。`response.json()` に当たるものまで偽物になっているか
- `not wrapped in act(...)` という警告が出る → 非同期の更新を、`findBy` や `waitFor` で待っているかを見直す
- テストなのに本物のAPIを呼んでいる → 偽物に差し替えた場所と、コンポーネントが `fetch` を呼ぶ経路が一致しているか。差し替えのタイミング（テストの前か、importの前か）を、Vitestの「Mocking」で確かめる

## 完了条件の確かめ方

1. G14のサーバーを動かした状態で、一覧・詳細・登録の3画面が動き、登録した1件が一覧に現れる
2. 画面を開いたまま、サーバーを止める。3つの操作をしても、画面が白くならず、メッセージが出て、Consoleに未処理のエラーがない。サーバーを起動し直し、「再試行」だけで一覧が戻る
3. `npx tsc --noEmit --strict`、`npx eslint .`、`npx vitest run` が、すべて終了コード0で終わる。出力に、課題3・11・12のケース名が並ぶ
4. `npm run build` のあと、`grep -rE 'https?://' dist/` に外部のURLがなく、`.env` に書いたトークンが `dist/` の中から見つからない（課題10で決めた方法による）
