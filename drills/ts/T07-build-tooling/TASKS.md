## ねらい

開発用サーバー（Vite）、コードの検査（ESLint）、テスト（Vitest）を、空のディレクトリから設定ファイルを1つずつ書いて組み上げる。ふだんはテンプレート生成のコマンド1つで済む作業だが、閉域ではそのコマンドが動かないことがあり、動いたとしても、壊れたときに直せるのは中身を知っている人だけ。設定の1行ごとに「これは何のためにあるか」を言える状態を作る。

## このユニットで身につけること

- テンプレート生成を使わず、Viteの開発用サーバーを起動する
- ESモジュール（`import` / `export`）でファイルを分ける
- 開発用サーバーと、本番用のビルド結果（`dist/`）の違いを説明する
- `vite.config.ts` を書き、開発中のAPI呼び出しをproxyでGoのサーバーへ中継する
- ESLintの設定ファイルを書き、問題のあるコードを検出させる
- Vitestでテストを書き、失敗したテストの出力を読む
- `package.json` の `scripts` に一連の確認をまとめ、`npm ci` から再現できることを確かめる

## キーワード

- **バンドラ**：たくさんのファイルと依存パッケージを、ブラウザ向けの少数のファイルにまとめる道具
- **Vite**：開発用サーバーとバンドラを兼ねる道具
- **ESモジュール**：`import` と `export` でファイル同士をつなぐ、JavaScript標準の仕組み
- **HMR**：ファイルを保存すると、ページ全体を再読み込みせずに、変更が反映される機能
- **proxy（中継）**：開発用サーバーが、特定のパスへのリクエストを、別のサーバーへ転送する設定
- **リンター**：コードを実行せずに読み、問題のありそうな書き方を指摘する道具。ESLintがその1つ
- **Vitest**：Viteの設定を共有して動く、テストの実行環境。Goの `go test` に当たる
- **npm scripts**：`package.json` の `scripts` に登録し、`npm run 名前` で実行するコマンド

## 平日に読むもの

- 『プロを目指す人のためのTypeScript入門』第7章（TypeScriptのモジュールシステム）
- 『サバイバルTypeScript』の「作って学ぶTypeScript」のPrettierでコード整形を自動化しよう、ESLintでコーディング規約を自動化しよう、Vitestでテストを書こう
- Vite、ESLint、Vitestの公式ドキュメント。DevDocsにあればオフライン保存し、なければ必要なページをブラウザで保存しておく。Viteは「Getting Started」「Features」の中のTypeScriptの項、「Config Reference」の中のServer Options。ESLintは「Configuration Files」。Vitestは「Getting Started」とAPIリファレンスの `test`、`expect`
- 入れたパッケージの `node_modules/<パッケージ名>/` にある `README.md` と型定義（`.d.ts`）も、オフラインで読める資料になる
- パッケージの取得にはネットワークが要る。回線が使えない場合は、`npm install` だけを平日に済ませておく（設定ファイルは、AIなしデーに自分で書く）

## 課題

1. 準備で入ったものを確かめる。`node_modules/.bin/` には、何があるか。`npx vite` と打ったとき、実際に動くのはどのファイルか。`package-lock.json` に記録されたパッケージの数は、直接入れた4つと比べて、どれくらい多いか
2. 最小の構成でViteを起動する。プロジェクトの直下に `index.html` を置き、`src/main.ts` を `script` 要素で読み込む（Viteのドキュメントで、`index.html` の置き場所と、`script` 要素に必要な属性を調べる）。`npx vite` で起動し、ホスト側のブラウザで、表示されたURL（既定では `http://localhost:5173/`）を開く。`main.ts` は、画面に1行出すだけでよい
3. `src/` にもう1つファイルを作り、関数を `export` して、`main.ts` から `import` する。Networkタブで、ブラウザが何を、どの順に読み込んでいるかを見る。`.ts` ファイルの中身は、ブラウザに届いた時点で、どうなっているか。ファイルを保存したとき、ブラウザとNetworkタブで何が起きるか（HMR）
4. `main.ts` に、わざと型エラーを入れる。Viteの開発用サーバーは、エラーを出すか。ブラウザでは動くか。この結果から、型チェックは誰の仕事だと言えるか。Viteのドキュメントの、TypeScriptの項が求めている `tsconfig.json` のオプションを調べ、T5の `tsconfig.json` を直す。直したオプションの意味を `notes.md` に書く
5. `npx vite build` を実行し、`dist/` の中身を読む。ファイル名、ファイルの数、コードの見た目は、`src/` とどう違うか。`npx vite preview` と、`dist/` の中での `python3 -m http.server` の、両方で開いて動くことを確かめる。`grep -rE 'https?://' dist/` で、外部のURLへの参照が紛れ込んでいないかを見る
6. `vite.config.ts` を書く。まず、開発用サーバーのポートを固定し、すでに使われていたら、別のポートに逃げずにエラーで止まるようにする。設定の書き方と、オプションの名前は、ViteのConfig Referenceで探す
7. T4の `fetch` のコードを小さく持ち込み（一覧を取得して表示するだけでよい）、G12のGoのサーバーを、別のシェルで動かす。Viteのページから `/items` を相対パスで呼ぶと、何が返ってくるか。絶対URL（`http://localhost:8080/...`）で呼ぶと、何が起きるか（T4の復習）
8. **本題**：開発中のAPI呼び出しを通す
   - Viteのproxy設定で、APIのパスへのリクエストを、Goのサーバーへ中継する。ブラウザのNetworkタブでは、リクエストの宛先はどこに見えるか。Goのサーバーの側からは、どこから来たように見えるか。`curl http://localhost:5173/items` でも確かめる
   - G14を終えている場合：proxyを使わず、G14のCORSミドルウェアを付けたサーバーを、絶対URLで呼ぶ。Networkタブで、レスポンスヘッダとプリフライトを確かめる
   - 2つの方法の違いを、`notes.md` に書く。本番で、Goのサーバーが `dist/` を配信する構成（T4と同じ同一オリジン）にするなら、どちらが本番に近いか
9. ESLintの設定ファイルを、手で書く（ESLintのドキュメントの「Configuration Files」で、ファイル名と書き方を調べる）。少なくとも、TypeScriptのファイルを検査できる、使っていない変数を検出する、`dist/` を検査の対象から外す、の3つを満たす。わざと違反のあるファイルを作り、`npx eslint .` が指摘することと、そのときの終了コード（`echo $?`）を確かめる。ルールを1つ、自分で選んで足し、選んだ理由を書く
10. **本題**：Vitestでテストを書く。T6の「イベントを1行の文字列にする関数」を `src/` に持ち込み、`*.test.ts` を書く。`npx vitest run` で実行する。わざと失敗させ、出力のどこに、期待した値と実際の値が出るかを読む。GoのG7のテーブル駆動テストに当たる書き方を、Vitestのドキュメントの `test.each` で調べて使う。`npx vitest` と `npx vitest run` は、何が違うか
11. `package.json` の `scripts` に、開発、ビルド、型チェック、リント、テストを登録する。さらに、型チェック・リント・テストを続けて行い、どれか1つでも失敗したら、失敗の終了コードで終わるコマンドを登録する（F5の `&&` の復習）
12. `node_modules` と `dist/` を消し、`npm ci` のあと、課題11のコマンドと `npm run build` がすべて通ることを確かめる。`package-lock.json` をコミットする。回線を切った状態で `npm ci` を実行すると、どうなるか（完全なオフラインでの再現は、Stage 4で扱う）

### 発展（任意）

- Vitestのカバレッジの出力を調べる。追加のパッケージが要る場合は、入れる前に、その依存の数を `npm view` などで確かめ、入れるかどうかを自分で判断する
- `vite build` の出力に、ソースマップを付ける設定を探す。本番で付ける利点と欠点は何か
- `dist/` を、T4のようにGoのサーバーから配信し、Viteなしで動くことを確かめる

## 詰まりやすいところ

- ホスト側のブラウザから、Viteの開発用サーバーに届かない → サーバーが待ち受けているアドレスを `ss -ltn` で見る。ViteのServer Optionsで、待ち受けるアドレスの設定を探す
- `import` したファイルが見つからない、というエラーが出る → パスの書き方（`./` の有無、拡張子）と、`tsconfig.json` のモジュールの解決に関するオプションを確かめる
- proxyを設定したのに、404やHTMLが返る → `curl -v` でVite経由とGo直接の両方を呼び、どちらが応答しているかをヘッダで見分ける。設定したパスの前方一致と、設定の変更後にViteを再起動したかを確かめる
- ESLintが「設定ファイルがない」と言う。または、`.ts` を解析できない → 設定ファイルの名前と置き場所、TypeScript用のパーサーの指定を、ドキュメントで確かめる
- Vitestがテストを見つけない → テストファイルの名前の決まりを、Vitestのドキュメントで確かめる

## 完了条件の確かめ方

1. このディレクトリの履歴に、テンプレート生成を使った跡がない（設定ファイルは、すべて自分で打ったもの）。`notes.md` に、`vite.config.ts`、`tsconfig.json`、ESLintの設定ファイルの、各行の意味が書いてある
2. `npm ci` の直後に、`npm run dev` で開発用サーバーが起動し、ホスト側のブラウザで、Goのサーバーから取得した一覧が表示される
3. `npx tsc --noEmit --strict`、`npx eslint .`、`npx vitest run` が、すべて終了コード0で終わる。テストを1つわざと壊すと、課題11のまとめのコマンドが、0以外で終わる
