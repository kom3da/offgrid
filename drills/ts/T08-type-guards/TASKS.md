## ねらい

T5の課題11で見たとおり、型は実行時には消える。`fetch` で届いたJSONが、型に書いたとおりの形をしている保証はどこにもない。このユニットでは、`unknown` から安全に絞り込む関数を自分の手で書き、G12〜G13のAPIのレスポンスを「信じる前に確かめる」。検証用のライブラリは使わない。仕組みを自分で書いておくと、ライブラリを入れられない現場でも同じ守りを作れるし、ライブラリを使うときも中で何が起きているかが分かる。

## このユニットで身につけること

- `unknown` と `any` の違いを、コンパイラの反応で説明する
- `typeof`、`in`、`Array.isArray` で、`unknown` の値を段階的に絞り込む
- 型述語（`x is T`）を返す関数を書き、呼び出し側で型が絞り込まれることを確かめる
- オブジェクトの型に対応する検証関数を書き、「型が違う」「項目がない」「余分な項目がある」「`null`」を拒否する
- 検証の失敗を、T6の成功・失敗の型で、どの項目がだめかまで返す
- 不正なデータが拒否されることを、Vitestのテーブル駆動テストで示す
- `as` による型の主張と、検証による絞り込みの違いを、実験で説明する

## キーワード

- **`unknown`**：「何が入っているか分からない」ことを正直に表す型。絞り込むまで、ほとんど何もできない
- **`any`**：検査を止める型。何でもできてしまい、間違いは実行時まで見つからない
- **絞り込み（narrowing）**：条件分岐によって、コンパイラが型の候補を狭めること（T6の復習）
- **型ガード**：絞り込みを起こす条件式や関数の総称。`typeof x === "string"` もその1つ
- **型述語（type predicate）**：関数の戻り値の型を `x is T` と書く形。`true` を返したとき、呼び出し側で `x` が `T` に絞り込まれる
- **実行時検証**：プログラムが動いている最中に、値の形を実際に確かめること。コンパイル時の型検査とは別物
- **信頼境界**：自分のコードが書いた値と、外（ネットワーク、ファイル、ユーザー）から来た値の境目。検証は境目で行う
- **型の主張（`as`）**：「この値はこの型だ」とコンパイラに言い切る書き方。何も確かめない

## 課題

1. `unknown` 型の変数に、文字列・数値・オブジェクト・`null` を順に代入し、それぞれの状態で、メソッドの呼び出し、プロパティの読み取り、`string` 型の変数への代入を試す。どれがコンパイルエラーになるか。同じことを `any` 型で試すと、どうなるか。`JSON.parse` の戻り値の型は何か（`node_modules/typescript/lib/` の中で、宣言を `grep` で探す）。その型は、T5の課題11の問題と、どう関係しているか
2. `unknown` を受け取り、文字列なら大文字にして返し、それ以外なら `null` を返す関数を書く。`typeof` で分岐したあと、分岐の中で型がどうなっているかを確かめる。次に、「文字列かどうか」を返す関数を、戻り値の型を `boolean` にした版と、型述語にした版の2通りで書く。呼び出し側の `if` の中で、変数の型はそれぞれどうなるか。何が違うか
3. `typeof x === "object"` で絞り込んだあと、`x` の型は何になっているか。`null` を渡すと、この条件は `true` と `false` のどちらになるか（T2で見た `typeof null` を思い出す）。オブジェクトのプロパティに触るには、さらに何を確かめる必要があるか。Handbookの「Narrowing」で、`in` による絞り込みの項を読み、`name` というプロパティを持つことを確かめたあとで、`name` の型が何になっているかを見る
4. アイテム1件の型（T5で定義したもの。G13の `api.md` と一致させる）に対する型述語の関数を書く。`id` と `value` が数値、`name` が文字列であることを確かめる。次に、アイテムの配列に対する型述語を書く（`Array.isArray` のあと、要素の型は何になっているか。要素を1つずつ確かめる）
5. **本題（その1）**：課題4の関数に、Vitestでテーブル駆動テストを書く（`test.each`）。少なくとも、次のケースを入れ、不正なものがすべて拒否されることを確かめる
   - 正しいアイテム
   - 型が違う（`id` が文字列、`value` が文字列の `"10"`、`name` が数値）
   - 項目がない（`name` がない、`value` がない、空のオブジェクト）
   - 余分な項目がある（`{"id":1,"name":"a","value":1,"admin":true}`）。このユニットでは拒否する。G13の課題3でサーバー側に決めた方針と比べ、揃えるべきかを `notes.md` に書く
   - `null`、`undefined`、数値、文字列、配列（1件のつもりで配列が来た）
   - 配列のテスト：空の配列、正しい要素だけ、正しい要素の中に1つだけ壊れた要素が混ざったもの、配列でなくオブジェクト
6. 検証の失敗に理由を付ける。`true` / `false` ではなく、T6の課題8で作った成功・失敗の型を返す検証関数を書く。失敗のときは、どの項目が、なぜだめか（G13の課題5と同じ考え方）をメッセージに入れる。課題5のケースごとに、期待するメッセージをテストで確かめる。型述語の版と、理由を返す版は、どちらを残すか。両方を残すなら、どう使い分けるか
7. G13で決めたエラーレスポンスの形（`api.md`）に対する検証関数を書く。「アイテムの一覧」と「エラーレスポンス」のどちらが来たかを、ステータスコードを見ずに本文だけで見分けられるか。見分けられないなら、どう設計すべきか。テストを足す
8. `as` の実験。壊れたJSON（`value` が文字列のもの）を `JSON.parse` し、`as` でアイテムの配列だと主張して、合計を計算する関数に渡す。コンパイルエラーは出るか。実行すると、どこで、何が起きるか（エラーになるか、黙っておかしな値になるか）。同じデータを課題6の検証関数に通した場合と、「問題に気づく場所」がどう違うかを `notes.md` に書く。あわせて、`"abc" as number` と `"abc" as unknown as number` は、それぞれコンパイルできるか
9. **本題（その2）**：T7の課題7で持ち込んだ `fetch` のコードに、検証を組み込む。`response.json()` の結果を検証に通し、通らなければ画面にメッセージを出す。次に、G12のGoのコードの構造体タグを一時的に変え（例：`value` を `val` にする）、サーバーを起動し直す。検証なしのコードと検証ありのコードで、画面とConsoleはそれぞれどうなるか。確かめたら、Goのコードを元に戻す
10. 課題4の配列の検証を、ジェネリクス（T6）で書き直す。「要素の型述語を受け取り、その配列の型述語を返す関数」にし、アイテムの配列と、文字列の配列の両方で使えることを確かめる。型引数と型述語を組み合わせたときの書き方は、Handbookの「Generics」と「Narrowing」を行き来して探す
11. アイテムの型に、項目を1つ仮に足す（例：`createdAt: string`）。課題4〜6の検証関数は、コンパイルエラーになるか。ならないなら、型と検証のずれに気づく仕組みを、テストでどう作れるかを考えて `notes.md` に書く。確かめたら、足した項目を元に戻す
12. 今のフロントエンドのコードの中で、外から値が入ってくる場所をすべて列挙する（`fetch` の本文、フォームの入力、T3の発展で使った `localStorage`、URLのクエリ文字列など）。それぞれ、検証が要るか、要らないかを、理由と一緒に `notes.md` に書く

### 発展（任意）

- `try` / `catch` の `catch` で受け取る値の型は、`strict` のとき何になっているか。`Error` かどうかを絞り込んで、メッセージを取り出す関数を書く
- 数値の検証で、`NaN` や `Infinity` は通るか。通るなら、通すべきかを考え、`Number.isFinite` をMDNで調べる。JSONの文字列から `NaN` が生まれることはあるか
- 日時を表す文字列の項目を想定し、「文字列である」だけでなく「日時として読める」ことまで検証する関数を書く。`Date` のコンストラクタが不正な文字列を受け取ったとき、何を返すかをMDNで調べる

## 詰まりやすいところ

- 型述語を書いたのに、`if` の中で型が絞り込まれない → 関数の戻り値の型注釈が `boolean` になっていないかを見る。課題2の比較に戻る
- `typeof x === "object"` のあとでプロパティに触ると、エラーになる → 課題3。`null` の可能性と、「どんなプロパティがあるか分からない」ことを、コンパイラがどう扱っているかを、エラーの文で読む
- `in` で確かめたのに、プロパティの型が `unknown` のまま → `in` が保証するのは「存在すること」だけ。そのプロパティの値に対して、さらに何が要るかを考える
- 余分な項目を検出したいが、どのキーがあるかを調べる方法が分からない → MDNの `Object.keys()` を読む
- `expect(...).toBe(...)` が、同じ内容のオブジェクトなのに失敗する → Vitestのドキュメントで、`toBe` と `toEqual` の違いを読む
- 課題9で、検証に失敗したのに画面に何も出ない → `fetch` の失敗と、検証の失敗が、同じ経路で画面に届いているかを、ブレークポイントで追う（T3の課題11）

## 完了条件の確かめ方

1. `npx vitest run` が通り、出力に、課題5と課題6のケース名が並ぶ（ケース名を1つずつ表示する設定は、Vitestのドキュメントの「Reporters」で探す）。型違い・項目なし・余分な項目・`null` の4種類が、それぞれ少なくとも1ケースずつ拒否されている
2. 検証関数の検査を1つわざと消す（例：`value` が数値であることの検査）と、テストが落ちる。確かめたら、元に戻す
3. `npx tsc --noEmit --strict` と `npx eslint .` が、終了コード0で終わる。`grep -n ' as ' src/` の結果が、課題8の実験用のファイルと `as const` を除いて0件、または理由が `notes.md` に書いてある
