## ねらい

「結果があとから届く処理」を、コールバック、Promise、`async`/`await` の順に書き、ブラウザから自分のGoのAPIを呼ぶ。通信は必ず失敗することがあるので、失敗を画面に出すところまでを1セットにする。あわせて、ブラウザが通信を止めるCORSエラーをわざと起こし、Networkタブで観察する。閉域の現場では「つながらない」の原因を自分で切り分けるしかなく、サーバーの問題なのかブラウザの決まりなのかを見分けられることが大事になる。

## このユニットで身につけること

- 非同期の処理が、書いた順番どおりには実行されないことを、実験で示す
- 同じ処理を、コールバック、Promise、`async`/`await` の3通りで書き分ける
- `fetch` でGET・POST・DELETEを送り、JSONを受け取って画面に出す
- 「通信そのものの失敗」と「サーバーがエラーのステータスを返した」を区別して扱う
- 失敗したとき、画面にメッセージを出す
- Networkタブで、リクエストとレスポンスのヘッダ、ステータス、本文を読む
- CORSエラーを再現し、起きる条件を説明する

## キーワード

- **非同期処理**：終わるのを待たずに次へ進み、結果はあとで受け取る処理
- **コールバック**：「終わったら呼んでほしい関数」を、引数として渡す書き方
- **Promise**：「あとで届く結果」を表すオブジェクト。成功（resolve）か失敗（reject）のどちらかで決着する
- **`async` / `await`**：Promiseを、上から順に読める形で書くための構文
- **`fetch`**：ブラウザとNode.jsに組み込まれた、HTTPリクエストを送る関数
- **同一オリジン**：スキーム・ホスト・ポートがすべて同じであること
- **CORS**：別オリジンのサーバーを呼ぶとき、サーバーが許可した場合だけ、ブラウザが結果を渡す仕組み
- **プリフライト**：条件によってブラウザが本番のリクエストの前に送る、確認用の `OPTIONS` リクエスト

## 課題

1. `order.js` を作り、「Aを表示」「`setTimeout` に0ミリ秒を指定して、Bを表示する関数を渡す」「Cを表示」の順に書く。表示される順番を予想してから、`node order.js` で確かめる。なぜその順になるのか
2. コールバック：「1秒後に1を表示、その1秒後に2を表示、その1秒後に3を表示」を、`setTimeout` の入れ子で書く。これが10段になったら、コードの形はどうなるか
3. Promise：「指定したミリ秒だけ待って決着するPromise」を返す関数を、自分で作る（MDNの `Promise` のコンストラクタの項を読む）。それを使い、課題2を `then` の連鎖で書き直す。途中で失敗（reject）させると、後ろの `then` と `catch` は、それぞれ呼ばれるか
4. `async`/`await`：課題3を、`async` 関数と `await` で書き直す。失敗は `try` / `catch` で捕まえる。`await` を1つ書き忘れると、何が表示されるか。エラーは出るか
5. `server/` のGoのコードを変更し、`web/` の中のファイルを `/` で配信するようにする。APIのパス（`/items` など）は、これまでどおり動くこと。ホスト側のブラウザで `http://localhost:8080/` を開き、`index.html` が表示されることを確かめる。`curl` でAPIも確かめる
6. 課題5のページを開いた状態で、Consoleに `fetch` を直接打ち込み、一覧を取得する。`fetch` が返すものは何か。`status`、`ok`、ヘッダは、どう読むか。本文のJSONを取り出すのに、なぜもう一度 `await` が要るのか。同じ通信を、Networkタブで選び、ヘッダ・本文・かかった時間を読む
7. **本題**：`web/main.js` に、次を作る（DOM操作はT3と同じ。ライブラリは使わない）
   - ページを開いたとき、APIから一覧を取得して表示する
   - フォームから1件登録する（POST、本文はJSON）。登録できたら、一覧に反映する
   - 1件ずつ削除できる
   - 通信している間は「読み込み中」と表示する
8. POSTのとき、`Content-Type` ヘッダを付けない場合と付けた場合で、Goのサーバー側の動きは変わるか。Networkタブの「リクエストヘッダ」と「送信した本文」で、実際に送られたものを確かめる
9. **本題**：失敗を画面に出す。次の3つを起こし、それぞれ `fetch` のPromiseは成功と失敗のどちらで決着するかを、まず観察する。そのうえで、どの場合も画面にメッセージが出て、Consoleに未処理のエラーが残らないようにする
   - 存在しないIDを削除する（404）
   - サーバーが受け付けない内容を登録する（G12の実装が返すエラーのステータス）
   - サーバーを Ctrl+C で止めてから、操作する
10. **本題**：CORSエラーを再現する。シェルをもう1つ開き、`web/` の中で `python3 -m http.server 8001` を動かす。`main.js` のAPIのURLを、`http://localhost:8080` から始まる形に一時的に変え、ブラウザで `http://localhost:8001/` を開く
    - Consoleには、何と表示されるか。メッセージを記録する
    - Networkタブでは、そのリクエストはどう表示されるか。リクエストヘッダの `Origin` には、何が入っているか
    - 一覧の取得（GET）は、Goのサーバーに届いているか。届いたかどうかを確かめる方法を考える（ハンドラに一時的にログの出力を足す、など）
    - JSONのPOSTでは、Networkタブにリクエストがいくつ出るか。GETのときと、何が違うか
11. 同じAPIを、`curl` で `-H 'Origin: http://localhost:8001'` を付けて呼ぶ。結果は返ってくるか。このことから、CORSで通信を止めているのは誰だと言えるか。`http://localhost:8080` と `http://127.0.0.1:8080` は、同一オリジンか。ブラウザで確かめる
12. 課題10で変えたURLを、元に戻す。CORSエラーを、サーバー側の設定で解消するのはG14で行う。ここでは直さず、解消には「誰が、何をする必要がありそうか」の予想だけを `notes.md` に書く

### 発展（任意）

- 3件の詳細を、1件ずつ順番に取得する場合と、同時に取得する場合で、かかる時間を比べる（MDNで `Promise.all` を調べる）。Networkタブのタイムラインでは、どう見えるか
- 応答に時間がかかりすぎるとき、途中であきらめる処理を足す（MDNで `AbortController` を調べる）。Goのハンドラに一時的に `time.Sleep` を入れて試す
- `order.js` に、決着済みのPromiseの `then` を足し、`setTimeout` のコールバックと、どちらが先に実行されるかを観察する

## 詰まりやすいところ

- 画面に `[object Promise]` と出る。または、値が `undefined` になる → その値を作っている関数が `async` かどうか、呼び出し側に `await` があるかを確かめる
- 404なのに、`catch` の処理に入らない → `fetch` が「失敗」とみなす条件を、MDNの `fetch()` のページで読む
- `/` でHTMLを配信するようにしたら、APIが動かなくなった。または、その逆 → `go doc net/http ServeMux` の、パターンの優先順位の説明を読む
- POSTしたのに、Goの側で本文が空、またはJSONの読み取りに失敗する → Networkタブで、送った本文とヘッダを確かめる。オブジェクトをそのまま渡していないか
- CORSエラーを起こしたいのに、普通に動いてしまう → ブラウザのアドレス欄のポートと、`fetch` に渡しているURLが、本当に別オリジンかを確かめる
