## ねらい

T2で体験した「間違っていても黙って動く」問題を、実行する前に見つける道具がTypeScript。npmでプロジェクトを作り、TypeScriptを入れ、設定ファイルの意味を1つずつ確かめながら、T3のToDoを書き換える。閉域では、パッケージを好きなときに取ってこられない。何が、どこに、どの版で入ったのかを自分で把握し、同じ状態を作り直せることを、最初のパッケージから習慣にする。

## このユニットで身につけること

- `npm init` でプロジェクトを作り、`package.json` の各項目の意味を説明する
- パッケージを開発用として入れ、`node_modules` と `package-lock.json` の役割を区別する
- `tsc` で `.ts` を `.js` に変換し、変換後のファイルで型がどうなったかを確かめる
- `tsconfig.json` を自分で書き、書いたオプションの意味を説明する
- 基本の型（数値、文字列、真偽値、配列、オブジェクト、関数、`null` を含む型）を書く
- コンパイルエラーの文から、ファイル・行・原因を読み取る
- `strict` を有効にした状態で、DOMを扱うコードから型エラーをなくす

## キーワード

- **パッケージ**：npmで配られるコードのまとまり。TypeScriptのコンパイラも、パッケージの1つ
- **`package.json`**：プロジェクトの名前、使うパッケージ、実行するコマンド（scripts）を書くファイル
- **`package-lock.json`**：実際に入ったパッケージの、正確な版と出どころの記録。必ずコミットする
- **`node_modules`**：パッケージの実体が入るディレクトリ。コミットしない
- **`npx`**：プロジェクトに入れたパッケージのコマンドを実行する道具
- **コンパイル（トランスパイル）**：TypeScriptのコードを、ブラウザやNode.jsが実行できるJavaScriptに変換すること
- **型注釈**：`: number` のように、変数や引数の型を書き添えること
- **型推論**：型注釈を書かなくても、コンパイラが値から型を決めること
- **`strict`**：厳しい検査をまとめて有効にする、`tsconfig.json` のオプション

## 課題

1. 準備で何が起きたかを読む。`package.json` の各項目は、何を表すか。`devDependencies` と `dependencies` は、どう使い分けるか。`node_modules` の中には、いくつのパッケージが入ったか。`package-lock.json` には、`package.json` にない、どんな情報が書かれているか。`tsc` の実体は、`node_modules` のどこにあるか
2. `hello.ts` に、型注釈つきの変数と、引数と戻り値に型を付けた関数を書く。`npx tsc hello.ts` で変換し、できた `hello.js` を読む。型注釈は、どこへ行ったか。`node hello.js` で実行する
3. わざと型エラーを5種類出し、エラーの文を記録する（数値の変数に文字列を代入、引数の数が違う、存在しないプロパティを読む、戻り値の型が違う、`null` かもしれない値のプロパティを読む）。エラーの文の、ファイル名・行・列・エラー番号は、どこに書かれているか。エラーがあるとき、`.js` は出力されるか
4. 基本の型を練習する。配列の型、オブジェクトの型（`type` で名前を付ける）、省略できるプロパティ、関数の型、`string | null` のように `null` を含む型。変数にマウスを重ねたとき（またはエラーの文）で、型注釈を書かなかった変数の型がどう推論されたかを確かめる。`let` と `const` で、推論される型は同じか
5. `tsconfig.json` を、自分の手で書く。`npx tsc --init` が出力するファイルを参考に眺めてもよいが、残すのは、TSConfigのリファレンスで意味を調べて理解したオプションだけにする。少なくとも、次のことを決める。決めたオプションの名前と意味を、`notes.md` に1行ずつ書く
   - 厳しい検査を有効にする
   - ソースを置くディレクトリと、出力先のディレクトリ
   - 出力するJavaScriptの版
   - ブラウザのDOMの型（`document` など）を使えるようにする
6. `tsconfig.json` を置いた状態で、`npx tsc` と、`npx tsc ファイル名` をそれぞれ実行する。`tsconfig.json` の設定は、どちらの場合に使われるか。`npx tsc --noEmit` は、何をして、何をしないか
7. `strict` の効果を確かめる。型注釈のない引数を持つ関数と、`document.querySelector` の結果をそのまま使うコードを書き、`strict` を `true` にした場合と `false` にした場合で、エラーの出方を比べる。`strict` は、どんな検査をまとめたものか。リファレンスで一覧を探す
8. T2のFizzBuzzと単語の集計を、型を付けて書き直す。単語と件数の対応を表す型は、どう書くか（Handbookで、インデックスシグネチャか `Record` を調べる）
9. **本題**：T3のToDoを、TypeScriptに書き換える。T3の `index.html`、`style.css`、`main.js` をコピーし、`main.js` は `src/main.ts` に名前を変えて始める。`index.html` は、コンパイル後の `.js` を読み込むようにする
   - ToDo1件を表す型を定義する
   - `npx tsc --noEmit --strict` で、エラーを0にする
   - `any`、`as`、末尾の `!` は、できるだけ使わない。使った場合は、箇所と理由を `notes.md` に書く
   - `python3 -m http.server 8000` で配信し、ホスト側のブラウザで `http://localhost:8000/` を開いて、T3と同じに動くことを確かめる
10. 変数に `any` と注釈すると、課題3のエラーのうち、どれが消えるか。消えたあと、実行すると何が起きるか。`any` が「危険」と言われる理由を、この実験をもとに書く
11. 型は、実行時には存在しない。ToDoの型と形の合わないJSONの文字列を `JSON.parse` し、ToDoの配列の型の変数に代入する。コンパイルエラーは出るか。実行すると、どこで、どんなおかしなことが起きるか（T8で、この問題に対処する）
12. `package.json` の `scripts` に、ビルドと型チェックのコマンドを登録し、`npm run` で実行する。次に、`node_modules` を消してから `npm ci` を実行し、ビルドがまた動くことを確かめる。`npm install` と `npm ci` は、何が違うか（`npm help ci` を読む）

### 発展（任意）

- `tsconfig.json` の出力するJavaScriptの版を、古いものと新しいもので切り替え、アロー関数や `const` が、出力でどう変わるかを見比べる
- ソースマップを出力する設定を探し、ブラウザのブレークポイントを、`.js` ではなく `.ts` の行に置けることを確かめる
- `noUncheckedIndexedAccess` を有効にすると、配列の要素を読むコードに何が起きるか。T2の「範囲の外の添字」の実験と結び付けて考える

## 詰まりやすいところ

- `document` や `console` が見つからない、というエラーが出る → TSConfigのリファレンスで、実行環境の型を指定するオプションを探す
- 入力欄の `value` を読もうとすると、「そのプロパティはない」と言われる → `querySelector` が返す型を、エラーの文で確かめる。Handbookの「Narrowing」で、`instanceof` による絞り込みを読む。MDNで、その要素のインターフェース名を調べる
- 「`null` の可能性がある」というエラーが消えない → `null` の場合に何をするべきかを、先に決める。`if` で確かめたあとの行で、型がどう変わるかをエラーの文で見る
- `.ts` を直したのに、ブラウザの動きが変わらない → ブラウザが読み込んでいるのは、どのファイルか。コンパイルし直したか。出力先はどこか
- 設定を書いたのに、効いていないように見える → 課題6の実験に戻る

## 完了条件の確かめ方

```sh
npx tsc --noEmit --strict
```

が、何も表示せずに終わる（終了コードを `echo $?` で確かめる）。コンパイルした結果をブラウザで開き、T3の課題6の5項目がすべて動く。`any` と `as` を使った箇所が、`grep -n` で数えて `notes.md` の記録と一致する。
