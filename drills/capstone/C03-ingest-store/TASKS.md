## ねらい

agent から届いたデータを検証し、PostgreSQL に保存し、保持期間を過ぎたものを自動で消す server の「入口」を作る。閉域の現場では、DBが壊れたり膨らんだりしても、外の助けを呼べない。空のDBからいつでも作り直せること、ディスクが勝手に埋まらないことを、最初から仕組みにしておく。

## このユニットで身につけること

- C1 のテーブル設計を、番号付きのマイグレーションにして、空のDBから再構築する
- 受信した JSON を検証し、不正な入力を、理由の分かるエラーで断る
- `pgx` で、プレースホルダを使って保存する。DBのエラーをラップして返す
- 保存のテストを、本物の PostgreSQL に対して書く
- 画面が出す問い合わせに対して、`EXPLAIN` でインデックスが効くことを確かめる
- 保持期間を過ぎたデータを、定期的に消す処理を、止められる形で動かす
- `go mod vendor` で依存を固め、ネットワークなしでビルドできる状態を保つ

## キーワード

- **マイグレーション**：スキーマの変更を、番号付きのSQLファイルで順に適用していく管理方法（D13）
- **入力の検証**：受け取ったデータが、決めた形と範囲に収まっているかを、保存する前に確かめること（G13）
- **プレースホルダ**：SQL文の中の `$1` のような穴。値を文字列連結せずに渡すためのもの（G17）
- **コネクションプール**：DBへの接続を使い回す仕組み。`pgx` の `pgxpool`
- **保持期間**：データを残しておく長さ。C1 のADRで決めた値
- **実行計画**：DBが、その問い合わせをどういう手順で実行するかの見積もり。`EXPLAIN` で見る（D9、D14）
- **べき等**：同じ操作を何回行っても、結果が変わらない性質。マイグレーションの再実行で問題になる

## 準備

実装は、リポジトリの `capstone/` に置く（この `TASKS.md` の隣ではない）。このディレクトリには、作業メモだけを置く。開発中のDBは、`pg-offgrid` コンテナの中に watchdeck 用のデータベースを1つ作って使う（作り方は D1）。

```sh
cd ~/offgrid-log/capstone
mkdir -p cmd/server migrations
touch ../drills/capstone/C03-ingest-store/notes.md
docker exec -it pg-offgrid psql -U postgres     # ここでデータベースを作る
```

DBの接続先は、`capstone/.env` に書く（Gitの管理外）。`pgx` は、平日のうちに `go get` し、`go mod vendor` まで済ませておく。ネットワークなしでもビルドできる状態にしておく（C7で、実際に切って確かめる）。

## 課題

1. C1 の `schema.md` を、`migrations/` の番号付きSQLファイルにする。D13 で決めた自分のやり方（ファイル名の付け方、適用済みの番号の記録）を使う。watchdeck 用のデータベースを消して作り直し、空の状態から全ファイルを順に適用できることを確かめる。同じファイルを2回適用すると、どうなるか。どうなるべきか
2. `psql` から、制約が効いていることを手で確かめる。使用率が範囲の外の値、存在しないサーバーの計測値、時刻が NULL の行を、それぞれ `INSERT` して、どのエラーになるかを `notes.md` に書く
3. `cmd/server` に、起動して `.env` の設定を読み、DBに接続し、接続できなければ理由を出して終了するところまでを書く。DBが動いていない状態で起動すると、どんなエラーになるか。パスワードを間違えると、どうなるか。ログに、パスワードやトークンが出ていないか
4. 受信のハンドラを書く。まだ保存はせず、C1 の `api.md` のとおりに JSON を受け取って検証する。次の入力で、それぞれ何番のステータスと、どんな本文を返すかを決めて実装する：JSONとして壊れている／必須の項目がない／使用率が範囲の外／時刻が未来すぎる・古すぎる／本文が極端に大きい／知らない項目が入っている。`go doc http.MaxBytesReader`、`go doc json.Decoder` を読む
5. 課題4のハンドラに、`httptest` でテーブル駆動テストを書く。正常系が1つ、異常系が課題4に挙げた数だけある
6. 保存の層を `internal/` の下に書く。ハンドラが、保存の層を小さなインターフェース越しに呼ぶ形にする（ハンドラのテストで、偽の保存先に差し替えるため）。値は必ずプレースホルダで渡す。「登録したサーバー」にない名前から届いたデータをどう扱うかは、C1 のADRに従う（決めていなければ、ADRを足してから実装する）
7. 保存の層のテストを、本物のDB（テスト用のデータベース）に対して書く。テストの最初に、マイグレーションで空のスキーマを作る。ホスト名に `'; DROP TABLE` を含む入力でも壊れないことを、テストで確かめる（G17）。DBが動いていない環境では、テストはどう振る舞うべきかを決める
8. **本題**：agent（C2）から server に実際に送り、`psql` で行が10秒ごとに増えることを確かめる。agent の送るトークンを、この時点でどう検証するか（G14 の簡易トークン認証を使う。作り込むのは C4）。server を止めて再開し、agent の送信が自動で戻ることも見る
9. ダミーデータを作る。10台・10秒間隔・保持期間ぶんの行を、SQL（`generate_series`）で入れる。C1 の課題7で書き出した問い合わせ（一覧用の「各サーバーの最新の1件」、グラフ用の「1台の過去24時間」、期間を変えたもの）を実際に書き、`EXPLAIN (ANALYZE, BUFFERS)` で、インデックスが使われているか、実行時間はどのくらいかを記録する。インデックスを消した場合と比べる
10. 古いデータの削除を実装する。server の中で、決めた間隔ごとに、保持期間を過ぎた行を消す。`context` で止められるようにし、消した行数をログに出す。確かめるために、保持期間と間隔を、設定で短く（たとえば数分に）できるようにする。削除が走っている間に、受信は止まらないか
11. 削除のテストを書く。保持期間の内側と外側の時刻の行を入れ、外側だけが消えることを確かめる。境界ちょうどの時刻の行は、どちらになるか。タイムゾーンの設定を変えても、結果は同じか（D8）
12. `go mod tidy`、`go mod vendor` を行い、`go clean -modcache` のあとで `go build -mod=vendor ./...` と `go test -mod=vendor ./...` が通ることを確かめる。そのあいだ `ss` に外向きの接続が出ないこと（O7）

### 発展（任意）

- 1回のリクエストで、複数の計測値をまとめて受け取れるようにする。途中の1件が不正なとき、全体をどう扱うかを決め、トランザクションで実装する
- 課題9を100台ぶんの行数でもう一度行い、実行時間の変化を記録する
- 削除を、大量の行でも長いロックを取らない形にできるかを、PostgreSQLマニュアルで調べてメモする

## 詰まりやすいところ

- マイグレーションの2回目の適用で、エラーになって止まる → 「適用済み」をどこに記録し、どう読み飛ばしているかを、D13 の自分のメモで確かめる
- テストが、実行する順番や回数で、通ったり落ちたりする → テストどうしが、同じテーブルの行を共有していないかを疑う。テストの前後の片付けを見直す
- `EXPLAIN` が、インデックスがあるのに Seq Scan を選ぶ → 行数が少なすぎないか、統計情報が古くないか（マニュアルの `ANALYZE` の節）、問い合わせの条件と並び順が、インデックスの列の順と合っているかを確かめる
- 保存される時刻が、9時間ずれて見える → 列の型、`psql` の `SHOW timezone`、Go側の `time.Time` のタイムゾーンを、それぞれ確かめる（D8）
- 削除のgoroutineが、server の終了後も動いている、または `-race` で警告が出る → 起動した goroutine に `context` が渡っているか、終了を待っているかを確かめる（G15、G16）
- `-mod=vendor` でビルドが止まる → `go env GOFLAGS`、`vendor/modules.txt` の有無、`go build` に付けたオプションを確かめる（G18）
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。受信、検証、保存、削除は、すべてそれにあたる。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- watchdeck 用のデータベースを消して作り直し、マイグレーションを適用し、server と agent を起動すると、1分後に `psql` で6行前後が入っている
- `go vet ./... && go test -race -cover ./...` が通る。受信のハンドラに、課題4の異常系すべてのテストがある
- `curl` で不正な JSON を送ると、`api.md` に書いたとおりのステータスとエラーの本文が返る。`curl` のコマンドと結果を `notes.md` に残す
- 課題9の3種類の問い合わせについて、`EXPLAIN (ANALYZE, BUFFERS)` の結果（インデックスあり・なし）が `notes.md` にあり、インデックスありの実行計画で、計測値のテーブルに Seq Scan が出ていない（出る問い合わせがあれば、問い合わせの書き方かインデックスを見直し、直す前後を記録する）
- 保持期間を数分に設定して server を動かし、期間を過ぎた行が、手を触れずに消える。消えた行数のログと、前後の `SELECT count(*)` の結果を残す
- `go clean -modcache` のあとでも `go build -mod=vendor ./...` が通り、`ss` に外向きの接続が出ない（O7）

## 残すもの

- `capstone/migrations/`、`capstone/cmd/server/`、`capstone/internal/` の下のパッケージとテスト、`capstone/vendor/`
- ダミーデータを入れるSQL（`capstone/migrations/` とは別の場所に置く。本番のDBに入れないため）
- このディレクトリの `notes.md`：課題2の制約の確認、課題9の実行計画、削除の確認、詰まったこと
- 設計を変えたら、C1 のADRと `schema.md` を直す（古い決定は消さず、変えた理由を書く）

この `TASKS.md` はカリキュラムの一部なので、書き換えない。
