## ねらい

watchdeck が「閉域で、自分以外の人でも、作り直して動かし続けられる」ことを、試験の結果で示す。ネットワークを切って一から再構築し、わざと壊して復帰を確かめ、その手順を runbook に残す。動くものを作るだけでなく、動かなくなったときの振る舞いを知っていることが、閉域の現場での信頼になる。必須版は、このステップで完成する。

## このユニットで身につけること

- 試験を、「手順・期待する結果・実際の結果・合否」の形で計画し、記録する
- ネットワークを切った新しい環境に、持ち込んだファイルだけで、ビルドから起動までを行う
- DBの停止、server の停止と再開に対して、各部品がどう振る舞い、どう戻るかを観察する
- 10台・10秒間隔の送信で、一覧とグラフが問題なく動くことを確かめる
- 起動、停止、確認、よくある障害への対応、バックアップと復元を、runbook に書く
- 自分の runbook を、「自分の記憶を使わずに」なぞって検証する
- 卒業制作の全体を振り返り、AIなしで書いた部分と、AIを使った部分を、理由付きで区分けする

## キーワード

- **runbook（運用手順書）**：そのシステムを知らない人が、書いてあるとおりに打てば運用できる手順の集まり
- **障害試験**：部品をわざと止め、システム全体の振る舞いと復帰を確かめる試験
- **復帰時間**：障害の原因を取り除いてから、正常な状態に戻るまでの時間
- **期待する結果**：試験の前に書いておく予想。後から書くと、試験にならない
- **閉域での再構築**：外部ネットワークに一切出ずに、ビルドから起動までを行うこと（O8）
- **ポストモーテム**：障害のあとに書く振り返り。誰の責任かではなく、何が起き、何を学んだかを書く
- **縮退**：一部が壊れても、残りの機能を止めずに動かし続けること

## 準備

試験の計画、結果、runbook は、リポジトリの `capstone/docs/` に置く（この `TASKS.md` の隣ではない）。このディレクトリには、作業メモだけを置く。

```sh
cd ~/offgrid-log/capstone
mkdir -p docs/tests
touch ../drills/capstone/C07-offline-rebuild/notes.md
```

再構築の試験には、まっさらな環境が要る。O8 と同じやり方で、新しい仮想マシン（または、作り直した Ubuntu の環境）を用意する。持ち込むのは、リポジトリ一式（`vendor/` を含む）、npm のオフラインキャッシュ、`docker save` したイメージ、agent のバイナリ、`.env`。ネットワークの切り方と、切れていることの確かめ方は、O8 の自分のメモに従う。Web検索は0回。

試験結果に貼るログや画面の写しは、ホスト名をダミー（`web01.example.test` など）に、IPアドレスを例示用の範囲（`192.0.2.0/24` など）に置き換え、トークンを伏せてからコミットする。

## 課題

1. 試験計画を `capstone/docs/tests/plan.md` に書く。C1 の `requirements.md` の必須の要件を1つずつ取り上げ、それを確かめる試験の「手順・期待する結果」を書く。「実際の結果・合否」の欄は、空けておく。課題3〜8の試験が、どの要件に対応するかを示す
2. runbook の初版を `capstone/docs/runbook.md` に書く。少なくとも次の節を持つ：必要なもの（持ち込むファイルと、その `sha256sum`）／中央側の構築と起動／agent の導入／動作確認（打つコマンドと、期待する出力）／停止と再起動／設定の変更（サーバーの登録、トークンの作り直し、保持期間の変更）／バックアップと復元（D11）／よくある障害と、最初に見る場所
3. **本題**：閉域での完全再構築。まっさらな環境でネットワークを切り、切れていることを確かめてから、runbook の手順だけで、Go のビルド（`-mod=vendor`）、web のビルド（`npm ci --offline`）、イメージのビルドまたは `docker load`、`docker compose up -d`、agent の導入までを行う。かかった時間と、runbook に書いていなかったのに打ったコマンドを、すべて記録する
4. 課題3で見つかった抜けを runbook に反映し、環境を作り直して、もう一度行う。「runbook にないコマンド」が0個になるまでくり返す
5. 障害試験1：DBの停止。compose の PostgreSQL のサービスだけを止める。止める前に、次のそれぞれがどうなるかの予想を `plan.md` に書く：agent の送信への応答／一覧とグラフの REST／つながっている SSE／web の画面の表示／server のプロセスとログ。止めて2分おき、観察を記録する。DBを再開し、手を触れずに正常に戻るまでの秒数を測る
6. 障害試験2：server の停止と再開。agent を動かしたまま、server を止めて5分おく。agent のログで、再試行の間隔が C1 のADRのとおりに空いていくことを確かめる。agent のメモリが増え続けていないかを見る。server を再開し、agent の送信と web の表示が、手を触れずに戻るまでの秒数を測る。止まっていた間のデータは、グラフでどう見えるか（失ってよい、が要件）
7. 障害試験3：agent の停止と、OSの再起動。agent を止め、一覧の表示が「停止」に変わるまでの秒数を測る。agent を動かしているマシンを再起動し、agent が自動で起動して、表示が戻ることを確かめる。中央側のマシンを再起動すると、どうなるか。compose のサービスは、自動で戻るか。戻らないなら、runbook に何を書くべきか
8. 10台の試験。C2 のホスト名の指定を使い、1台のマシンから10台ぶんの agent を10秒間隔で30分動かす。一覧が5秒以内に更新されること、24時間のグラフが表示され、期間を切り替えられることを確かめる。その間の server と PostgreSQL のCPU・メモリ（`docker stats`）、テーブルの行数、代表的な問い合わせの `EXPLAIN ANALYZE` の実行時間を記録する
9. 保持期間の試験。保持期間を短く設定した環境で、期間を過ぎたデータが自動で消えることを、行数の推移で示す。DBのサイズの確かめ方を PostgreSQL のマニュアルで調べ、runbook の「動作確認」に足す
10. 試験結果を `capstone/docs/tests/` にレポートとしてまとめる。試験ごとに、日付、環境、手順、期待する結果、実際の結果、合否を書く。予想と違った点は、原因を調べる。直すか、「既知の制限」として runbook に書くかを決める。コードを直したら、その試験をやり直す
11. runbook の検証。日を改めて、自分の記憶に頼らず、runbook の文字だけを追って、再構築と「よくある障害」の対応を1つ行う。迷った箇所、書いていない前提に、印を付けて直す
12. 振り返りと区分けを `capstone/docs/retrospective.md` に書く
    - 見積もり（C1 で書いた回数）と実績の差、その理由
    - いちばん詰まった点を3つと、どうやって抜け出したか
    - C1 のADRのうち、今なら違う決定をするもの
    - 「AIなしで書いた部分」と「AIを使った部分」の区分け。`git log --grep` で `[no-ai]`・`[ai]`・`[mixed]` のコミットを数え、ディレクトリやファイルの単位で一覧にする。AIを使った箇所のそれぞれに、なぜそこはAIに任せてよいと判断したかを書く

### 発展（任意）

- 障害試験に「ディスクがいっぱいになる」「時計が大きくずれる」を足し、予想と結果を記録する
- 課題5〜7のうち1つを選び、ポストモーテムの形式（何が起きたか、時系列、影響、原因、学んだこと）で書く
- runbook の「動作確認」を、1本のシェルスクリプトにする（`shellcheck` の指摘ゼロ）

## 詰まりやすいところ

- ネットワークを切ると、ビルドのどこかが止まる → どの段階が、どのホストに出ようとしているかを、エラーメッセージと O3 の道具（`ss`、`strace`）で特定する。O7 のチェックリストのどの項目にあたるかを確かめる
- 再構築のたびに、手順が少しずつ違ってしまう → 打ったコマンドを、その場で `notes.md` に写す。`history` に頼らない。runbook にないコマンドを打ったら、その時点で印を付ける
- DBを再開しても、server が戻らない → server が、DBへの接続をどう持っているか（`pgxpool` のドキュメント）、エラーのあとに接続を取り直しているかを、ログから追う
- server を再開しても、agent の送信がなかなか戻らない → 再試行の間隔が、そのときどこまで伸びていたかをログで確かめ、C1 のADRの「間隔の上限」と照らす。それは不具合か、決めたとおりの動きか
- 予想を書かずに試験を始めてしまい、結果が「合格」にしか見えない → 試験をやめ、先に `plan.md` の「期待する結果」を埋める
- runbook が、自分にしか分からない言葉で書かれている → 課題11を、日を空けて行う。平日にAIへ「この runbook だけで構築できるか。足りない前提はどこか」を尋ねるのもよい
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。試験で見つかった不具合の修正も、それにあたる。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正（runbook とレポートの校正を含む）。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- ネットワークを切ったまっさらな環境で、runbook の手順だけで、ビルドから起動までが完了する。「runbook にないコマンド」が0個の回の記録がある
- 障害試験1〜3のレポートがあり、どれも、原因を取り除いたあと、手を触れずに正常に戻っている。復帰までの秒数が書いてある
- server の停止と再開のあと、agent が自動で送信を再開している（止まっていた間のデータは、なくてよい）
- 10台・10秒間隔で30分動かし、一覧の更新が5秒以内、24時間のグラフと期間の切り替えが動く
- `plan.md` のすべての必須の要件に、合否が入っている。不合格が残っていない
- [評価基準](../../../docs/06-evaluation.md)の Stage 5 チェックリストを確かめる。「設計と技術選定を30分でAIに説明する」は平日に行い、やり取りを `capstone/docs/` に残す
- `retrospective.md` に、AIなしで書いた部分と、AIを使った部分の区分けと、判断理由がある
