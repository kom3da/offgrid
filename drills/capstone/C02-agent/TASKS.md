## ねらい

各サーバーで動き、CPU・メモリ・ディスクの使用率を10秒ごとに集めて送る agent を、Goの標準ライブラリだけで書く。閉域の現場では、既製の監視エージェントを入れられないことがある。OSが公開している数字を自分で読み、意味のある値に直す力が要る。

## このステップで身につけること

- `/proc/stat` と `/proc/meminfo` を読み、必要な数字を取り出す
- 「起動してからの累計」の数字2回ぶんから、その間の使用率を求める
- `/proc` にない情報（ディスクの使用率）を、OSの仕組み（`statfs`）をGoから呼んで得る
- 読み取り元を差し替えられる作りにし、`testdata/` の偽のファイルでテストする
- 10秒ごとの収集と送信を、`context` で止められるループにする
- 送信の失敗時に、間隔を空けて再試行し、相手の復旧後に自動で再開する
- 設定（送信先、トークン、ホスト名、間隔）を環境変数から受け取る

## キーワード

- **`/proc`**：カーネルが、プロセスやシステムの状態をファイルの形で見せている場所（O1）
- **jiffies**：`/proc/stat` のCPU時間の単位。起動してからの累計で増えていく
- **`statfs`**：ファイルシステムの容量と空きを返す、OSの機能（システムコール）。`df` が内部で使っている
- **システムコール**：プログラムがカーネルに仕事を頼む窓口（O3 で `strace` を使って見た）
- **指数バックオフ**：失敗するたびに、再試行までの間隔を倍々に空ける方法（G19）
- **ticker**：一定の間隔で合図を出す仕組み。`go doc time.Ticker`
- **静的バイナリ**：ほかのライブラリなしで、単体で動く実行ファイル（O4）

## 準備

実装は、リポジトリの `capstone/` に置く（この `TASKS.md` の隣ではない）。このディレクトリには、作業メモだけを置く。

```sh
cd ~/offgrid-log/capstone
go mod init offgrid/capstone
mkdir -p cmd/agent internal
touch ../drills/capstone/C02-agent/notes.md
```

確認は、`capstone/` で `go vet ./... && go test -race -cover ./...`。Web検索は0回。標準ライブラリは、`go doc` とローカルの `pkgsite` で引く。

## 課題

1. `cat /proc/stat` の1行目を、10秒あけて2回とり、`notes.md` に貼る。各列の意味を `man` で調べて書く。どの列が増え、どの列がほとんど増えないか。その間に `top` が示していたCPU使用率は、どのくらいだったか
2. 課題1の2回ぶんの数字から、その10秒間のCPU使用率を、紙と電卓で求める。求め方は自分で考える（手がかりは、どの数字も「起動してからの累計」であること）。`top` や `vmstat` の値と大きくずれていないかで確かめる。1回ぶんの数字だけでは求められないのは、なぜか
3. `/proc/meminfo` と `free` の出力を見比べ、`free` の各列が `/proc/meminfo` のどの項目から来ているかを `man free` で調べる。watchdeck の「メモリ使用率」を、どの項目から求めるかを決め、理由を `notes.md` に書く
4. `/proc/stat` の中身を解析するパッケージを `internal/` の下に書く。ファイルのパスではなく、`io.Reader` を受け取る形にする（G8）。`testdata/` に、自分のマシンからとった本物の内容と、壊れた内容（行がない、列が足りない、数字でない）を置き、テーブル駆動テストを書く。壊れた入力では、panic せずにエラーを返す
5. 2回ぶんの読み取り結果からCPU使用率を求める関数を書き、テストする。課題2で手計算した値を、期待値に使う。2回の数字がまったく同じ場合と、2回目のほうが小さい場合（再起動をまたいだ場合）に、どう振る舞うかを決めてテストに入れる
6. `/proc/meminfo` の解析とメモリ使用率を、課題4・5と同じ形で書く。単位（kB）の扱いを確かめる
7. ディスク：`strace` で、`df /` がどのシステムコールで容量を得ているかを探す。次に、Goの標準ライブラリの中から、その仕組みを呼べる関数と、結果が入る構造体を探す（`go doc` で、OSの機能を直接呼ぶためのパッケージを調べる）。構造体のどの項目から使用率を求めるかを `man 2 statfs` で調べ、`df` の「Use%」と比べる。一般ユーザーが使える空きと、root だけが使える空きの違いは、どの項目に表れるか
8. 収集のループを書く。10秒ごとに3つの値を集め、まずは標準出力にJSONで1行ずつ出す。`signal.NotifyContext` で、Ctrl+C を受けたらすぐに止まる（G16）。起動直後の1回目は、CPU使用率をどう扱うか
9. **本題**：送信を実装する。C1 の `api.md` の形式で、トークンを付けて server に送る。`http.Client` にタイムアウトを付け、`resp.Body` を必ず閉じる。失敗したら、C1 のADRで決めた方針（間隔の上限、あきらめる条件）で再試行する。送信が詰まっている間、次の10秒ぶんの収集がどうなるかを決め、`notes.md` に書く
10. 送信のテストを `httptest` で書く。次の3つを含める
    - 正常に送れたとき、サーバー側に届いた本文とヘッダが、`api.md` のとおりである
    - サーバーが何回か500を返したあとに成功を返すと、再試行して成功する。待ち時間は、テストが数秒で終わるように差し替えられる作りにする
    - `context` がキャンセルされたら、再試行の待ちの途中でも、すぐに戻る
11. 設定を環境変数から読む（送信先のURL、トークン、ホスト名、間隔）。ホスト名は、指定がなければOSから取り、指定があればそれを使う（C7 で、1台のマシンから10台ぶんを送るのに使う）。必須の項目が欠けていたら、項目名を含むエラーで起動を止める（G6）。ログ（`log/slog`）に、トークンの値が出ないことを確かめる
12. 受け側がまだないので、G12〜G14 で作ったAPIか、届いた本文を表示するだけの小さなサーバーを相手に、agent を5分動かす。途中で相手を30秒止めて、再開する。再開後に送信が自動で戻ること、止めている間にagentのメモリやgoroutineが増え続けないことを、ログと `top` で確かめる

### 発展（任意）

- CPU使用率を、user・system・iowait の内訳でも送る
- ディスクの対象を、設定で複数のマウントポイントにできるようにする
- `go test -bench` で、`/proc/stat` の解析1回にかかる時間を測る

## 詰まりやすいところ

- CPU使用率が、いつも0%か100%に近い、または負の値になる → 引き算の向きと、整数どうしの割り算になっていないかを疑う。課題2の手計算と、途中の値を1つずつ比べる
- メモリ使用率が、`free` や `top` の印象より、ずっと高い → 「空き」をどの項目で数えているかを、`man free` の available の説明で確かめる
- ディスクの使用率が、`df` と数%ずれる → `df` が分母と分子に何を使っているかを `man 2 statfs` の項目の説明から考える。ブロック数とバイト数を混ぜていないかも見る
- 再試行のテストが、何十秒もかかる → 「待つ」部分を、テストから短くできる作りになっているかを見直す（G19 の自分のコード）
- Ctrl+C を押しても、すぐに止まらない → 待っている場所（`time.Sleep` など）が、`context` のキャンセルに気づける書き方かを確かめる。`go doc time.After`、`go doc context`
- サーバーを止めている間に、agent のメモリがじわじわ増える → 送れなかったデータやgoroutineが、どこかに溜まっていないかを疑う。必須版では、止まっていた間のデータは失ってよい
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。このステップのコードは、ほぼすべてがそれにあたる。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- `capstone/` で `go vet ./... && go test -race -cover ./...` が通る。`/proc` の解析と使用率の計算のパッケージは、カバレッジ80%以上
- テストが、実行するマシンの本物の `/proc` に頼らず、`testdata/` だけで通る（`/proc` のないOSの上でも通る作りか、を自問する）
- agent を動かしたまま、`top`、`free`、`df` の値と、agent が送った値を3回見比べ、CPUとメモリは数ポイント以内、ディスクは1ポイント以内で合う。結果を `notes.md` に残す
- 課題12の「止めて再開」で、再開後に手を触れずに送信が戻る。そのときのログを `notes.md` に貼る（ホスト名は、ダミーの名前に置き換える）
- この時点では、`go list -m all` の結果に、自分のモジュール以外が出ない（agent は標準ライブラリだけで書く）

## 残すもの

- `capstone/cmd/agent/`、`capstone/internal/` の下のパッケージとテスト、`testdata/`（ホスト名などが入っていたら、ダミーに置き換える）
- このディレクトリの `notes.md`：課題1〜3と7の調査、課題9で決めたこと、値の見比べの結果、詰まったこと
- `.env` はコミットしない。項目を足したら、`capstone/.env.example` にダミー値で足す
