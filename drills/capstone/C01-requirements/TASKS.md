## ねらい

コードを書く前に、watchdeck の「何を作るか」と「なぜその方式にしたか」を文章で決め切る。閉域の現場では、後から設計を相談できる相手もAIもいないことが多い。迷った点と決めた理由を紙に残しておくことが、C2〜C7 の実装を止めないための、いちばんの備えになる。

## このユニットで身につけること

- トラックのページの要件を、「確かめ方」が付いた要件定義書に書き直す
- 設計上の決定を、ADR（決定の記録）として1件ずつ残す
- 1つの決定について、案を2つ以上並べ、捨てた案と理由を書く
- 時系列データを入れるテーブルを、型・キー・制約・インデックスまで設計する
- データ量を見積もり、保持期間と削除の方式を決める
- agent・server・web の間でやり取りするデータの形を決める

## キーワード

- **要件定義書**：作るものが満たすべきことを、確かめられる形で並べた文書
- **機能要件・非機能要件**：「何ができるか」と、「どのくらい速く・安全に・壊れにくく動くか」
- **ADR（Architecture Decision Record）**：設計上の決定を1件1ファイルで残す記録。状況、検討した案、決定、その結果（良い点と困る点）を書く
- **トレードオフ**：ある案の利点を取ると、別の利点を失う関係
- **時系列データ**：時刻と値の組が、増え続けるデータ
- **保持期間**：データを残しておく長さ。過ぎたものは消す
- **死活判定**：サーバーが生きているかどうかを決める規則。watchdeck では「最後の受信から30秒以上たったか」
- **受け入れ条件**：その要件を満たしたと言える、実行できる確認手順

## 課題

1. [トラックのページ](../../../docs/15-track-c-capstone.md)の必須の機能要件と非機能要件を、1つずつ `capstone/docs/requirements.md` に写し、それぞれに受け入れ条件（何を実行し、何が見えたら合格か）を自分の言葉で付ける。発展の要件は「今回はやらない」節にまとめる
2. 登場するもの（agent、server、PostgreSQL、web）の間を流れるデータを、図か箇条書きで書く。それぞれの矢印について、「誰が・いつ・何を・どの形式で」送るかを埋める。埋められない矢印が、これから決めるべきことになる
3. ADR の書式を決め、`capstone/docs/adr/0000-template.md` に置く。キーワードに挙げた4項目（状況、検討した案、決定、結果）を含める。番号の付け方と、後から決定を変えたときの扱い（古いADRをどうするか）も決める
4. **本題**：次の決定を、1件ずつADRに書く。どれも、案を2つ以上挙げ、選ばなかった案の理由を書く
   - 時系列メトリクスのデータモデル（1行に何を入れるか。指標ごとに行を分けるか、列を分けるか）
   - 保持期間と、古いデータの削除のしかた（D15 で試した方法のどれを使うか）
   - 死活判定（30秒の判定を、どこで、どの時刻を基準に行うか。agent と server の時計がずれていたらどうなるか）
   - SSE の認証（`EventSource` はヘッダを付けられない。T11 で挙げた2案を、トークンが漏れる経路の観点で比べ直す）
   - agent の送信間隔と再試行の方針（間隔の上限、あきらめる条件、止まっていた間のデータの扱い）
   - トークンの扱い（`.env` で渡す。誰がどのトークンを持つか、ログやURLに出ないか、作り直すときの手順）
5. テーブルを設計する。`capstone/docs/schema.md` に、テーブルごとの列、型、主キー、外部キー、`CHECK` 制約、NULL を許すかを書く。「登録したサーバー」を表すテーブルと、計測値のテーブルの関係を、D7 の正規形の観点で説明する。ここではSQLを実行しない（マイグレーションを書くのは C3）
6. データ量を見積もる。10台・10秒間隔で、1日に何行、保持期間の全体で何行になるか。100台ならどうか。D15 の1000万行での計測結果と比べて、パーティションが要るか・要らないかを判断し、ADRに書く
7. 画面が出す問い合わせ（一覧、直近1時間のグラフ）を文章で書き出し、それぞれがどの列で絞り込み、どの順で並べるかを調べる。そこから必要なインデックスを決め、理由を `schema.md` に書く。直近1時間ぶんの点をそのまま返すか、まとめて返すかも、ここで決める（24時間のグラフと期間の切り替えは発展。C8 で選んだときに決め直す）
8. agent から server への送信と、server から web への REST・SSE について、パス、メソッド、データの項目、エラー時の応答を `capstone/docs/api.md` に書く。時刻の形式とタイムゾーン、使用率の単位（0〜1 か 0〜100 か）を明記する
9. 設定項目の一覧を作る。agent と server が `.env` から受け取る項目の名前と意味を並べ、`capstone/.env.example` にはダミー値だけを書く。`git check-ignore -v capstone/.env` で、`.env` がGitの管理外であることを確かめる
10. C2〜C7 の各ステップで「終わったと言える状態」を、1〜2行ずつ `requirements.md` の末尾に書く。必須版の全体で28〜33回が目安なので、各ステップの回数の見積もりも添える

## 詰まりやすいところ

- ADRが「決定」だけで、1〜2行で終わってしまう → 捨てた案が書かれているか、その決定で「後で困ること」が書かれているかを見直す
- テーブル設計が決まらない → 課題7の「画面が出す問い合わせ」を先に書く。D15 の自分の表と計測結果を見直す
- SSE の認証で、どの案も不安が残る → 「トークンがどこに記録されうるか」（サーバーのログ、ブラウザの履歴、プロキシ）を案ごとに書き出して比べる
- 死活判定の30秒が、実装の場面を想像すると曖昧になる → 「誰の時計で測るか」「一覧を5秒以内に更新する要件と、どう両立するか」を図に書く
- 書いているうちに、発展の機能まで設計したくなる → 必須版に要るかどうかだけで判断する。発展は「やらないこと」の節に1行で残す
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）と、その設計。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- **C2〜C7 の課題を1つずつ開き、その課題を始めるのに必要な決定が、すべて `requirements.md`・`schema.md`・`api.md`・ADR のどこかに書いてあることを確かめる。** 見つからないものを一覧にし、決めて書き足す（ここが主な合格の条件。自分だけで確かめられる）
- 課題4の6件すべてに、案が2つ以上と、選ばなかった理由がある
- `requirements.md` の必須の要件すべてに、実行できる受け入れ条件が付いている
- `grep -rnE '([0-9]{1,3}\.){3}[0-9]{1,3}' capstone/` の結果に、例示用の範囲（`192.0.2.0/24` など）以外のIPアドレスがない。実在のホスト名やトークンもない

補助として、間の日にAIへ `capstone/docs/` 一式のレビューを頼んでよい（[レビューのプロンプト](../../../prompts/weekly-review.md)に「C2〜C7 を実装するうえで、まだ決まっていない決定を挙げてください。代わりの案は書かないでください」と添える）。指摘は次のセッションで自分で直す。ただし**AIの指摘が0件になることを合格の条件にはしない**（何周するか読めないため）。
