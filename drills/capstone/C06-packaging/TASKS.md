## ねらい

手元で `go run` と `npm run dev` で動いているものを、他のマシンに持っていける形にする。中央側（server、PostgreSQL、web）は `docker compose up` の一発で、agent は単体の静的バイナリと systemd で動かす。閉域の現場に持ち込めるのは、ファイルだけ。イメージとバイナリと設定例が揃っていて、手順が短いことが、そのまま品質になる。

## このステップで身につけること

- server を、マルチステージビルドで小さなイメージにする。ビルドは `-mod=vendor` で、ネットワークなしで通す
- web のビルド結果を、中央側のどこから配信するかを決めて組み込む
- server・PostgreSQL・（使うなら）リバースプロキシを、compose でまとめて起動する
- 空のDBへのマイグレーションの適用を、起動の手順に組み込む
- 設定と秘密の値を、`.env` からコンテナとサービスに渡す。イメージやリポジトリには入れない
- agent を静的バイナリにし、専用ユーザーの systemd サービスとして常駐させる
- イメージを `docker save` で持ち出せるファイルにする

## キーワード

- **マルチステージビルド**：ビルド用のイメージと、実行用の小さなイメージを分ける Dockerfile の書き方（O4）
- **静的バイナリ**：ほかの共有ライブラリなしで動く実行ファイル。`CGO_ENABLED=0` で作る（O4）
- **distroless**：シェルもパッケージ管理もない、実行に要るものだけのイメージ（O4）
- **ヘルスチェック**：コンテナが「使える状態」かを、定期的に確かめる仕組み。起動の順番を待つのに使う
- **ボリューム**：コンテナを消しても残る、データの置き場所（F10）
- **ユニットファイル**：systemd に、サービスの起動のしかたを教える設定ファイル（O2）
- **リバースプロキシ**：ブラウザとアプリの間に立ち、リクエストを中継するサーバー（O5）
- **`.dockerignore`**：イメージのビルドに送らないファイルの一覧

## 平日に読むもの

- `man systemd.service`、`man systemd.exec`、`man systemd.unit`、`man journalctl`
- 『［試して理解］Linuxのしくみ』第11章（コンテナ）、第12章（cgroup）
- 自分の O2、O4、O5、O7 のファイルとメモ
- 平日のうちに、ビルドと実行に使うベースイメージ（Go、Node.js、PostgreSQL、distroless、使うならリバースプロキシ）を `docker pull` し、`docker save` しておく

```sh
cd ~/offgrid-log/capstone
mkdir -p deploy
touch ../drills/capstone/C06-packaging/notes.md
```

agent を systemd で試す場所は、O2 で使った自分のUbuntu（または検証用の仮想マシン）。設定例に書く接続先は `server.example.test` のようなダミーにし、トークンは `changeme` のような値にする。本物は `.env`（Gitの管理外）にだけ書く。Web検索は0回。

## 課題

1. 配布物の一覧を `capstone/docs/` に書く。中央側と agent 側のそれぞれについて、「何のファイルを持ち込み、どこに置き、どの設定を書き、どのコマンドで起動するか」を箇条書きにする。まだ存在しないファイルが、このステップで作るもの
2. web の配信のしかたを決める。server（Go）が `dist/` を配るか、リバースプロキシが配るか。それぞれの場合に、同一オリジンになるか、SSE とトークン認証がそのまま動くか、イメージがいくつになるかを比べ、ADRに書く
3. server の Dockerfile を書く（O4）。ビルドは `-mod=vendor` で行い、ビルドの途中でネットワークに出ないこと。実行用のイメージは、root 以外のユーザーで動かす。`docker images` でサイズを確かめる。`.dockerignore` を書き、`.env`、`.git`、`node_modules` がビルドに送られないことを確かめる
4. web のビルドを、イメージのビルドに組み込む（課題2の決定に従う）。`npm ci` が、オフラインキャッシュだけで通るようにする方法を、O7 のメモから組み立てる
5. compose ファイルを書く（O5）。PostgreSQL のデータはボリュームに置く。パスワードとトークンは `.env` から渡し、compose ファイルには値を書かない。`docker compose config` で、値がどう展開されるかを見る。展開後の出力を、そのまま人に見せてよいか
6. 起動の順番を扱う。PostgreSQL が接続を受け付ける前に server が起動すると、どうなるか。compose のヘルスチェックで待つ方法と、server 側で接続を再試行する方法の、どちらを使うか（両方か）を決める。`docker compose down -v` のあと `docker compose up -d` を5回くり返し、毎回、手を触れずに全体が立ち上がることを確かめる
7. マイグレーションを、起動の手順に組み込む。server の起動時に適用するか、専用のコンテナやコマンドで適用するかを決め、ADRに書く。空のボリュームからの起動と、データが入ったボリュームでの再起動の、両方で問題がないこと
8. **本題**：中央側を `docker compose up -d` の一発で起動し、ブラウザで一覧とグラフが表示されることを確かめる。リバースプロキシを挟んだ場合は、SSE が10秒ごとに遅れなく届くこと、`docker compose stop` で server が安全な停止（C4）をしていることを、ログで確かめる
9. agent を静的バイナリにする。`file` と `ldd` の出力で、静的リンクであることを確かめる。サイズを記録する。別のマシン（または、素の `ubuntu` コンテナ）にバイナリ1つだけをコピーして、動くことを確かめる
10. agent の systemd ユニットを書く（O2）。専用のユーザーで動かし、設定はファイルから環境変数として渡す（`man systemd.exec` で、その指定を探す）。設定ファイルのパーミッションを、誰が読める必要があるかから決める。異常終了したら自動で再起動し、OSの再起動後も自動で起動すること。`systemctl status` と `journalctl -u` で確かめる
11. agent の導入と削除を、短いシェルスクリプトにする（F5）。`set -euo pipefail` を付け、`shellcheck` の指摘をゼロにする。2回続けて実行しても壊れないこと
12. 持ち出せる形にまとめる。中央側のイメージを `docker save` でファイルにし、`sha256sum` の一覧を付ける。イメージをすべて消してから `docker load` し、`docker compose up -d` で起動することを確かめる（ネットワークを切った完全な再構築は、C7 で行う）

### 発展（任意）

- server のイメージを、`docker history` で層ごとに調べ、さらに小さくできる箇所を探す
- systemd のユニットに、サービスができることを絞る設定（`man systemd.exec` のサンドボックスの節）を足し、agent が動き続けることを確かめる
- compose のログが、ディスクを埋めないようにする設定を調べる

## 詰まりやすいところ

- イメージのビルドが、`go mod download` や `npm` の通信で止まる → ビルドの中で、`vendor/` とオフラインキャッシュが見えているか。`.dockerignore` で、要るものまで外していないか
- 実行用のイメージで、「ファイルがない」と言われて起動しない → バイナリが静的かどうかを、課題9の方法で確かめる。distroless にはシェルがないので、中に入って調べる代わりに、何が使えるかを考える
- server が、起動直後にDB接続のエラーで落ちる。何回かに1回だけ起きる → コンテナが「起動した」ことと、PostgreSQL が「接続を受けられる」ことの違いを、compose のドキュメントで確かめる
- リバースプロキシを通すと、SSE がまとめて遅れて届く。または、1分ほどで切れる → プロキシの、応答をためる設定と、タイムアウトの設定を疑う。server に直接つないだ場合と、`curl -N` で比べる
- systemd で動かすと、設定が読めない、または `/proc` やディスクの値が取れない → サービスが、どのユーザー・どの環境変数・どの作業ディレクトリで動いているかを、`systemctl show` と `journalctl` で確かめる
- `docker compose config` や `docker inspect` の出力を `notes.md` に貼ったら、トークンが入っていた → 貼る前に値を伏せる。コミットしてしまったら、トークンを作り直す（C1 のADRの手順）
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。このステップの Dockerfile、compose、ユニットファイルも、O2・O4・O5 の再現として自分で書く。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- `docker compose down -v` のあと、`docker compose up -d` だけで中央側が起動し、ブラウザで一覧とグラフが見える。5回くり返して、5回とも成功する
- server のイメージが30MB以下（O4 の基準）。`docker images` の出力を `notes.md` に残す
- agent のバイナリが静的リンクで、バイナリ1つと設定ファイル1つだけで、別の環境で動く
- agent が systemd で常駐し、`sudo systemctl kill --signal=SIGKILL サービス名` で強制終了させても自動で戻り、OSを再起動しても自動で起動する。`journalctl -u` のログを残す（ホスト名はダミーに置き換える）
- `git ls-files | grep -F .env` に出るのが `.env.example` だけ。設定例の値は、すべてダミー。リポジトリのどこにも、本物のトークン、パスワード、ホスト名、IPアドレスがない
- 導入スクリプトが `shellcheck` の指摘ゼロで、2回続けて実行できる

## 残すもの

- `capstone/deploy/`：Dockerfile、compose ファイル、agent のユニットファイル、agent の設定例（ダミー値）、導入スクリプト
- `capstone/.env.example`：項目を足したら、ダミー値で更新する
- `capstone/docs/`：配布物の一覧、課題2・6・7のADR
- このディレクトリの `notes.md`：イメージとバイナリのサイズ、起動のくり返しの結果、詰まったこと
- `docker save` したファイルは、コミットしない

この `TASKS.md` はカリキュラムの一部なので、書き換えない。
