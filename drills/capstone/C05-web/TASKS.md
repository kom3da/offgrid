## ねらい

server の REST と SSE を受け、死活とリソースの一覧、24時間のグラフ、リアルタイム更新を持つダッシュボードを、TypeScript と React で作る。閉域では、CDN のグラフライブラリもフォントも読めない。描画を自分で書くか、同梱できるものだけで組み、`npm ci --offline` で再現できる形を保つ。

## このユニットで身につけること

- Vite・ESLint・Vitest・Testing Library の環境を、テンプレートなしで組む（T7）
- APIの応答と SSE のイベントを、`unknown` から型ガードで検証して受け取る（T8）
- 「読み込み中・成功・失敗」の状態を、判別可能ユニオンで表す（T6）
- 一覧を、SSE で届いた値で5秒以内に更新する。切断時は、自動で再接続する（T11）
- 時系列の値を、SVG か Canvas の座標に変換して、折れ線グラフを描く
- グラフの期間を切り替え、切り替えのたびにデータを取り直す
- 主要なコンポーネントと変換の関数に、テストを書く

## キーワード

- **`EventSource`**：ブラウザで SSE を受ける仕組み。切断時の再接続を、ある程度は自動で行う（T11）
- **クリーンアップ**：`useEffect` が返す後片付けの関数。接続やタイマーを閉じる（T9）
- **型ガード**：`unknown` の値が、期待する型かどうかを実行時に確かめる関数（T8）
- **判別可能ユニオン**：`kind` のような目印の項目で、場合分けできる型（T6）
- **スケール**：データの値（時刻、使用率）を、画面の座標（ピクセル）に変換する関数
- **SVG と Canvas**：ブラウザで図を描く2つの方法。要素として描くか、ピクセルに描くか
- **Testing Library**：コンポーネントを、利用者から見える文字や役割を手がかりにテストする道具
- **Viteのproxy**：開発中に、APIへのリクエストを server に中継する設定（T7）

## 準備

実装は、リポジトリの `capstone/web/` に置く（この `TASKS.md` の隣ではない）。このディレクトリには、作業メモだけを置く。

```sh
cd ~/offgrid-log/capstone
mkdir -p web && cd web
npm init -y
touch ../../drills/capstone/C05-web/notes.md
```

使う npm パッケージは、TypeScript、Vite、ESLint、Vitest、React、Testing Library（と、その動作に要る型定義やテスト用のDOM環境）。グラフのライブラリを使う場合は、1つに絞って npm で入れて同梱し、CDN からは読まない。インストールは、平日のネットワークがある日に済ませ、`package-lock.json` をコミットする。確認は `npx tsc --noEmit --strict` と `npx vitest run`。

確かめるときは、C4 の server、ダミーデータ入りのDB、動いている agent を用意する。

## 課題

1. T7 のやり方で、`capstone/web/` に環境を手で組む。空の画面が `npm run dev` で開き、`npx tsc --noEmit --strict`、`npx eslint .`、`npx vitest run`（ダミーのテスト1本）が通る。開発中のAPI呼び出しを server に通す方法（Viteのproxy か、G14 のCORS）を決める。node_modules を消して `npm ci --offline` で戻せるか
2. C1 の `api.md` を見ながら、APIの応答と SSE のイベントの型を書く。それぞれに、`unknown` を受け取る型ガードを書き、Vitest でテストする。項目が足りない、型が違う、使用率が範囲の外、時刻として読めない、の入力を拒否すること
3. トークンの扱いを決める。ブラウザ側で、トークンをどこから受け取り、どこに持つか（ソースコードやビルド結果に埋め込まない）。REST の呼び出しにトークンを付ける関数を1つ書き、401 のときに画面でどう見せるかを決める
4. 一覧の画面を作る。まず REST だけで、サーバーごとの死活、CPU・メモリ・ディスクの使用率、最後の受信時刻を表示する。読み込み中、失敗（再試行のボタン付き）、0台、の表示を持つ。状態は判別可能ユニオンで表し、`switch` の網羅をコンパイラに検出させる（T6）
5. SSE を受けるフックかモジュールを書く。C1 のADRで決めた認証の手順で接続し、届いたイベントを型ガードに通してから渡す。コンポーネントが画面から消えたら接続を閉じる。開発者ツールのNetworkタブで、接続が1本だけであること、画面を行き来しても増えていかないことを確かめる
6. **本題（その1）**：一覧を SSE で更新する。agent が送った値が、5秒以内に一覧に反映される。agent を止めると、止めてから35秒以内に、そのサーバーが「停止」の表示に変わる。server を止めると、画面に「切断中」であることが分かり、server を再開すると、手を触れずに表示が再開する。3つとも、秒数を測って `notes.md` に残す
7. グラフのための計算を、React から切り離した関数として書く。入力は時刻と値の配列と、描く領域の幅・高さ。出力は座標の並び。Vitest でテストする：値が0と100のとき、点が1つだけのとき、空のとき、途中が抜けている（agent が止まっていた）とき。抜けている区間を、線でつなぐか・切るかを決める
8. **本題（その2）**：グラフのコンポーネントを作る。1台のサーバーの直近1時間のCPU・メモリ・ディスクを、SVG（T1）で折れ線にする。座標は課題7の関数で作る。縦軸と横軸の目盛り、時刻のラベルを付ける。時刻は、どのタイムゾーンで表示するかを決める。点が1つのとき、無いときの表示も決める
9. コンポーネントのテストを、Vitest と Testing Library で書く。少なくとも次を含める
    - 一覧：取得成功で、サーバー名と使用率と死活が表示される。取得失敗で、エラーと再試行のボタンが表示される
    - 一覧：SSE のイベント（テスト用に差し替えたもの）が届くと、表示の値が変わる
    - グラフ：データが届くと折れ線が描かれ、空のときはその旨が表示される
    - 不正な応答が来ても、画面が真っ白にならず、エラーの表示になる
10. 本番用にビルドする（`npm run build`）。出力された `dist/` の中を `grep -rnoE 'https?://[^"]+' dist/` で調べる。見つかったURLを1つずつ、「実行時に読みに行くもの（スクリプト、スタイル、フォント、画像）」か「ただの文字列（XMLの名前空間、エラーメッセージの中の案内）」かに分けて `notes.md` に書く。次に、ビルド結果を server 経由（または `npx vite preview`）で開き、開発者ツールのNetworkタブに、自分の server 以外へのリクエストが1本もないことを確かめ、課題6をもう一度行う

### 発展（任意）

- 過去24時間のグラフと、期間の切り替え（1時間・6時間・24時間）。切り替えのたびにデータを取り直し、素早く続けて切り替えたとき古い応答が新しい表示を上書きしないようにする
- 表示中のグラフに、SSE で届いた新しい点を足す。期間の外に出た点を捨て、1時間開きっぱなしでもメモリが増え続けないことを Memory タブで確かめる
- グラフの上にマウスを置くと、その時刻の値を表示する
- 一覧を、使用率の高い順・名前順で並べ替えられるようにする
- キーボードだけで、一覧からグラフへ移動し、期間を切り替えられるようにする

## 詰まりやすいところ

- 画面を行き来するたびに、SSE の接続が増えていく。開発中だけ、接続が2本になる → `useEffect` のクリーンアップで閉じているか。React の開発モードが、`useEffect` をどう実行するかを、公式ドキュメントで確かめる（T9、T11）
- Vitest で、`EventSource` や `fetch` が「定義されていない」と言われる → テスト用のDOM環境に、ブラウザのどの機能があり、どれがないかを疑う。Vitest のドキュメントで、グローバルなものを差し替える方法を調べる
- server を再開しても、表示が戻らない → `EventSource` が、どんな切れ方のときに自動で再接続し、どんなときにあきらめるかを、MDN と開発者ツールのNetworkタブで確かめる。認証の失敗（401）のときは、どうなっているか
- グラフが上下逆になる。または、右端に固まる → 画面の座標は、どの向きに増えるか。時刻をどの単位の数にして計算しているかを、課題7のテストで確かめる
- 時刻のラベルが、9時間ずれる → APIが返す時刻の形式と、`Date` がそれをどう解釈するかを、Consoleで1つ試す
- 環境によって画面の文字の見た目が変わる。または、アイコンが消える → 実行時に外部のURLを読みに行っていないかを、課題10の方法で調べる
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。web では、APIの呼び出し、型ガード、SSE の受信、状態の管理、グラフの座標計算がそれにあたる。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- `npx tsc --noEmit --strict`、`npx eslint .`、`npx vitest run` が、すべて通る。課題9のテストが揃っている
- 課題6の3つの測定が、要件の中に収まる（値の反映は5秒以内、停止の表示は35秒以内、server の再開後は手を触れずに再開）
- 1台のサーバーの直近1時間のグラフが表示され、軸のラベルが正しい時刻を指す
- agent 10台ぶん（C2 のホスト名の指定を使い、1台のマシンから送る）で、一覧とグラフが引っかかりなく動く
- 課題10で、Networkタブに自分の server 以外へのリクエストがない
- `rm -rf node_modules && npm ci` のあと、ビルドとテストが通る
