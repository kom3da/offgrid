## ねらい

保存したデータを、web が使える形で出す。一覧とグラフ用の REST、更新を流し続ける SSE、その両方を守るトークン認証を実装し、C1 で決めた「SSEの認証」を実際の形にする。長くつながり続ける接続を持つサーバーを、安全に止められるようにするところまでが、このステップの範囲。

## このユニットで身につけること

- 一覧用とグラフ用の REST エンドポイントを、C1 の `api.md` のとおりに実装する
- 死活（最後の受信から30秒以上たったか）を、決めた場所と時計で判定する
- 新しい計測値を、つながっている複数のブラウザに SSE で配る
- 切断したクライアントのgoroutineと登録を、確実に片付ける
- REST と SSE の両方にトークン認証をかける。SSE は、C1 のADRで決めた方式で通す
- SSE の接続が開いたままでも、Ctrl+C で server が決めた時間内に止まるようにする
- `httptest` で、認証、REST、SSE のテストを書く

## キーワード

- **SSE（Server-Sent Events）**：サーバーからブラウザへ、1本のHTTP接続でデータを流し続ける仕組み（G20）
- **`EventSource`**：ブラウザで SSE を受ける仕組み。リクエストに、自分でヘッダを足せない（T11）
- **ファンアウト**：1つの出来事を、複数の受け手に配ること
- **購読（subscribe）**：受け手が「更新を受け取りたい」と登録すること。切断時には、解除が要る
- **goroutine リーク**：役目を終えたgoroutineが、終わらずに残り続けること
- **グレースフルシャットダウン**：処理中のリクエストを終えてから、サーバーを止めること（G16）
- **ミドルウェア**：ハンドラの前後に、共通の処理（認証、ログ）を挟む関数（G14）
- **401 と 403**：「認証されていない」と「認証されたが、許可されていない」の違い

## 課題

1. 一覧の REST を実装する。登録したサーバーごとに、最新のCPU・メモリ・ディスクの使用率、最後に受信した時刻、死活を返す。死活は、C1 のADRで決めた場所と時計で判定する。1回も受信していないサーバーは、どう返すか。`curl` で確かめる
2. 死活判定を、時刻を引数で受け取る小さな関数に切り出し、テーブル駆動テストを書く。29秒前、30秒ちょうど、31秒前、受信なし、時刻が未来、の5ケースを入れる
3. グラフ用の REST を実装する。サーバーと期間を指定して、時系列の値を返す。期間の指定のしかた、既定値（直近1時間）、上限、不正な指定への応答は、`api.md` に従う。存在しないサーバーを指定したら、何を返すか。直近1時間ぶんの応答の大きさ（バイト数）と所要時間を `curl -w` で測り、`notes.md` に残す
4. トークン認証のミドルウェアを、G14 のものを元に入れる。トークンなし・間違ったトークン・正しいトークンの3つで、REST の応答を `curl -i` で確かめる。agent 用のトークンと web 用のトークンを分けるかどうかは、C1 のADRに従う。トークンの比較に `==` を使うことの弱点を、`go doc crypto/subtle` を読んで調べ、どうするかを決める
5. SSE の土台を作る。server の中に、「新しい計測値が保存された」ことを、購読している全員に配る仕組みを `internal/` の下に書く。購読、解除、配る、の3つの操作を持つ。複数のgoroutineから同時に呼ばれても安全にする（G15）。受け手の1人が遅いとき、ほかの受け手と受信のハンドラ（C3）を待たせないために、どうするかを決める
6. 課題5の仕組みに、テストを書く。購読者が0人・1人・3人の場合、解除した人には届かないこと、遅い購読者がいても配る側が止まらないこと。`go test -race` で警告が出ない
7. SSE のハンドラを書く。接続したら購読し、計測値が届くたびに、`api.md` で決めた形式のイベントを流す。クライアントが切断したら（`r.Context()`）、解除して戻る。`curl -N` で、agent の送信に合わせて10秒ごとに流れてくるのを確かめる
8. 死活の変化を、SSE でどう伝えるかを実装する。agent を止めたあと、計測値は届かなくなる。そのとき、誰が「30秒たった」ことに気づき、どうやってブラウザに伝えるか。要件は、一覧が5秒以内に更新されること。agent を止めてから、`curl -N` の出力に変化が現れるまでの秒数を測る
9. **本題**：SSE に、C1 のADRで決めた方式の認証をかける。`EventSource` はヘッダを付けられない、という制約の下で動くこと。認証なしの `curl -N` が 401 で断られること、決めた方式どおりの手順を `curl` でなぞると流れてくることを確かめる。server のアクセスログ（G14）に、トークンの値が残っていないかを `grep` で確かめる
10. goroutine が残らないことを確かめる。`curl -N` を5本つないで切る、を3回くり返し、その前後で goroutine の数が元に戻ることを観察する。観察の方法は、O3 で使った `pprof` か、`go doc runtime.NumGoroutine` を使った一時的なログ
11. 安全な停止を実装する。`signal.NotifyContext` で Ctrl+C を受けたら、新しい接続を断り、処理中の REST を終え、SSE の接続と削除のgoroutine（C3）を止め、DBの接続を閉じてから終了する。`curl -N` を2本つないだまま Ctrl+C を押し、終了までの秒数を測る。終了コードは何か（`echo $?`）
12. `httptest` で、ハンドラのテストを書く。REST の正常系と異常系、認証の3パターン、SSE で1件以上のイベントが決めた形式で届くこと、クライアント側の `context` をキャンセルするとハンドラが戻ること

### 発展（任意）

- SSE の再接続で、切れていた間のぶんを取りこぼさない方法を、MDN の `Last-Event-ID` の説明で調べ、必須版では対応しない理由と合わせてADRに書く
- 一覧の REST に対して、`curl` を100回くり返して所要時間の分布をとり、遅い回の原因を探す
- 同時につなげる SSE の数に、上限を設ける

## 詰まりやすいところ

- `curl -N` で、何も流れてこない。または、まとめて一気に出る → 書いたあとに、送り出す操作をしているか。ヘッダの `Content-Type` は何か。G20 の自分のコードと1行ずつ比べる
- Ctrl+C を押しても、server がいつまでも終わらない → そのとき開いている接続は何か。`go doc http.Server.Shutdown` の説明を最後まで読み、「待つもの」と「待たないもの」を確かめる
- `curl -N` を切ったあとも、goroutine の数が減らない → ハンドラの中で、切断に気づける場所で待っているか。解除が、どの戻り方でも必ず呼ばれるか（`defer`）
- `-race` で警告が出る。または、まれに `concurrent map` の panic になる → 購読者の一覧を、どのgoroutineが読み書きしているかを書き出す（G15）
- 遅い受け手が1人いると、全員の更新が止まる → channel のバッファの有無と、送る側が「待つ」書き方になっていないかを疑う。`select` の使い方を見直す
- SSE の認証を通したら、トークンがアクセスログに出ていた → ログに何を出しているか（パス、クエリ、ヘッダ）を確かめ、C1 のADRの「漏れる経路」の検討と照らす
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。配信、認証、停止の処理は、すべてそれにあたる。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする

## 完了条件の確かめ方

- `go vet ./... && go test -race -cover ./...` が通る。認証のミドルウェアと、配る仕組みに、単体テストがある
- `api.md` に書いた全エンドポイントを、`curl` で確かめられる。コマンド（トークンは変数のまま）と結果の先頭を `notes.md` に残す
- トークンなしでは、REST も SSE も 401 になる。SSE は、C1 のADRの方式で通る
- agent を動かした状態で、`curl -N` に10秒ごとにイベントが流れる。agent を止めると、止めてから35秒以内に、死活の変化が流れてくる
- 課題10で、接続と切断をくり返したあと、goroutine の数が元に戻る
- 課題11で、SSE を2本つないだまま Ctrl+C を押し、決めた時間内（目安は10秒以内）に終了する。処理中だった REST のリクエストは、最後まで応答が返る
