## ねらい

動くものを作っただけでは、運用は始まらない。壊れたときに、自分以外の人でも、手順書だけで戻せるか。このユニットでは、runbook だけから watchdeck を作り直し、わざと壊し、AIなしで直し、その手順を runbook に残す。卒業制作の採点にあたる回で、C1〜C6 で作ったものが「動かし続けられるもの」かどうかを、試験の結果で示す。

## このユニットで身につけること

- runbook だけで、まっさらな環境に再構築できる（文書の質を、自分以外の手で測る）
- 障害を計画的に起こし、検出 → 原因の特定 → 復旧を、時間を計って行える
- 復旧の手順を、次に同じことが起きたときに5分で読める形で残せる
- 10台分の負荷で、一覧とグラフが要件を満たすことを確かめられる
- 試験の結果から、設計の弱点を見つけて記録できる

## キーワード

- **runbook**：障害のときに開く手順書。「症状 → 確かめること → 直すこと」の順
- **障害試験**：わざと壊して、検出と復旧を確かめること
- **復旧までの時間**：壊れてから直るまで。ここでは自分で計る
- **フェイルセーフ**：壊れたときに、危険でない側に倒れること（データを消さない、嘘の表示をしない）
- **既知の問題**：直していないが分かっている問題の一覧。runbook に付ける

## 準備

server 側（compose）は、まっさらな環境に置く（新しい仮想マシンか、作り直した Ubuntu）。持ち込むのは、リポジトリ一式、`.env`、C6 の課題12で作った配布物（tar と `sha256sum` の一覧）だけ。リポジトリの中に、C6 で書き始めた `capstone/docs/runbook.md` があること。agent は C6 と同じく自分の Ubuntu で systemd で動かす（server とは別の時計になる）。課題7の10台も、その Ubuntu から C2 のホスト名の指定で10プロセス動かす（C5 の完了条件と同じやり方）。障害は自分で仕込むと答えを知ってしまうので、**種類は決めるが順番は `shuf`（`man shuf`）で決める**。

```sh
cd ~/offgrid-log/capstone
mkdir -p docs/tests
touch ../drills/capstone/C07-fault-drill/notes.md
```

## 課題

1. runbook（C6 で書き始めたもの）を、まっさらな環境で**そのとおりに打つ**。手順に無いコマンドを打った回数、詰まった箇所、かかった時間を `tests/rebuild-1.md` に書く。「runbook に無いコマンド」が0になるまで、runbook を直して繰り返す（回数も記録する）。runbook に「バックアップと復元（D11）」の節が無ければ足し、復元もそのとおりに打つ
2. 障害の一覧を作る（`tests/faults.md`）。少なくとも次を含める：PostgreSQL の停止、ディスクの満杯、server の停止、agent 1台の停止、agent の大量送信（10倍の頻度）、時刻のずれ、設定の誤り（`.env` の値）、トークンの不一致（server 側だけ作り直す）、ポートの衝突、ログの肥大。それぞれに「起こし方」「期待する検出」「期待する復旧」を書く
3. 検出の手段を決める。watchdeck 自身の死活表示、ログ、`ss`、`df`、`journalctl`。障害ごとに「何を見れば分かるか」を `faults.md` に足す
4. **本題（その1）**：障害試験を行う。`shuf` で順番を決め、1つずつ起こす。障害ごとに、検出までの時間、原因の特定までの時間、復旧までの時間を計り、打ったコマンドを全部 `tests/fault-<名前>.md` に書く。45分で直らなければ打ち切って、次へ
5. すべての障害を runbook の項目にする。5分以内に直せたものは「症状・確かめること・直すこと」の3行でよい。直せなかったもの、または30分以上かかったものは、次は5分で直せる長さの手順にする
6. 復旧のあとで、データが失われていないか、嘘の表示（止まっているのに「稼働中」）が出ていないかを確かめる。出ていたら、それは障害ではなく設計の問題。`capstone/docs/known-issues.md` に書く
7. **本題（その2）**：10台の試験。自分の Ubuntu から、C2 のホスト名の指定で10台ぶんの agent を10秒間隔で30分動かす。一覧が5秒以内に更新されること、グラフが表示されることを確かめる。その間の server と PostgreSQL の CPU・メモリを記録する。障害試験の中で最も影響が大きかった障害を、この負荷の中でもう一度起こす
8. runbook を更新したあと、**別の人の手で**課題1をやり直す（家族や友人でよい。いなければ、1週間あけて自分で。どちらだったかを記録に書く）。手順に無いコマンドが出たら、それは runbook の欠陥。あけている間は、`known-issues.md` の修正か、C8 の課題1〜2（基準の測定）を進めてよい
9. **本題（その3）**：試験の結果をまとめる（`tests/summary.md`）。障害ごとの検出・特定・復旧の時間の表、直せなかったもの、設計の弱点、次にやること。C1 の要件定義書と照らし、満たせていない要件があれば正直に書く
10. 振り返りと区分け。`capstone/docs/retrospective.md` に、AIなしで書いた部分とAIを使った部分の区分け（`git log --grep` で `[no-ai]`・`[ai]`・`[mixed]` のコミットを数え、ディレクトリやファイルの単位で一覧にする）と、そこはAIに任せてよいと判断した理由を書く。`notes.md` には、O8 の `retro.md` と比べて「読む順」「境界を壊す」が自分のコードにも効いたか、効かなかったならなぜかを書く

### 発展（任意）

- 障害を1つ、O6 の Ansible で自動的に起こし、自動的に検出する（監視の監視）
- 復旧を自動化できるものを1つ選び、自動化したうえで、自動化が壊れたときの手順も runbook に書く

## 詰まりやすいところ

- runbook のとおりに打っても動かない → 手元の環境にあって、まっさらな環境に無いものを探す（O7 の課題9）。`which`、`env`、`ls ~/.config` の差
- 障害を起こしたのに検出できない → 検出の手段（課題3）が、その障害を見ていない。「何を見れば分かるか」が空欄のまま試験に入っていないか
- 直したつもりで直っていない → 復旧の確認（課題6）を飛ばしていないか。「動いた」と「正しく動いた」は違う
- 障害の起こし方が分からない → ディスクは `man fallocate`（大きなファイルを一瞬で作る）、時刻は `man date`（時刻を設定するオプション。成功しても何も表示しないので、続けて `date` で確かめる）と `man timedatectl`（同期を止める方法）を引く。ログは agent の間隔を1秒にして、server に拒否させると増える
- ディスクを埋めたのに `df` が減らない → 書いた場所が別のファイルシステム。`df <書いた場所>` と `findmnt` で見る（Ubuntu 26.04 では `/tmp` は tmpfs、つまりメモリ）
- 時刻をずらしても数秒で戻る → 何が戻しているかを `journalctl -f` で見る。NTP（`timedatectl` で止める）のほかに、VM がホストの時計に合わせていることがある（Lima なら `lima-guestagent`、WSL2 なら Hyper-V の時刻同期。効き方の設定は `/sys/module/hv_utils/parameters/` にある）。**うしろへずらしたときだけ戻る**なら、戻しているものは遅れだけを直している。ずらすのは agent 側の VM（server とは別の時計）。そのうえで、死活の判定（最後の受信から30秒）がどの時計を見ているかを C4 の判定の関数と C1 の ADR で確かめる
- 10台で一覧が遅い → D14 の実行計画。インデックスが効いているかを `EXPLAIN` で見る

## 完了条件の確かめ方

1. `tests/rebuild-*.md` に、「runbook に無いコマンド」が0個の回の記録がある（自分以外の人の手で1回。いなければ、1週間あけて自分で。どちらかを明記）
2. `tests/faults.md` の障害のうち8割以上に、検出・特定・復旧の時間と、打ったコマンドの記録がある
3. すべての障害に runbook の項目がある（5分で直せたものは3行でよい。30分以上かかったものは「症状 → 確かめること → 直すこと」の形で）
4. 10台・10秒間隔で30分動かし、一覧の更新が5秒以内、グラフが表示される記録がある
5. `tests/summary.md` があり、C1 の要件との照合が書いてある
6. `retrospective.md` に、AIなしで書いた部分とAIを使った部分の区分けと、判断理由がある
7. [評価基準](../../../docs/06-evaluation.md)の Stage 5 の「設計と技術選定を30分でAIに説明する」を平日に行い（頼み方は `prompts/capstone-defense.md`）、やり取りを `capstone/docs/defense.md` に残してある

## 残すもの

- `capstone/docs/runbook.md`（更新版。バックアップと復元の節を含む）、`capstone/docs/known-issues.md`、`capstone/docs/retrospective.md`
- `capstone/docs/tests/`（`rebuild-*.md`、`faults.md`、`fault-*.md`、`summary.md`）
- `notes.md`（振り返り）
- 障害試験で使ったダミーデータや `.env` はコミットしない

試験の記録と runbook は `capstone/docs/` に置く（この `TASKS.md` の隣ではない）。`notes.md` だけをこのディレクトリに書く。どちらも AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
