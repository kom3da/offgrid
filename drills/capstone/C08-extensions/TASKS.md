## ねらい

必須版は C7 で完成している。C8 は任意で、卒業の条件ではない。ここでは、[トラックのページ](../../../docs/15-track-c-capstone.md)の発展の項目から、自分の運用で困った順に選び、要件 → 設計 → 実装 → 試験 → runbook への反映、を1項目ごとに一周させる。どれを選んでも、負荷試験とチューニング（O9）は行う。機能を足せば負荷の形が変わり、「10台で動く」が「100台で動く」とは限らないことを、数字で確かめるため。

## このユニットで身につけること

- 発展の項目を、実際の運用で困ったことから選び、理由をADRに書く
- 選んだ項目ごとに、実行して確かめられる受け入れの条件を先に書き、その観察の記録で「できた」を示す
- 変更の前後で負荷試験を行い、追加した機能が性能に与えた影響を数字で示す
- 100台・10秒間隔の負荷を模し、p95を測り、O9の型でホットスポットを直す
- 追加のたびに、runbook からの再構築（C7）と障害試験が壊れていないことを確かめる
- 追加した部分についても、AIなしで書いた部分とAIを使った部分を区分けする

## キーワード

- **Webhook**：出来事が起きたときに、決めておいたURLへHTTPの `POST` で知らせる仕組み
- **prober（プローブ）**：外から対象にHTTPやTCPでつなぎ、応答の有無で死活を判定する方式。agent が内側から送る方式と対になる
- **ロールアップ（集約）**：細かい計測値を、1分平均などの粗い値にまとめること（D15）
- **パーティション**：1つの表を、時刻などで区画に分けること（D15）。古い区画は、行を消すのではなく区画ごと落とせる
- **監査ログ**：誰が、いつ、何を、どう変えたかの記録。後から書き換えられないことが要点
- **バッファリングと再送**：送れなかったデータを手元に貯め、復旧後に順に送ること
- **自己監視**：監視システム自身の受信件数・遅延・エラー数を、同じ仕組みで見ること
- **チューニング**：測って、1か所直して、もう一度測ること。測らずに直さない（O9）

## 課題

1. 選ぶ。困ったこと3つと `retrospective.md` から、項目を1〜3個選ぶ。1項目ごとにADRを書く（なぜ今それか、何はやらないか、下の受け入れの確認を自分の環境に合わせた形）。`requirements.md` の「今回はやらない」節から、選んだ項目を発展の要件に移し、回数を見積もる。C7 の `tests/faults.md` の形式（起こし方・期待する検出・期待する復旧）で、試験の「手順・期待する結果」を先に書く
2. **本題（その1）**：変更前の基準を測る。O9 の型で、watchdeck に対するシナリオを `docs/tests/` に書き、流す。負荷は、C7 の10台・10秒間隔と、模した100台・10秒間隔の2段階。同時に、読む側の負荷（一覧の `GET`、直近1時間のグラフの `GET`（24時間を足していればそれも）、SSE の接続3本）も入れる。記録するのは、受信の `POST` と各 `GET` の p50・p95・p99・エラー率、`docker stats`、表の行数の増え方、グラフの問い合わせの `EXPLAIN (ANALYZE, BUFFERS)` の実行時間、CPUプロファイルの `top`
3. アラートとWebhook
   - 目標：閾値の規則を超えたら「発生」を、戻ったら「復旧」を記録し、両方をWebhookで通知する
   - 使うユニット：G15、G16、G19、D6、D8、C1のADR
   - 受け入れの確認：「CPUが80%を3回連続で超えたら」の規則を1つ入れる。通知の受け口は、G12 の要領で、届いた `POST` の本文を標準出力に書くだけのサーバーを別に作る。agent の値をわざと超えさせると、判定の間隔1回ぶん以内に「発生」の行が1件でき、受け口に `POST` が1件だけ届く。値が戻ると「復旧」の行と `POST` が1件。発生中に server を再起動しても、「発生」が二重に記録・通知されない（行数と `POST` の件数で示す）。受け口を止めておくと、再試行がC1のADRの間隔で行われ、ログに残る。URLとトークンは `.env` にだけ書く
4. prober
   - 目標：agent を入れられない対象（ルータ、compose の PostgreSQL など）を、外からHTTPかTCPで死活判定する
   - 使うユニット：G15、G16、G19、F8、F9
   - 受け入れの確認：対象を3つ登録する（自分のAPIの確認用パス、TCPの `127.0.0.1:5432`、そして応答しない対象。応答しない対象は、`net.Listen` で受け付けるだけで何も返さない小さなプログラムを作る）。間隔10秒・タイムアウト2秒で、応答しない対象が「停止」になるまでの秒数と、残り2つの判定にかかる時間が伸びていないことを、ログで示す。`docker compose stop` でDBを止めると、30秒以内に「停止」になる。対象を50に増やしても、1周が間隔の中に収まる。`go test -race` が通る
5. グループとタグでの絞り込み
   - 目標：サーバーにグループやタグを付け、一覧・グラフ・SSE を絞り込める
   - 使うユニット：D6、D7、D9、G12、G13、T8〜T10、C4
   - 受け入れの確認：10台のうち3台に `web` のタグを付け、絞り込みの `GET` が3台だけを返す。存在しないタグ、使えない文字を含むタグでの応答は、`api.md` に決めたとおりになる（テストで示す）。画面で絞り込むと行が減り、SSE の更新は表示中の行にだけ反映される。絞り込みの状態がページの再読み込み後も残る。絞り込みの問い合わせの `EXPLAIN` で、インデックスが使われている
6. 1分集約とパーティション
   - 目標：古い生データを1分平均などに集約し、生データの表を時刻で区画に分け、削除を区画の削除に置き換える
   - 使うユニット：D13、D14、D15、C3
   - 受け入れの確認：模した100台で30分動かすと、集約の表に1台あたり30行（±1）でき、平均・最大・最小が入っている。保持期間を試験用に短くすると、期間を過ぎた区画が落ち、24時間のグラフは集約の表から表示され続ける。グラフの問い合わせの `EXPLAIN (ANALYZE, BUFFERS)` で、期間外の区画が読まれていないこと（計画に出る区画の名前で示す）と、実行時間の前後比較。行の削除と区画の削除で、かかった時間を比べる。区画に変えるマイグレーションは番号付きSQLで書き、C7 の runbook の「バックアップと復元」の手順で戻した、データ入りのDBに対して通る
7. 監査ログ
   - 目標：設定の変更（サーバーの登録と削除、トークンの再発行、保持期間、規則）を、誰が・いつ・何を・前後の値、の形で残す
   - 使うユニット：G14、D6、D8、D11
   - 受け入れの確認：5種類の変更をAPI経由で1回ずつ行うと、監査の表に5行でき、それぞれに誰（トークンの識別）・いつ（`timestamptz`）・何を・変更前と後の値がある。`GET` では1行も増えない。失敗した変更（400や401）を残すかどうかは決めて、テストで示す。アプリのDBロールで監査の表を `UPDATE`・`DELETE` しようとすると権限エラーになる（`psql` でそのロールとして試す）。runbook に「誰がいつ変えたか」を調べる問い合わせを足す
8. agent のバッファリングと再送
   - 目標：中央側が止まっている間の計測値を agent が手元に貯め、復旧後に順に再送する（C7 で「失ってよい」とした空白をなくす）
   - 使うユニット：G5、G9、G16、G19、C2
   - 受け入れの確認：server を5分止めて再開すると、グラフにその5分の空白がない。保存される時刻が、受信時刻ではなく agent の計測時刻であることを、行を見て示す。貯める量の上限を決め（件数かMB）、server を2時間止めても、貯めた量が上限で止まり、agent の `VmRSS`（`/proc/<PID>/status`）が増え続けない。上限に達したとき、古いものと新しいもののどちらを捨てるかを決め、テストで示す。止めている間に agent を再起動しても貯めたものが残るかは、貯め方（メモリかファイルか）で決まる。どちらにしたかと理由をADRに書く。100台が同時に再送する瞬間の受信の p95 を、課題2のシナリオに足して測る。再送された古いデータで、死活判定が「稼働」に変わらないことを確かめる
9. 自己監視
   - 目標：watchdeck 自身の受信件数・最終受信からの遅延・エラー数・SSE の接続数を出し、同じ画面と同じ規則（課題3を選んだ場合）で見る
   - 使うユニット：G14、G15、G20、C4
   - 受け入れの確認：自己監視の値を返すエンドポイントがあり、トークンなどの秘密の値を含まない。10台・10秒間隔で5分動かすと、受信件数が毎分60件（±5%）ずつ増える。agent を3台止めると、その3台だけ遅延が伸びる。不正な `POST` を10回送ると、エラー数がちょうど10増える。server を再起動したとき値がどうなるかを決め、runbook に書く。数え上げの処理が `-race` で警告を出さない
10. Ansible での構築
    - 目標：空のUbuntuに、中央側（compose）と agent の一式を、プレイブック1回で構築する
    - 使うユニット：O6、O7、C6、C7
    - 受け入れの確認：O6 の検証環境を作り直し、プレイブックを1回流すと、`docker compose ps` の全サービスが動き、画面が見え、agent が `systemctl is-active` で `active`。続けて2回目を流すと `PLAY RECAP` が `changed=0`、`failed=0`。`.env` の値はリポジトリの外から渡す。runbook の再構築の節が「プレイブックを流す」に置き換わり、C7 の「runbook にないコマンドが0個」の確認が通る。C7 の手作業の再構築と、かかった時間を比べる
11. 100台・10秒間隔で p95 100ms以下
    - 目標：模した100台・10秒間隔で、受信の `POST` と、一覧・グラフの `GET` の p95 が、利用者から見える経路（リバースプロキシ経由）で 100ms 以下
    - 使うユニット：O9、O3、D14、D15、G17
    - 受け入れの確認：課題2と同じシナリオを30分流し、`POST` と各 `GET` の p95 が 100ms 以下、エラー率0、SSE の3本が5秒以内に更新を受け取る（C7 の基準）。届かない場合は、O9 の型で「CPUプロファイルと `pg_stat_activity` と `docker stats` で場所を特定 → 1か所直す → 同じシナリオで測り直す」を繰り返し、1回ごとの数字を `docs/tests/` に残す。届いたら止める。届かなくても、「どこが詰まり、何を試し、なぜ届かなかったか」を数字付きで残せば、この項目の記録としては完成
12. **本題（その2）**：選んだ項目がすべて終わったら、課題2と同じシナリオを流して「変更後」を記録する。少なくとも1つはチューニング（O9 の「1か所直して測り直す」）を行い、前後を並べる。C7 の runbook からの再構築（runbook にないコマンドが0個）と障害試験をやり直し、足した部品（prober、alert、再送など）の障害を `tests/faults.md` に足して行う。runbook（新しいサービス、新しい「よくある障害」）、`api.md`、`.env.example`、`retrospective.md`（追加した部分のAI・AIなしの区分け）、`PROGRESS.md` を更新する

### 発展（任意）

- server を ingest（受信）と api（配信）に分ける（トラックのページの「構成」の発展）。compose にサービスを足し、片方を止めてももう片方が動き続けることを、障害試験で示す

## 詰まりやすいところ

- どれを選ぶか決められない → 「実際に使っていて困った順」で1つだけ選ぶ。全部はやらない。卒業の条件には入っていない
- 足したら、C7 で通っていた試験が落ちる → 追加のたびに `tests/faults.md` の障害試験と、runbook からの再構築を回す。戻せる単位でコミットする。落ちた試験が、追加した部品のどの振る舞いのせいかを、障害試験の型（予想 → 観察）で切り分ける
- 100台の模擬で、負荷試験の道具や模した agent のほうが先に飽和する → O9 の「道具自身の飽和」を思い出す。`top` で誰がCPUを使っているかを見て、道具と模した agent を O6 の検証環境から動かす
- p95 が 100ms を超え、どこを直せばよいか分からない → O9 の課題7の「兆候」の箇条書きに戻る。グラフの問い合わせの `EXPLAIN (ANALYZE, BUFFERS)` の実行時間が、p95 のうちどれだけを占めるかを先に見る。1か所ずつ
- 再送を入れたら、復旧の瞬間に server が詰まる → 再送の間隔と1回の件数の上限をADRで決める。課題2のシナリオに「復旧の瞬間」を足して測る
- どこまでAIに頼ってよいか迷う → Stage 5 の決まり：AIなしデーに書くのは、agent・server・web の中心部分（データの流れに関わるコード）。C8 で足す prober、alert、再送、集約も、データの流れに関わるので自分で書く。Ansible のプレイブックは O6 の再現として自分で書く。平日にAIを使ってよいのは、レビュー、見た目の調整（CSS）、ドキュメントの校正。使った箇所は `[ai]` か `[mixed]` でコミットする
