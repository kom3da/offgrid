## ねらい

API、PostgreSQL、リバースプロキシの3つを、1つのファイルに書き、コマンド1つで全体を起動できるようにする。閉域の現場では、「手順書どおりに `docker run` を5回打つ」よりも、「ファイル1つと `docker compose up`」のほうが、間違いが起きにくく、引き継ぎもしやすい。卒業制作の中央側も、この形で配る。

## このユニットで身につけること

- 複数のコンテナの構成を、composeファイルに書く
- コンテナどうしが、サービス名で通信できることを確かめる
- 外に公開するポートを、必要なものだけに絞る
- データをボリュームに置き、作り直しても消えないようにする
- ヘルスチェックを付け、「起動した」と「使える状態になった」の違いを観察する
- 起動の順番と、依存先が使えるようになるまで待つ設定を書く
- リバースプロキシの設定を書き、外からのリクエストをAPIに中継する
- パスワードなどの値を、composeファイルの外から渡す

## キーワード

- **docker compose**：複数のコンテナの構成を1つのファイルに書き、まとめて起動・停止する道具
- **サービス**：composeファイルの中での、コンテナ1種類ぶんの定義（O2の systemd のサービスとは別のもの）
- **リバースプロキシ**：外からのリクエストを受け取り、内側のサーバーに中継するサーバー。TLS、圧縮、静的ファイルの配信などを、アプリの手前で受け持つ
- **ボリューム**：コンテナを消しても残る、データの置き場所（F10）
- **ユーザー定義ネットワーク**：composeが自動で作る、コンテナどうしをつなぐ内部のネットワーク。サービス名で名前解決できる
- **ヘルスチェック**：コンテナの中でコマンドを定期的に実行し、「使える状態か」を判定する仕組み
- **`depends_on`**：サービスの起動の順番と、待つ条件を指定する項目
- **`.env`**：composeが自動で読み込む、変数の定義ファイル。コミットしない

## 平日に読むもの

- Docker Composeの公式ドキュメントの「Compose file reference」のうち、services、networks、volumes の節と、「Control startup and shutdown order」のページを読む（手元に保存しておくと速い）
- Docker Hubの `postgres` イメージの説明ページを保存する。環境変数と、初期化スクリプト（Initialization scripts）の節を読む
- リバースプロキシは、nginx か Caddy のどちらかを自分で選ぶ。**平日のうちにイメージを `docker pull` し、ドキュメントを保存する**
  - nginx：公式ドキュメントの「Beginner's Guide」と、`ngx_http_proxy_module` のページ
  - Caddy：公式ドキュメントの「Caddyfile Concepts」と、`reverse_proxy` ディレクティブのページ
- `docker compose version` が動くことを確かめる。動かなければ、平日のうちに入れる（パッケージ名は `apt search docker-compose` で探す）
- `docker compose --help` と、各サブコマンドの `--help`。AIなしデーは、これと保存したドキュメントだけで進める

## 準備

```sh
mkdir -p ~/sandbox/o5
cd ~/sandbox/o5
docker images
```

`docker images` で、O4の `api:step3`、`postgres:18`、選んだリバースプロキシのイメージが、手元にあることを確かめる。これまで使ってきた `pg-offgrid` のコンテナとは別に、compose用のPostgreSQLを新しく作る。`pg-offgrid` は消さない。

composeファイル、リバースプロキシの設定、メモは、リポジトリの `drills/infra/O05-compose/` に写しを置く。

## 課題

1. PostgreSQLだけを書いた、最小のcomposeファイルを作る。F10で使った `docker run` のオプション（`--name`、`-e`、`-p`、`-v`）は、composeファイルではそれぞれどの項目に当たるか。`docker compose up -d`、`docker compose ps`、`docker compose logs`、`docker compose down` を試す。`docker compose config` は、何を表示するか
2. `docker compose down` と `docker compose down -v` の違いを、テーブルを1つ作ってから試して確かめる。`docker volume ls` に出る名前は、どういう規則で付いているか。PostgreSQL 18のイメージで、ボリュームをどのパスにマウントするべきかは、[基礎トラック](../../../docs/10-track-f-foundation.md)の「F10で使う起動例」の注意書きで確かめる
3. パスワードを、composeファイルに直接書かずに渡す。「Compose file reference」で、環境変数をファイルから読み込む方法と、`.env` の変数をcomposeファイルの中で参照する方法を調べる。`.env` を `.gitignore` に入れ、ダミーの値を書いた `.env.example` だけを残す
4. APIのサービスを足す。イメージはO4の `api:step3`。APIからDBへの接続先のホスト名は、何にすればよいか。`localhost` では、なぜ駄目か。この時点では、確認のためにAPIのポートを `127.0.0.1` に公開してよい
5. 空のDBには、テーブルがない。D13のマイグレーションを、どうやって適用するかを決める。`postgres` イメージの説明ページの、初期化スクリプトの節を読む。その仕組みは「いつ」実行され、「いつ」実行されないか。ボリュームが残っている状態で `up` し直すと、どうなるか
6. **観察**：`docker compose down -v` で全部消してから `docker compose up` し、APIとDBのログを、時刻の順に読む。APIが最初にDBへつなごうとした時刻に、DBは接続を受け付けていたか。APIは、そのときどう振る舞ったか（落ちた、再試行した、エラーのまま動き続けた）。何回か繰り返して、結果が毎回同じかを確かめる
7. DBにヘルスチェックを付ける。`postgres` のイメージの中に入っている、接続を受け付けているかを確かめるコマンドを探す（コンテナの中で `ls /usr/lib/postgresql/*/bin/` を見る）。`docker compose ps` の `STATUS` は、起動の直後からどう変わっていくか。`docker inspect` で、ヘルスチェックの履歴を見る
8. APIの `depends_on` を、「DBが起動したら」ではなく「DBのヘルスチェックが通ったら」に変える。「Control startup and shutdown order」のページで、書き方を調べる。課題6の観察をもう一度行い、何が変わったかを書く。DBが、運用中に一時的に落ちた場合、`depends_on` は助けになるか
9. リバースプロキシのサービスを足す。設定ファイルを自分で書き、コンテナにマウントする。すべてのリクエストを、APIに中継する。ホストに公開するポートは、リバースプロキシの1つだけにし（`127.0.0.1:8080` など）、APIとDBのポートの公開をやめる。`curl -v` で、レスポンスヘッダのどこに、リバースプロキシを通った痕跡があるか
10. リバースプロキシを通したとき、APIのアクセスログ（G14）に出る「相手のIPアドレス」は、誰のものになるか。本来のクライアントのアドレスをAPIに伝えるために、よく使われるHTTPヘッダを、リバースプロキシのドキュメントで調べる
11. **本題**：`docker compose down -v` で何もない状態にしてから、`docker compose up -d` だけを実行する。ほかのコマンドを一切打たずに、`curl` でリバースプロキシ経由の登録（POST）と一覧取得（GET）が成功することを確かめる。そのあと `docker compose down`（`-v` なし）と `docker compose up -d` を行い、登録したデータが残っていることを確かめる
12. マシンを再起動したあと、compose の一式は動いているか。「Compose file reference」で、再起動の方針を決める項目を探して設定する。O2の systemd のサービスで設定した再起動と、考え方はどこが同じで、どこが違うか

### 発展（任意）

- O4の distroless のAPIコンテナには、`curl` もシェルもない。このコンテナにヘルスチェックを付ける方法の案を2つ書き、できれば1つを実装する
- リバースプロキシで、`/healthz` のような確認用のパスだけを、リバースプロキシ自身が直接返すようにする
- `docker compose up` を `-d` なしで実行し、Ctrl+C で止める。3つのコンテナは、どの順番で止まるか。APIの終了処理（G16）のログは出るか
- 自己署名の証明書（F9）を作り、リバースプロキシで HTTPS を受ける

## 詰まりやすいところ

- `up` すると、ポートが使用中だというエラーになる → `ss -tlnp` で、そのポートを誰が使っているかを調べる（`pg-offgrid` や、O2のサービスが動いていないか）
- APIが `connection refused` や名前解決のエラーで落ちる → 接続先のホスト名が、composeのサービス名と一致しているか。`docker compose exec` でDBのコンテナに入り、DBそのものは動いているかを先に確かめる
- 初期化スクリプトを直したのに、反映されない → その仕組みが実行される条件を、`postgres` イメージの説明ページで読み直す
- リバースプロキシが502を返す → リバースプロキシのログを `docker compose logs` で読む。中継先のホスト名とポートは、コンテナの中から見たものになっているか
- 設定ファイルを直したのに、動きが変わらない → マウントしたパスが、そのイメージが設定を読む場所と合っているか。コンテナを作り直したか
- composeファイルのエラーの意味が分からない → `docker compose config` で、解釈された結果を見る。インデント（字下げ）が、構造そのものを表す書式であることを思い出す

## 完了条件の確かめ方

課題11を、そのまま実行する。

- `docker compose down -v` のあと、`docker compose up -d` の1コマンドだけで、30秒以内に `docker compose ps` の全サービスが動いている（DBは `healthy`）
- リバースプロキシ経由の `curl` で、POST と GET が成功する
- `docker compose down` → `docker compose up -d` のあとも、データが残っている
- `ss -tlnp` で見て、ホストに公開されているのは、リバースプロキシのポートだけ

## 残すもの

- composeファイル、リバースプロキシの設定ファイル、`.env.example`（値はダミー）
- 課題6と課題8の観察の記録（ログの抜粋と、時刻の順に何が起きたか）を `notes.md` に
- nginx と Caddy のどちらを選んだかと、その理由を1〜2行
- `.env` はコミットしない

コマンドを試す場所は `~/sandbox/o5`。メモと設定ファイルの写しは、リポジトリの中のこのディレクトリに、AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
