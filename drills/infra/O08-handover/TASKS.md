## ねらい

現場で渡されるのは、自分が書いたコードではない。誰か（多くの場合はAI）が書いた数千行を、説明も足りないまま引き継ぎ、動かし、直し、足す。このユニットでは、AIに小さなサービスを書かせて問題を仕込ませ、それを**AIなしで**読み解いて直す。デバッグドリル（100行に3つ）を、システムの大きさでやる。このカリキュラムの動機そのものにあたる回。

## このユニットで身につけること

- 知らないリポジトリを、決まった順で読み、構造を図にできる
- 動かして、ログと挙動から、書いてあることと実際の差を見つけられる
- 設計上の問題（責務の混ざり、エラーの握り潰し、境界の抜け）を指摘できる
- 直したことをテストで固定し、動いたままで機能を1つ足せる
- 次の人に渡す引き継ぎ文書を書ける

## キーワード

- **引き継ぎ**：他人が書いたものを、動かし続けられる状態で受け取ること
- **読む順**：入口（`main`）→ 設定 → データの流れ → エラーの流れ → テスト
- **境界**：外から来るもの（HTTP、DB、ファイル、時刻、環境変数）と、自分のコードの境目。問題はここに集まる
- **握り潰し**：エラーを受け取って何もしないこと（`_ = err`、空の `catch`）
- **仕込まれた問題**：このユニットでは、AIに5〜8個入れさせる。設計の問題とバグの両方

## 平日に読むもの

- O3 で使った `strace`・`ss` の使い方を、自分のメモで見返す
- Go の公式ブログ「Organizing a Go module」（ディレクトリの役割の目安）
- 『リーダブルコード』の、コードを読む側の章（章番号は、手元の本の目次で確認する）

## 準備

**セッションの間の日に**、[prompts/handover.md](../../../prompts/handover.md) の文面でAIにサービスを作らせる。仕込んだ問題の答えは `answers/` に置き、開かない。作らせるもの：HTTP API＋PostgreSQL＋Dockerfile＋compose＋不完全な README。1,500〜3,000行。置き場所は `drills/infra/O08-handover/service/`。

```sh
mkdir -p drills/infra/O08-handover
# AI が service/ を作る。answers/ にできる答えは開かない
```

## 課題

1. 動かす前に読む。`main` から入口を辿り、ディレクトリごとの役割と、外との境界（HTTP・DB・時刻・環境変数）を `structure.md` に図か箇条書きで書く。**この時点で `service/` の中を書き換えない**
2. README のとおりに動かしてみる。動かないなら、何が書いていないか・何が違うかを `blockers.md` に書く。README を直すのは後にし、まず動かす
3. 動いたら、O3 の道具で観察する。`ss` で待ち受けと接続、`strace -f -e trace=network,openat` で何を開いているか、ログに何が出て何が出ないか。読んで想像した構造と、観察した構造の差を `structure.md` に足す
4. 境界を1つずつ壊す。DB を止める、不正な JSON を送る、環境変数を消す、大きな入力を送る。それぞれ、サービスがどう振る舞うか（落ちる、黙る、正しく断る）を表にする
5. **本題（その1）**：問題を一覧にする（`findings.md`）。設計の問題とバグを分け、それぞれに「どこで」「何が」「どう困るか」「重要度」を書く。答えを見ずに、少なくとも5つ挙げる
6. **本題（その2）**：重要度の高いものから直す。直すたびに、それを見つけるテストを先に書いて落とし、直して通す。`go test -race ./...` を通す。1つ直すごとにコミットする
7. 機能を1つ足す（`prompts/handover.md` で指定したもの）。既存の構造に合わせて書き、既存のテストを壊さない
8. README を、自分が課題2で詰まった箇所から書き直す。次の人が課題2で詰まらない README にする
9. `handover.md` を書く：構造の要点、直したこと、直していない既知の問題、足した機能、次に手を付けるべき箇所。5分で読める長さにする
10. **本題（その3）**：答え合わせ。`answers/` を開き、仕込まれた問題と自分の `findings.md` を照らす。見つけた数、見つけられなかったものとその理由（読み飛ばした／動かして観察しなかった／知識が無かった）を `retro.md` に書く
11. 見つけられなかった問題を、どうすれば見つけられたかを考え、課題1〜4のどの段階に何を足せばよいかを `retro.md` に書く。C7 の障害試験で使う

### 発展（任意）

- 同じ文面で別のAIにサービスを書かせ、仕込み方の癖を比べる
- 直したあとのサービスに O9 の負荷をかけ、直す前と比べる

## 詰まりやすいところ

- どこから読めばいいか分からない → `main` の最初の20行。そこから呼ばれる関数を1段ずつ。全部を読もうとしない
- 動かす前に直したくなる → まず動かす。動かないものを直すと、直したから動いたのか、元から動いたのか分からなくなる
- 問題が見つからない → 境界を壊す（課題4）。正常系だけ見ていると見つからない。エラーの行き先を全部追う
- 直したら別の場所が壊れた → 直す前の挙動をテストで固定してから直したか
- 答えを見たくなる → 課題10まで開かない。開いたら、このユニットの意味が無くなる

## 完了条件の確かめ方

1. `findings.md` に5つ以上の問題があり、答えと照らして、仕込まれた問題の6割以上を見つけている
2. 直したものに、それを見つけるテストがあり、`go test -race ./...` が通る
3. `handover.md` を読んだだけで、次の人が README のとおりに動かせる（O7 の課題9 と同じやり方で、まっさらな環境で確かめる）
4. `retro.md` に、見つけられなかった理由と、次に足す手順がある

## 残すもの

- `structure.md`、`blockers.md`、`findings.md`、`handover.md`、`retro.md`
- `service/`（直したコードとテスト）
- 答えのファイル（answers の中）は、答え合わせのあとも引用しない

ファイルは、リポジトリの中のこのディレクトリに、AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
