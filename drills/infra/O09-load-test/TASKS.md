## ねらい

「なんとなく遅い」を、数字にする。閉域の現場では、サーバーを増やして逃げることも、クラウドの監視画面に頼ることもできない。自分のAPIが「毎秒何件まで、どのくらいの応答時間で」さばけるかを測り、遅い箇所を `pprof` で見つけ、1つ直して、前後を同じ条件で比べる。この「測る → 1つ直す → また測る」の型が、卒業制作の100台の試験（C8）と、その後の運用で、そのまま使える。

## このユニットで身につけること

- 負荷試験の道具（`vegeta` か `k6`）を、版を固定して入れて動かす
- 対象・率・時間を決めたシナリオを書き、同じ条件で何度でも流す
- p50・p95・p99 とエラー率を読み、「平均」だけで判断しない
- 率を上げていき、応答時間が伸び始める点と、エラーが出始める点を見つける
- 負荷をかけている最中にCPUプロファイルを取り、時間を使っている関数を見つける
- DBが詰まっているのか、Goのコードが詰まっているのかを、複数の道具の見え方で切り分ける
- 改善を1つだけ入れ、同じシナリオで前後を比べて記録する

## キーワード

- **負荷試験**：決めた量のリクエストを送り続け、応答時間と失敗の割合を測ること
- **スループット**：1秒あたりにさばけた件数（req/s）
- **レイテンシ（応答時間）**：リクエストを送ってから、応答が返るまでの時間
- **パーセンタイル（p50・p95・p99）**：応答時間を小さい順に並べたときの、50%目・95%目・99%目の値。p95が200msなら、20回に1回は200msより遅い
- **エラー率**：失敗した割合。接続できなかった、タイムアウトした、5xxが返った、を分けて数える
- **一定レート**：応答を待たずに、決めた間隔でリクエストを送り続ける方式。`vegeta` の基本の動き。`k6` では、実行のしかた（executor）で選ぶ
- **ウォームアップ**：測る前に、短く負荷をかけておくこと。起動直後の遅さを、測定に混ぜないため
- **ホットスポット**：プログラムの中で、時間の多くを使っている箇所
- **飽和**：CPUや接続がいっぱいで、それ以上受けられない状態。ここを超えると、応答時間が急に伸びる
- **コネクションプール**：DBへの接続を何本か持って使い回す仕組み（G17）。本数の上限が、詰まる場所になることがある

## 平日に読むもの

  - `k6`：公式ドキュメントの「Running k6」「Options」「Metrics」「Scenarios」の各ページ。`k6 run --help`
- `go tool pprof -h`。O3で保存したGoの公式ブログ「Profiling Go Programs」と、自分のO3の `cheatsheet.md`
- PostgreSQLマニュアルの「Monitoring Database Activity」（`pg_stat_activity` の列の説明）と、D14で読んだ「Using EXPLAIN」
- 『［試して理解］Linuxのしくみ』第3章（プロセススケジューラ）、第8章（記憶階層）
- 『入門 監視』4章（統計入門）、7章（アプリケーション監視）

## 準備

```sh
mkdir -p ~/sandbox/o9
cp -r ~/sandbox/o4/api ~/sandbox/o9/api
cd ~/sandbox/o9/api
docker exec -it pg-offgrid psql -U postgres -c 'CREATE DATABASE o9;'
```

対象は、まずコンテナやリバースプロキシを通さず、ホストの上で直接動かしたAPIにする（`go build -mod=vendor` したバイナリを、`DATABASE_URL` を `o9` に向けて起動する）。O3の課題7で付けた `pprof` の入口が、`127.0.0.1` からだけ見えることを確かめておく。表には、D14の要領（`generate_series`）で、数万行のダミーデータを入れておく。

負荷をかける道具と、対象のAPIと、PostgreSQLが、同じマシンで動くことになる。これが結果に与える影響は、課題5で観察する。シナリオ、結果、メモは、リポジトリの `drills/infra/O09-load-test/` に置く。

## 課題

1. 平日に入れた道具が `PATH` にあることを確かめる（`~/bin` などに置く）。`<道具> version` の出力を `notes.md` に書く。`GET /items` に対して、1秒に1件を5秒間、という小さな負荷をかけ、出力の中から、p50・p95・p99、成功の割合、ステータスコードごとの件数を見つける。p99が出ていなければ、ドキュメントで、表示する統計を指定する方法を探す
2. `scenario.md` にシナリオを書く。対象のエンドポイント（一覧の `GET`、1件の `GET`、登録の `POST`。`POST` は本文とヘッダの指定のしかたを、道具のドキュメントで調べる）、率（req/s）、時間（30秒以上）、ウォームアップの有無、繰り返しの回数（3回流して中央値を採る）、毎回記録するもの（道具のバージョン、対象のコミット、開始前の `uptime`、表の行数）。`POST` で増えた行を、次の回の前に戻すかどうかも決める
3. 基準の測定。3つのエンドポイントそれぞれに、低い率（例：10 req/s、30秒）で3回流し、p50・p95・p99・エラー率を `results.md` に書く。**観察**：一覧、1件、登録で、p95はどう違うか。それぞれがDBで何をしているか（D14の `EXPLAIN` で確かめる）と、対応しているか
4. **観察**：一覧の `GET` の率を、10 → 50 → 100 → 200 → 500 req/s と上げ、30秒ずつ流す。p95が急に伸び始めた率と、エラーが出始めた率を見つける。エラーの中身（接続できない、タイムアウト、5xx、途中で切れた）は何で、どの層（道具、OS、API、DB）が出したものか。ここで見つけた「伸び始める率」を、以後の測定の率にする
5. **観察**：課題4の高い率を流している最中に、別の端末で `top` を見る。CPUを使っているのは、API、道具、PostgreSQL（`docker stats pg-offgrid`）のどれか。道具自身がCPUを使い切っていたら、その結果はAPIの性能を表しているか。道具のドキュメントで、決めた率を維持できなかったことをどう知らせるかを探す。`ss -tan` で、`TIME-WAIT` の本数と `ulimit -n` の値も見ておく
6. 課題4の「伸び始める率」で負荷をかけながら、`go tool pprof http://127.0.0.1:<ポート>/debug/pprof/profile?seconds=30` でCPUプロファイルを取る（O3）。`top` で、自分のコードの関数、`pgx` の関数、`runtime` や `syscall` の関数が、それぞれ全体の何%かを読む。`list` で、自分の関数のどの行が重いかを見る。保存先のファイル名（出力の先頭に出る）を控える。負荷をやめて1分後に、goroutineの数が負荷の前と同じに戻っているかも見る（G20）
7. **観察**：DBが詰まる場合と、Goのコードが詰まる場合を、わざと作って見比べる。比較用に、DBに触らず固定のJSONを返すだけのハンドラを一時的に足す
   - 同じ率で、DBに触らないハンドラと一覧の `GET` を流し、p95、`pprof` の `top`、`docker stats` のDBのCPUを並べる
   - 一覧の `GET` が使うインデックスを一時的に落とす（または、表を100万行に増やす）と、p95、`pprof` の `top`、`pg_stat_activity` の `state` と `wait_event_type` の列、DBのCPUは、それぞれどう変わるか
   - 2つの場合の見え方の違いを、「DBが詰まっているときの兆候」「Goが詰まっているときの兆候」として `notes.md` に表にせず箇条書きで残す
8. 課題6と7の結果から、「ここを直せば、p95がこう変わるはず」という仮説を2つ以上書く。1つを選び、変更は1か所だけにする。標準ライブラリと、すでに使っている `pgx`、SQLの範囲で行う。何を変えたかを、`git diff` の写しとして `results.md` に貼る
9. **本題**：変更のあと、課題3・4とまったく同じシナリオ（同じエンドポイント、率、時間、回数）で3回流し、p50・p95・p99・エラー率を、変更前の行と並べて `results.md` に書く。もう一度CPUプロファイルを取り、`top` の出力を変更前と並べる。p95が下がらなかったら、それも結果として書き、仮説のどこが違ったかを考える。戻すか残すかを決め、理由を書く
10. 課題4の率の段階を、もう一度流す。「伸び始める率」と「エラーが出始める率」は動いたか。直したことで、詰まる場所が別（DB側など）に移っただけではないか。`go vet ./... && go test -race -cover ./...` が通ったままかも確かめる
11. `explain.md` に、何も見ずに書く：平均ではなくp95・p99を見る理由、DBが詰まっているときとGoが詰まっているときの見分け方、今回の変更が効いた（または効かなかった）理由。平日にAIに採点を頼む（[prompts/grade-explain.md](../../../prompts/grade-explain.md)）
12. 道具を同じ版で入れる手順（版を固定した取得。バイナリはコミットしないので、手順で入れる）と、`scenario.md` の対象ファイル（`vegeta` の対象ファイル、または `k6` のスクリプト）を、O7 の `build.sh` に足す。まっさらな仮想マシンで `build.sh` を実行したあと、道具が動き、課題1の小さな負荷が流せることを確かめる

### 発展（任意）

- O5のcompose一式（リバースプロキシ経由）に対して同じシナリオを流し、直接の場合と比べる。リバースプロキシは、p50とp95にそれぞれ何msを足しているか。`docker stats` で、3つのコンテナのCPUの配分も見る
- 率を自動で上げていく方式（`k6` の ramping の executor、`vegeta` なら率を変えた `attack` を続けて流す）で、エラーが出る直前の率を見つけ、課題4の手作業の結果と比べる
- O3の発展のヒープのプロファイル（`inuse_space` と `alloc_space`）と、`go test -bench` に `-benchmem` を付けた測定で、いちばん重い関数の1回あたりの割り当て回数を見る（G10）
- もう1つの道具でも同じシナリオを流し、p95が一致するかを見る。一致しないなら、それぞれが「どこからどこまで」を応答時間として測っているか、応答を待つかどうか（一定レートかどうか）を、ドキュメントで確かめる

## 詰まりやすいところ

- 同じシナリオなのに、回ごとにp95が大きくばらつく → 開始前の `uptime` の負荷平均、ほかに動いていたもの（`docker stats`）、ウォームアップの有無、表の行数、道具が同じマシンにいることを疑う。3回の中央値を採り、ばらつきの幅も書く
- `connection refused`、`too many open files`、`cannot assign requested address` が出る → どちら側（道具、API、OS）のエラーか。`ulimit -n`、`ss -tan` の状態ごとの本数（O3）を見る。道具のドキュメントで、接続を使い回す設定を探す
- CPUプロファイルに、自分の関数がほとんど出てこない → プロファイルを取っていた30秒の間に、本当に負荷がかかっていたか。遅さが、CPUを使う種類ではなく、何かを待つ種類ではないか（O3）。goroutineのプロファイルで、何を待っているかを見る
- 改善したのに、数字が変わらない → 詰まっている場所が、仮説の場所だったか（課題7の兆候と照らす）。シナリオを、知らないうちに変えていないか（率、行数、ウォームアップ）。仮説に書いた「変わるはずの数字」と、実際の数字を並べる
- 率を上げると、道具のCPUが100%になり、応答時間が跳ね上がる → 道具自身が飽和している。率を下げる、道具のドキュメントで並列数の設定を探す、O6の検証環境から流す、のどれかにする
- `POST` の試験で表が増え続け、あとの一覧が遅くなる → シナリオに「回の前に表を戻す」を入れたか。行数を毎回記録しているか

## 完了条件の確かめ方

- `results.md` に、同じシナリオ（エンドポイント、率、時間、道具のバージョンが同じ）で測った、変更前3回と変更後3回の p50・p95・p99・エラー率があり、中央値に印が付いている。変更の内容が、`diff` の写しかコミットのハッシュで示されている
- 変更前と変更後の `pprof` の `top` の出力が、テキストで保存されている
- `scenario.md` を読めば、他人が同じ測定を再現できる（打つコマンドがそのまま書いてある）
- 変更のあとも `go vet ./... && go test -race -cover ./...` が通る
- `explain.md` を書き、平日に採点を受けている

## 残すもの

- `scenario.md`、対象ファイルまたは `k6` のスクリプト、`results.md`、`before-top.txt` と `after-top.txt`（`pprof` の `top` の写し）、`explain.md`、`notes.md`（課題4・5・7の観察）
- 改善の変更は、コピーで試したあと、リポジトリの G18 のAPIにも同じ変更を入れてコミットする（`[no-ai]`）
- プロファイルのファイルそのものと、道具のバイナリは、コミットしない

コマンドを試す場所は `~/sandbox/o9`。シナリオとメモは、リポジトリの中のこのディレクトリに、AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
