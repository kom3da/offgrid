## ねらい

「ネットワークがなくても、開発・ビルド・起動ができる」状態を、部品ごとに作り、1つずつ確かめる。閉域の現場に入ってから「あれを持ってくるのを忘れた」と気づいても、取りに戻れない。何を、どの形で持ち込み、持ち込んだものが使えることをどう確かめるか。その段取りを、やり直せるスクリプトとして残す。次のO8で、丸1日の本番を行う。

## このユニットで身につけること

- Goの依存を `vendor/` に固め、ネットワークなしでビルドとテストを通す
- npmのパッケージをキャッシュに集め、ネットワークなしで `node_modules` を再現する
- Dockerイメージをファイルに保存し、消してから復元する
- Goのドキュメントを、手元の `pkgsite` で表示する
- PostgreSQL、MDN、TypeScriptのドキュメントを、オフラインで引けるようにする
- ローカルLLMとモデルを事前に取得し、ネットワークなしで応答が返ることを確かめる
- 持ち込む一式を `tar` と `sha256sum` でまとめ、検証する
- 「集める」手順と「確かめる」手順を、スクリプトにする

## キーワード

- **閉域（エアギャップ）**：インターネットにつながっていない環境
- **ベンダリング**：依存するライブラリのソースを、自分のリポジトリの `vendor/` にコピーして持つこと（G18）
- **モジュールプロキシ**：Goがモジュールを取りに行く先のサーバー。環境変数 `GOPROXY` で指定する
- **`package-lock.json`**：npmが、依存のバージョンと入手元を正確に記録したファイル。`npm ci` は、これに厳密に従う
- **npmのキャッシュ**：一度取得したパッケージを、手元に保存しておく場所
- **`pkgsite`**：pkg.go.dev と同じ見た目で、Goのドキュメントを手元で表示するプログラム
- **DevDocs**：多くの公式ドキュメントを1か所で引けるWebアプリ。ブラウザの中に保存して、オフラインで使える
- **ローカルLLM**：自分のマシンの中だけで動かす言語モデル。Ollamaは、それを動かす道具の1つ
- **マニフェスト**：持ち込むファイルの一覧と、それぞれのハッシュ値を書いたファイル

## 平日に読むもの

- `go help modules`、`go help vendor`、`go help environment`（`GOFLAGS`、`GOPROXY` の説明）
- `npm help ci`、`npm help cache`、`npm help config`（npmのヘルプは、手元に入っているものが開く）
- `docker save --help`、`docker load --help`
- Ollamaの公式の `README.md` と、コマンドの一覧を保存する
- **平日にしかできない「集める」作業が多いユニット。** AIなしデーの前に、次を済ませる
  - `pkgsite` を入れる：`go install golang.org/x/pkgsite/cmd/pkgsite@latest`
  - DevDocs をブラウザで開き、PostgreSQL、JavaScript、DOM、HTML、CSS、TypeScript を有効にして、オフライン用のデータを取得する（設定の「Offline」）
  - Ollamaを入れ、自分のマシンのメモリに収まる大きさのモデルを1つ `ollama pull` する。どのモデルにするかは、自分で決める
  - 『新しいLinuxの教科書』などの書籍と、ここまでのユニットで保存してきたドキュメントの置き場所を、1か所に決める

## 準備

```sh
mkdir -p ~/sandbox/o7 ~/offline-bundle
cd ~/sandbox/o7
```

確認のために、短時間だけネットワークを切る場面がある。切り方は、環境によらず確実な方法として、**ホスト（VMやWSL2を動かしているパソコン本体）のWi-Fiを切る、またはLANケーブルを抜く**ことにする。切れていることは、Ubuntuの中で次の両方が失敗することで確かめる（切る前に、成功することも見ておく）。

```sh
curl -m 5 -sS https://example.com > /dev/null; echo "exit=$?"
getent hosts example.com; echo "exit=$?"
```

リポジトリの `drills/infra/O07-offline-prep/` に、`checklist.md` を作り、[トラックのページ](../../../docs/14-track-o-ops.md)の「閉域環境の準備チェックリスト」の7項目を写す。各項目に、「確かめたコマンド」「結果」「日付」を書き込んでいく。

## 課題

1. 棚卸し：G17のAPIをビルドしてcomposeで起動し、T10の画面をビルドするまでに、ネットワークから取ってくるものを、すべて書き出す（Goのモジュール、npmのパッケージ、Dockerのイメージ、`apt` のパッケージ、ドキュメント）。それぞれ、「どのコマンドが」「いつ」取りに行くか
2. Go：APIのディレクトリで `go mod vendor` を実行する。`vendor/` の中身と `vendor/modules.txt` を眺める。`go help environment` で `GOFLAGS` と `GOPROXY` を調べ、「必ず `vendor/` を使う」「モジュールを取りに行くことを禁止する」設定を、環境変数で指定する。その状態で `go build ./...` と `go test ./...` が通ることを確かめる。`vendor/` をGitにコミットするべきか。理由も書く
3. **観察**：課題2の「取りに行くことを禁止する」設定のまま、`vendor/` を一時的に別名に変えてビルドすると、どんなエラーになるか。このエラーメッセージを、`notes.md` に写しておく（O8で同じものを見たら、すぐ原因が分かるように）
4. npm：T10のディレクトリで、`npm config get cache` でキャッシュの場所を確かめる。`npm help ci` と `npm help config` で、キャッシュの場所を指定するオプションと、オフラインで動かすオプションを調べる。ネットワークがある状態で、`~/offline-bundle/npm-cache` にキャッシュを作る。次に、`node_modules` を消し、`npm ci --offline` で再現して、`npx tsc --noEmit --strict` と `npx vitest run` が通ることを確かめる
5. **観察**：`package-lock.json` にないパッケージを、オフラインの状態で `npm install` しようとすると、どうなるか。`npm ci` と `npm install` は、何が違うか
6. Docker：この先のビルドと起動に必要なイメージを、すべて書き出す（ビルド用、実行用、PostgreSQL、リバースプロキシ）。`docker save` で `~/offline-bundle/` に保存する。1つのファイルに、複数のイメージを入れられるか。ファイルの大きさは、`docker images` の `SIZE` の合計と比べてどうか。1つだけ `docker rmi` で消し、`docker load` で復元して、イメージのIDが元と同じかを確かめる
7. Goのドキュメント：`pkgsite -h` でオプションを確かめ、APIのディレクトリで `pkgsite` を起動する。ブラウザで、標準ライブラリの `net/http` のページと、自分のAPIのパッケージのページを開く。`go doc` と比べて、何が便利か。ネットワークを切った状態でも、開けるか
8. ドキュメント：ネットワークを切り、DevDocsで、PostgreSQLの `CREATE INDEX`、MDNの `fetch`、TypeScriptの `Utility Types` のページを開く。ここまでのユニットで保存してきたドキュメント（Docker、Compose、Ansible、systemd の `man`）の置き場所を `checklist.md` に一覧にする。足りないものは、詰まりメモに書き、平日に集める
9. ローカルLLM：ネットワークを切った状態で、`ollama list` にモデルが出ること、`ollama run` で短い質問に応答が返ることを確かめる。応答が始まるまでの時間と、そのときのメモリの使用量（O1の `/proc/meminfo` か `free -h`）を記録する。**AIなしデーに行うのは、この動作確認の1往復だけ。** 課題を解かせたり、コードを書かせたりしない
10. まとめる：`~/offline-bundle/` の中身の一覧と、それぞれの `sha256sum` を書いたマニフェストを作る（O1）。全体を `tar` でまとめる必要はあるか。USBメモリなどで運ぶ場合の、ファイルの大きさの上限も考える
11. **本題（その1）**：ここまでの手順を、2本のスクリプトにする。どちらも `set -euo pipefail` を付け、`shellcheck` の指摘を0件にする
    - `fetch.sh`：ネットワークがある状態で実行する。`~/offline-bundle/` に、必要なものを集める。2回実行しても壊れない
    - `verify.sh`：ネットワークを切った状態で実行する。最初に「ネットワークが切れていること」を確かめ、切れていなければ中止する。チェックリストの各項目を確かめ、項目ごとに `OK` か `NG` を表示する。1つでも `NG` があれば、終了コードを0以外にする
12. **本題（その2）**：ネットワークを切り、`verify.sh` を実行する。すべて `OK` になるまで、ネットワークを戻して `fetch.sh` を直し、切って確かめる、を繰り返す。最後の実行結果を `checklist.md` に貼り、7項目すべてにチェックを入れる

### 発展（任意）

- Goモジュールのローカルプロキシを立てる。`go help goproxy` を読み、`GOPROXY=file://...` の形で、手元のディレクトリからモジュールを取得できるようにする。`vendor/` との使い分けを考える（Athens というプロキシのサーバーもある）
- npmのローカルレジストリ（Verdaccio）を立て、`npm ci` の取得先をそこに向ける。平日に、Verdaccio本体とドキュメントを取得しておく
- `apt` のパッケージを、閉域へ持ち込む方法を `man apt-get` で調べる（パッケージのファイルだけを取得するサブコマンドがある）。依存するパッケージは、どうなるか
- `fetch.sh` と `verify.sh` を、Ansibleのプレイブック（O6）に書き直す

## 詰まりやすいところ

- `vendor/` があるのに、Goがモジュールを取りに行こうとする → `go env GOFLAGS` の値と、`go.mod` の `go` の行のバージョン、`vendor/modules.txt` が `go.mod` と合っているかを確かめる
- `npm ci --offline` が、キャッシュにないというエラーで止まる → エラーに出ているパッケージ名とバージョンを読む。キャッシュを作ったときと、場所の指定が同じか。キャッシュを作ったあとに、`package-lock.json` が変わっていないか
- `docker load` したイメージに、タグが付いていない（`<none>` になる）→ `docker save` のときに、イメージをIDで指定したか、名前とタグで指定したか
- `pkgsite` が起動に時間がかかる、または外へつなごうとする → `pkgsite -h` で、参照先に関するオプションを読む。どのディレクトリで起動したかも確かめる
- DevDocsで、オフラインにしたはずのページが開けない → 設定の「Offline」の画面で、そのドキュメントが取得済みになっているか。ブラウザの閲覧データを消していないか
- ネットワークを切ったのに、`verify.sh` の最初の確認が「つながっている」と判定する → `curl` の終了コードを、手で確かめる。有線と無線の両方がつながっていないか

## 完了条件の確かめ方

- ネットワークを切った状態で、`./verify.sh` の全項目が `OK`、終了コードが0
- `shellcheck fetch.sh verify.sh` の指摘が0件
- `checklist.md` の7項目すべてに、確かめたコマンド、結果、日付が書いてあり、チェックが入っている

## 残すもの

- 課題1の棚卸しの表、課題3と課題5で写したエラーメッセージ（`notes.md`）
- マニフェスト（ファイル名とハッシュ値）。`~/offline-bundle/` の中身そのものは、コミットしない
