## ねらい

サーバーの設定を、手順書ではなくコードとして書き、何度実行しても同じ状態になるようにする。閉域の現場では、サーバーを作り直す機会が少なく、手順書は古くなりやすい。実行できるコードにしておけば、「書いてあること」と「実際の状態」がずれない。O5で作った構成を、まっさらな検証環境に、コマンド1つで作れるようにする。

## このユニットで身につけること

- 対象のサーバーの一覧（インベントリ）を書き、Ansibleから接続を確かめる
- プレイブックを書き、パッケージの導入、ファイルの配置、サービスの起動を行う
- 同じプレイブックを2回実行し、2回目に変更が0件になること（冪等性）を確かめる
- 実際には変更せずに、何が変わるかだけを先に見る
- 冪等になる書き方と、ならない書き方の違いを観察する
- 値（ポート番号、パスワードなど）を変数に切り出す
- 検証環境を壊して作り直し、同じ手順で元に戻せることを確かめる

## キーワード

- **構成管理**：サーバーの「あるべき状態」をコードに書き、道具にその状態へそろえさせること
- **Ansible**：構成管理の道具の1つ。対象のサーバーにSSHでつないで作業する。対象の側に、専用の常駐プログラムは要らない
- **インベントリ**：対象のサーバーの一覧を書いたファイル
- **プレイブック**：「どのサーバーに、何をするか」をYAML形式で書いたファイル
- **タスクとモジュール**：タスクは作業の1項目。モジュールは、タスクの中で呼ぶ部品（パッケージを入れる、ファイルを置く、など）
- **冪等性（べきとうせい）**：何回実行しても、結果が同じになる性質。すでにあるべき状態なら、何もしない
- **ファクト**：Ansibleが、対象のサーバーから自動で集める情報（OS、メモリ、IPアドレスなど）
- **`become`**：対象のサーバーの上で、`sudo` を使って権限を上げる指定
- **YAML**：字下げで構造を表す、設定ファイルの書式（O5のcomposeファイルと同じ）

## 平日に読むもの

- Ansibleの公式ドキュメントの「Getting started」（インベントリ、プレイブックの最初の例）、「YAML Syntax」、「Playbook Keywords」を、オフラインで読めるように保存する
- 平日のうちに Ansible を入れ（`sudo apt install -y ansible`）、`ansible --version` と `ansible-doc -l | wc -l` が動くことを確かめる。**モジュールの説明は、`ansible-doc <モジュール名>` でオフラインで引ける。** AIなしデーは、これが主な資料になる
- `ansible-doc ansible.builtin.copy` を、試しに1つ読んでおく。説明、パラメータの一覧、末尾の例、の順に並んでいる
- **平日のうちに、検証環境を用意する**（下の「準備」）

## 準備

検証環境は、壊してよい、もう1台のUbuntu。次のどちらかを、平日に用意する。

- 2台目のVM（Limaなら別のインスタンス、WSL2なら別のディストリビューション、Linuxなら手元の仮想化ソフト）。**こちらを勧める**
- `sshd` を動かしたコンテナ。ただし、コンテナの中でさらにDockerを動かすのは難しい。こちらを選んだ場合、課題8〜10（Dockerの導入とcomposeの起動）は、自分のUbuntu自身を対象（`localhost`）にして行う

どちらの場合も、F7で作ったSSH鍵で、パスワードなしで `ssh` できるようにしておく。`~/.ssh/config` に、`o6-target` という別名で登録する。インベントリやメモには、この別名を書く（実際のIPアドレスは書かない。例が必要なときは `192.0.2.10` や `target.test` を使う）。

```sh
mkdir -p ~/sandbox/o6
cd ~/sandbox/o6
ssh o6-target 'cat /etc/os-release; python3 --version'
```

プレイブック、インベントリ、メモは、リポジトリの `drills/infra/O06-ansible/` に置く。

## 課題

1. インベントリを書き、`ansible-inventory` で、Ansibleがどう解釈したかを表示する（`ansible-inventory --help`）。`ansible` コマンドで、`ping` モジュールを全対象に実行する。このモジュールは、F8の `ping` コマンドと同じことをしているか。`ansible-doc` で確かめる
2. `ansible` コマンドで、`command` モジュールを使って対象の上で `uptime` を実行する。次に `setup` モジュールを実行し、集まったファクトの中から、OSのバージョン、メモリの量、IPアドレスを探す。O1の `sysinfo.sh` で集めた情報と比べる
3. 最初のプレイブックを書く。対象に、`tree` パッケージを入れるだけのもの。パッケージを入れるモジュールは、`ansible-doc -l` の一覧から探す。権限が足りないというエラーが出たら、「Playbook Keywords」で `become` を調べる。実行結果の最後の `PLAY RECAP` の、`ok`、`changed`、`failed` は、それぞれ何を数えているか
4. **観察**：同じプレイブックを、もう一度実行する。`changed` の数は、1回目とどう変わったか。`ssh` で入って `tree` を手で消してから実行すると、どうなるか。「手順を実行する」と「状態をそろえる」の違いを、自分の言葉で書く
5. `ansible-playbook --help` で、「構文だけを検査する」「実際には変更せず、変わる点だけを報告する」「ファイルの差分を表示する」オプションを探して、それぞれ試す。本番のサーバーに対して実行する前に、どれを使うべきか
6. ファイルを配置する。手元のテキストファイルを、対象の `/opt/o6/` の下に、持ち主とパーミッションを指定して置く（ディレクトリを作るモジュールと、ファイルを置くモジュールを探す）。手元のファイルを1文字変えて、差分を表示するオプション付きで実行する
7. **観察**：`command` モジュールで `touch /opt/o6/marker` を実行するタスクを書き、2回実行する。2回目の `changed` は、いくつか。同じことを、ファイルを扱う専用のモジュールで書いた場合は、どうか。`ansible-doc ansible.builtin.command` で、`command` を冪等に近づけるためのパラメータを探す
8. ポート番号やディレクトリ名を、変数に切り出す。変数をどこに書けるか（プレイブックの中、別のファイル、コマンドライン）を、保存したドキュメントで調べる。ファイルの中身に変数を埋め込むには、どのモジュールを使うか。パスワードのような値は、どう扱うべきか（ここではダミーの値でよい。コミットするファイルに、本物の値を書かない）
9. 対象に Docker と compose を入れ、サービスを起動し、自動起動を有効にするタスクを書く。F10で、自分が手で行った手順を思い出し、1つずつタスクに置き換える。サービスを操作するモジュールを探す
10. O4の `api:step3` のイメージは、自分のマシンにしかない。対象へ、どうやって届けるかを決める（`docker save --help` と `docker load --help`。O7で詳しく扱う）。「すでに対象にイメージがあるなら、何もしない」ようにするには、どうすればよいか
11. **本題**：O5のcomposeファイル、リバースプロキシの設定、`.env` に当たるファイルを対象に配置し、`docker compose up -d` まで行うプレイブックを完成させる。Docker関連のモジュールが手元にあるかは、`ansible-doc -l` を `grep` して確かめる。なければ `command` モジュールでよいが、課題7で学んだ方法で、2回目に `changed` にならないようにする。対象の上で、リバースプロキシ経由の `curl` が成功することを確かめる
12. **本題**：検証環境を、まっさらに作り直す（VMを消して作り直す。できなければ、Dockerと `/opt/o6` を手で消す）。プレイブックを1回実行するだけで、課題11と同じ状態になることを確かめる。続けてもう1回実行し、`PLAY RECAP` が `changed=0` になることを確かめる

### 発展（任意）

- プレイブックを、役割ごとのファイル（ロール）に分ける。保存したドキュメントで「Roles」を調べる
- `ansible-vault --help` を読み、パスワードの入った変数ファイルを暗号化する
- O2で作った systemd のサービス（バイナリ、ユニットファイル、専用ユーザー）を、Ansibleで配置する
- OpenTofu（インフラの構成をコードで書く道具）の公式ドキュメントの入門を読み、Ansibleとの役割の違い（何を管理する道具か、状態をどこに覚えているか）を `explain.md` に書く。プロバイダの取得にネットワークが要るので、試すなら平日に取得しておく

## 詰まりやすいところ

- 対象につながらない（`UNREACHABLE`）→ まず、Ansibleを使わずに `ssh o6-target` でつながるかを確かめる。つながるなら、インベントリに書いた名前と、接続するユーザーを疑う
- `sudo` のパスワードを求められて止まる、または失敗する → 対象の上で `sudo -l` を実行し、O1で読んだ `sudoers` の設定を思い出す。`ansible-playbook --help` で、`become` のパスワードを尋ねさせるオプションを探す
- YAMLの構文エラーが、書いた覚えのない行で出る → 字下げにタブが混ざっていないか、`:` のあとに空白があるか、値に `:` や `{` が含まれていないか
- モジュールが見つからないというエラー → `ansible-doc -l` に、その名前があるか。名前は、完全な形（`ansible.builtin.〜`）で書いたか
- 2回目の実行で、`changed` が0にならない → どのタスクが `changed` かを出力で特定し、そのタスクが「状態」を書いているか、「操作」を書いているかを考える
- Dockerのグループに入れたのに、対象の上で `docker` が権限エラーになる → F10と同じ理由を疑う。Ansibleの1回の接続の中で、グループの変更はいつ反映されるか

## 完了条件の確かめ方

課題12を、そのまま実行する。

- まっさらな検証環境に対して、`ansible-playbook` を1回実行するだけで、リバースプロキシ経由の `curl`（POST と GET）が成功する
- 続けて2回目を実行し、`PLAY RECAP` が `changed=0`、`failed=0`
- 1回目と2回目の `PLAY RECAP` を、`notes.md` に貼る

## 残すもの

- インベントリ（別名だけを書いたもの）、プレイブック、変数のファイル（値はダミー）
- 課題4と課題7の観察の記録、1回目と2回目の `PLAY RECAP`（`notes.md`）
- 検証環境の作り方と、消し方の手順（`target-setup.md`）

コマンドを試す場所は `~/sandbox/o6`。プレイブックとメモは、リポジトリの中のこのディレクトリに、AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
