## ねらい

「つながらない」「遅い」「だんだん重くなる」という症状から、動いているプロセスを外から観察して、原因にたどり着けるようになる。閉域の現場では、エラーメッセージを検索することも、AIにログを貼ることもできない。頼れるのは、OSに最初から入っている調査ツールと、Goに付いてくるプロファイラだけになる。

## このユニットで身につけること

- `ss` で、どのプロセスがどのポートで待ち受け、誰とつながっているかを調べる
- `lsof` で、プロセスが開いているファイルと接続を調べる
- `strace` で、プロセスがOSに何を頼んでいるか（システムコール）を観察する
- Goの `pprof` で、CPUを使っている関数と、増え続けている goroutine を見つける
- 症状 → 仮説 → 道具で確認 → 記録、の順で調査を進める
- 調査の経過を、あとから他人が追える形で書き残す

## キーワード

- **ソケット**：ネットワーク通信の出入り口。`ss` は、この一覧を見せるコマンド
- **ソケットの状態**：`LISTEN`（待ち受け中）、`ESTAB`（接続中）、`TIME-WAIT`、`CLOSE-WAIT` など。接続がどの段階にあるかを表す
- **ファイルディスクリプタ（FD）**：プロセスが開いているファイルや接続に付く番号。1つのプロセスが持てる数には上限がある
- **システムコール**：プログラムがOSに仕事（ファイルを開く、通信するなど）を頼む呼び出し
- **プロファイル**：プログラムが、どこで時間やメモリを使っているかを記録したもの
- **`pprof`**：Goに標準で付いているプロファイラ。`net/http/pprof` でHTTP経由で取り出し、`go tool pprof` で読む
- **goroutine リーク**：終わるはずの goroutine が終わらずに、増え続けること（G15、G20）
- **仮説**：「原因は〜ではないか」という見立て。道具を使う前に、必ず言葉にする

## 課題

1. `ss -tlnp` を実行し、自分のAPI、`sshd`、PostgreSQL（`pg-offgrid`）の行を見つける。`-t`、`-l`、`-n`、`-p` のそれぞれを外すと、出力はどう変わるか。`sudo` を付けた場合と付けない場合で、どこが違うか
2. `curl` でAPIを呼んだ直後に、`ss -tan` を実行する。`ESTAB` と `TIME-WAIT` の行を探す。`TIME-WAIT` は、接続のどちら側に残るか。APIとPostgreSQLの間の接続は、何本あるか。その本数は、何で決まっているか（G17）
3. APIを起動したまま、同じポートでもう1つAPIを起動する。どんなエラーが出るか。そのポートを使っているプロセスを、`ss` と `lsof -i` のそれぞれで見つける
4. `lsof -p <APIのPID>` の出力を読む。`FD`、`TYPE`、`NAME` の列は何を表すか。`cwd`、`txt`、数字に `u` や `r` が付いたものは、それぞれ何か。`/proc/<PID>/fd` を `ls -l` した結果と見比べる。1つのプロセスが開けるファイルの上限は、どこで分かるか（`/proc/<PID>/limits`）
5. `strace cat /etc/hostname` と、存在しないファイルに対する `strace cat` を比べる。ファイルを開くシステムコールの、戻り値はどう違うか。`man strace` で、特定のシステムコールだけに絞るオプション、結果をファイルに書き出すオプションを探す
6. 動いているAPIに、`sudo strace -p <PID>` でつなぐ。何も表示されない、またはごく一部しか表示されない場合は、Goのプログラムが複数のスレッドで動いていることを思い出し、`man strace` で、スレッドや子プロセスも追うオプションを探す。`curl` を1回投げ、リクエストの受信と、DBとのやり取りに当たる行を見つける。`man strace` で、システムコールごとの回数と時間を集計するオプションを探して試す
7. APIに `pprof` の入口を付ける。`go doc net/http/pprof` を読み、自分で作った `ServeMux`（G12）の場合に、どう登録すればよいかを調べる。この入口を、外から誰でも見られる状態にしてはいけないのは、なぜか。ブラウザか `curl` で `/debug/pprof/` を開き、どんな種類のプロファイルがあるかを書き出す
8. `for` ループで `curl` を数百回投げながら（F5）、`go tool pprof` でCPUプロファイルを30秒取る。対話モードの `top` と `list <関数名>` を試す。`flat` と `cum` の違いは何か。`/debug/pprof/goroutine?debug=2` を開き、今いる goroutine の数と、それぞれが何を待っているかを読む
9. **本題（その1）**：`fault1` を調査する。進め方は下のとおり。1問につき40分で打ち切る
   - `README.md` の手順で症状を再現し、見たままを記録する
   - **道具を使う前に**、仮説を2つ以上書く
   - 最初の30分は、ソースコードを読まない。外からの観察（`ss`、`lsof`、`strace`、`pprof`、`journalctl`）だけで、仮説を絞る
   - そのあとでコードを読み、原因の行と、「なぜその症状になるのか」を `report-fault1.md` に書く。元のG17のコードとの `diff` は取らない
10. **本題（その2）**：`fault2` を、同じ進め方で調査する
11. **本題（その3）**：`fault3` を、同じ進め方で調査する
12. 3問とも終えたら（または打ち切ったら）、`answers/` の答えを開いて照合する。当たり外れにかかわらず、「どの道具の、どの出力が決め手になったか（なるはずだったか）」を、1問ずつ書く

### 発展（任意）

- 特定できた障害を直し、その障害を検出するテスト、または確認用のスクリプトを1本足す
- `go tool pprof` で、ヒープ（メモリ）のプロファイルを取り、`inuse_space` と `alloc_space` の違いを調べる
- `strace` の時刻を表示するオプションを `man strace` で探し、1回のリクエストの中で、どのシステムコールの間に時間がかかっているかを調べる

## 詰まりやすいところ

- `strace -p` が `Operation not permitted` で失敗する → 他人のプロセスをのぞくのに必要な権限を疑う。`sudo` を付けても駄目な場合は、対象がコンテナの中のプロセスでないかを確かめる
- `strace` をつないでも、待ち状態の1行が出たきり動かない → 見ているのが、プロセスの中の1つのスレッドだけではないかを疑う
- `/debug/pprof/` が404になる → `net/http/pprof` が、どの `ServeMux` に登録されるのかを `go doc` で確かめる
- `go tool pprof` のグラフ表示が、エラーになる → エラーメッセージに出ている、足りないプログラムの名前を確かめる。`top` と `list` は、それがなくても使える
- CPUプロファイルに、自分の関数がほとんど出てこない → プロファイルを取っている間に、負荷がかかっていたか。そもそも、その遅さはCPUを使う種類の遅さか、何かを待っている種類の遅さか
- 仮説なしに道具を順番に試して、時間が溶ける → 症状を1文で書き直し、「この仮説が正しければ、`ss` にはこう見えるはず」を先に書く

## 完了条件の確かめ方

課題12の照合で、3問のうち2問以上、`report-faultN.md` に書いた原因が、答えの原因と一致している。一致したかどうかは、自分で甘く判定しない。迷う場合は、平日にAIに `report-faultN.md` と答えの両方を渡し、「原因の特定として一致しているか」だけを判定させる。

2問に届かなかった場合は、平日に別の3問を作らせて、もう1回やる。
