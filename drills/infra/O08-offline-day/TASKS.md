## ねらい

O7では、部品ごとに「ネットワークなしで動く」ことを確かめた。O8では、ネットワークを本当に切ったまま、AIなしデー1回分の作業（コードの変更、テスト、イメージのビルド、composeでの起動）を最初から最後までやり切る。閉域の現場に入る前の、最後の予行演習にあたる。この日にネットワークがなくて進めなかったことは、失敗ではなく、O7の準備の抜けを教えてくれる収穫になる。

## このユニットで身につけること

- 自分の環境（Lima、WSL2、Linux）で、ネットワークを確実に切り、切れたことを2つの方法で確かめる
- 切った状態で、コードの変更 → テスト → イメージのビルド → `docker compose up` を通す
- ネットワークがないせいで失敗したことを、その場で記録し、O7のチェックリストのどの項目の抜けかに対応付ける
- 「詰まったときの手順」（[AIなしデーの運用](../../../docs/04-ai-free-day.md)）を、Web検索もAIもなしで回す
- ネットワークを戻し、戻ったことを確かめてから、記録をコミットして push する
- 1日の記録をもとに、閉域へ持ち込む一式（O7の `fetch.sh`）を更新する

## キーワード

- **ネットワークインターフェース**：OSがネットワークにつながる出入り口（`eth0` などの名前が付く）。`ip link` で一覧が見える
- **デフォルト経路**：宛先の分からないパケットを送る先。`ip route` で見える。これがないと、外へは出られない
- **名前解決**：`example.com` のような名前をIPアドレスに変えること（F8）。`getent hosts` で試せる
- **ホストとゲスト**：LimaとWSL2では、Ubuntu（ゲスト）のネットワークは、パソコン本体（ホスト）を経由している
- **ループバック**：`127.0.0.1`（`localhost`）。自分自身への通信。外のネットワークを切っても使える
- **ブリッジネットワーク**：Dockerがコンテナどうしをつなぐ、マシンの中だけのネットワーク（O5）
- **ブロッカー**：ネットワークがないせいで進めなかった事柄。この日の主な収穫
- **ツールチェーン**：Go本体（コンパイラ一式）。`go.mod` の指定によっては、`go` コマンドが別のバージョンを取りに行くことがある

## 平日に読むもの

- `man ip-link`、`man ip-route`、`man getent`。`resolvectl` が入っていれば `man resolvectl`（名前解決の設定と状態を見る道具）
- Limaの公式ドキュメントの、ネットワークを扱うページ（VMの通信が、ホストをどう通っているか）。WSL2なら、MicrosoftのWSLの公式ドキュメントの、ネットワークを扱うページ。自分の環境のぶんだけ保存する
- 自分のO7の `checklist.md`、`notes.md`（エラーメッセージの写し）、`fetch.sh`、`verify.sh`
- [AIなしデーの運用](../../../docs/04-ai-free-day.md)の「詰まったときの手順」と「1日のテンプレート」。この日は、Web検索が0回で、ローカルLLMも使わない（ローカルLLMを使う「閉域AIデー」は、別の日に行う）
- **前日に済ませること**：課題1（計画と、切り方のリハーサル）と、`fetch.sh` の実行

リポジトリの `drills/infra/O08-offline-day/` に、`plan.md`（前日に書く）、`blockers.md`（当日、失敗を書く）、`notes.md` を置く。当日の作業の対象は、O4でコピーしたG17のAPI（`vendor/` 入り）、O5のcompose一式、O7で用意した `~/offline-bundle/`。当日は、朝いちばんにネットワークを切り、振り返りが終わるまで戻さない。

## 課題

1. **前日**：`plan.md` に、1日の予定を書く。テンプレートのブロックごとに、「何をするか」「そのために引く資料は何で、それはオフラインで引けるか」を1行ずつ。次も決めておく
   - APIに足す小さな機能を1つ。90分で、ハンドラ・検証・テストまで書ける大きさにする（例：一覧の絞り込みの引数を1つ足す、項目を1つ足してマイグレーションを書く）。当日に設計で迷わないよう、`api.md` の追記まで前日に書く
   - ネットワークを切る手順と、戻す手順を、打つコマンドの形で書く（課題2）。それぞれ5分だけリハーサルし、戻ることまで確かめる
   - 最後に `fetch.sh` を実行し、`~/offline-bundle/` を最新にする
2. 切り方を決める。O7で使った「ホストのWi-Fiを切る／LANケーブルを抜く」が、環境によらずいちばん確実な方法。それに加えて、Ubuntuの中から切る方法も1つ用意する。`man ip-link` で「インターフェースを下ろす」操作を、`man ip-route` で「デフォルト経路を消す」操作を探し、どちらかを選ぶ（どちらも `sudo` が要る）
   - Lima：`limactl shell` はホストからVMへの接続で、VMのネットワークを通っている。切った瞬間に自分のシェルごと落ちないかを、リハーサルで確かめる。落ちる場合は、ホスト側で切る方法にする
   - WSL2：Ubuntuのネットワークは、Windows側の設定を共有している。ホストのWi-Fiを切った場合と、Ubuntuの中で切った場合で、`ip route` の出力はどう違うか
   - Linux：`nmcli` が入っていれば、`man nmcli` で `networking` の節を読む。入っていなければ `ip link` か `ip route`
   - **観察**：「インターフェースを下ろす」と「デフォルト経路を消す」で、`ip a` の表示、`curl http://127.0.0.1:...`（自分のAPI）、`docker ps` は、それぞれどうなるか
3. **当日の朝**：切る前に `getent hosts example.com` と `curl -m 5 -sS https://example.com` が成功することを見てから、ネットワークを切る。両方が失敗すること（終了コードとメッセージ）、`ip route` にデフォルト経路がないことを `notes.md` に時刻付きで書く。続けてO7の `verify.sh` を実行し、全項目 `OK` を確かめる。`NG` があれば、`blockers.md` に書いて先へ進む（この時点で戻さない）
4. 切ったままで、何が使えるかを確かめる。`pg-offgrid` への `psql`、`pkgsite`、DevDocs、`go doc`、`man`、保存したドキュメントの置き場所。この日に引いた資料は、「何を引いたか」「オフラインで引けたか」を、そのつど `notes.md` に1行ずつ足していく
5. **本題（その1）**：課題1で決めた機能を、APIに足す。テスト（G13の形式）を書き、`go vet ./...` と `go test -race -cover ./...` を通す（`-mod=vendor` は、O7で決めた環境変数の指定で効いているはず）。マイグレーションが要るなら、D13の番号付きSQLで `pg-offgrid` に流す。`go build` や `go test` が外へ出ようとしたら、そのメッセージをO7の `notes.md` の写しと見比べる
6. **本題（その2）**：O4のDockerfileで、変更後のAPIのイメージを `api:o8` として作る。ビルドの出力を読み、`FROM` のイメージを取りに行こうとした形跡、依存をダウンロードしようとした形跡がないことを確かめる。大きさは、O4の基準（30MB以下）のままか
7. **本題（その3）**：O5のcompose一式で、APIのイメージを `api:o8` に差し替え、`docker compose down -v` のあと `docker compose up -d` だけで起動する。リバースプロキシ経由の `curl` で、既存のエンドポイントと、今日足した機能が動くことを確かめる。**観察**：外のネットワークが切れているのに、コンテナどうしは通信できる。なぜか（O5のキーワードから考える）
8. 余裕があれば、T10の画面を `npm ci --offline` で再現し、`npx tsc --noEmit --strict`、`npx vitest run`、`npm run build` を通す。`npm` が外へ出ようとした形跡（`package-lock.json` にないもの、インストール時のスクリプト）がないか、出力を読む
9. O9が済んでいれば、O9の `scenario.md` と同じシナリオを、課題7の一式に対して流し、p95をO9の記録と並べて `notes.md` に書く。済んでいなければ、この課題は飛ばし、「未実施（O9前）」と書く
10. 午後の枠（コードリーディングかデバッグドリル）と振り返りも、切ったまま行う。読む対象は、Stage 3で手元にcloneしたOSSか自分の過去のコード。デバッグドリルの答え（`answers/`）は開かない。ブロックごとに、かかった時間と、`plan.md` の予定との差を記録する
11. `blockers.md` に、ネットワークがなくて失敗したことを、起きた順にすべて書く。1件ごとに：時刻、打ったコマンド、エラーメッセージ（先頭の数行をそのまま）、足りなかったもの、O7のチェックリストのどの項目に当たるか（当たらなければ「チェックリストにない」）、その場でどうしたか（回避した、45分で打ち切った）。45分で打ち切ったものは、平日にAIと一緒に解消する詰まりメモにもする
12. 振り返りが終わったら、課題2で決めた手順でネットワークを戻す。`getent hosts example.com` と `curl -m 5 -sS https://example.com` の両方が成功することを確かめてから、`git push` する。**観察**：`git commit` は切ったままでできたが、`git push` はどうだったか。それに気づいたのは、いつか。平日に、`blockers.md` の各件を `fetch.sh` と `checklist.md`（O7）に反映する

### 発展（任意）

- O3の道具で、失敗したコマンドがどのホスト・どのポートへ出ようとしていたかを特定する（`strace` で名前解決や接続のシステムコールを絞る、`ss` で試みた接続を見る）
- ホスト側で切った場合と、Ubuntuの中で切った場合で、失敗のしかた（すぐ失敗する／タイムアウトまで待つ）がどう違うかを、`curl` の終了コードとメッセージで比べ、両方の場合を `verify.sh` の判定が正しく扱えるようにする
- O6の検証環境も切った状態で、O6のプレイブックを流す。自分のマシンどうしのSSHはつながるはず。何が失敗するか（`apt` など）を記録する
- 別の日に、トラックのページの「閉域AIデー」を行う。同じ作業を、ローカルLLMだけを使って進め、クラウドAIとの差（精度、速度、扱える文脈の長さ）を記録する

## 詰まりやすいところ

- 切った瞬間に、Ubuntuに入っているシェルごと切れた → LimaやWSL2では、ホストからの接続自体がVMのネットワークを通っている。まず戻し方を実行して復帰し、切り方を「ホスト側で切る」か「デフォルト経路だけを消す」に変える。これを当日ではなく、前日のリハーサルで見つける
- `go build` や `go test` が、何かを取りに行こうとして失敗する → エラーメッセージを最後まで読み、O7の課題3で写したものと同じかを見る。`go env GOFLAGS GOPROXY GOTOOLCHAIN` の3つと、`go.mod` の `go` の行、`toolchain` の行を確かめる
- `docker build` や `docker compose up` が、イメージを取りに行けずに止まる → `docker images` に、`FROM` と `image:` に書いた名前とタグが、そのとおりに揃っているか。タグが `<none>` になっていないか（O7）。composeのドキュメントで、イメージを取りに行く方針を決める項目を探す
- `npm ci --offline` が止まる → O7と同じ観点（キャッシュの場所の指定、`package-lock.json` が変わっていないか）。エラーに出ているパッケージ名を `blockers.md` に写す
- 切ったつもりなのに、`verify.sh` が「つながっている」と判定する → `ip route` にデフォルト経路が残っていないか。有線と無線の両方がつながっていないか（O7）。LimaやWSL2なら、ホスト側の状態を見る
- 1件で時間が溶けていく → 「詰まったときの手順」に切り替え、45分で打ち切って `blockers.md` に書き、次の課題へ進む。この日は「抜け出せなかったこと」を正確に記録することも成果

## 完了条件の確かめ方

- 朝の記録がある：`getent` と `curl` の両方が失敗したこと（時刻、終了コード）と、`verify.sh` の全項目 `OK`
- ネットワークを戻す前に、次のすべてができている：課題5のテストが `-race` で通る、`api:o8` がビルドできている、`docker compose up -d` だけで起動し、リバースプロキシ経由で新しい機能が動く
- `blockers.md` がある（0件なら「0件」と書く）。45分での打ち切りが2件以下で、`plan.md` のブロックをすべて消化していれば「1日を通して作業を完了できた」とする
- 打ち切りが3件以上、または課題5〜7のどれかが最後までできなかった場合は、平日に `fetch.sh` を直してから、別のAIなしデーでもう1回O8を行う
- Web検索が0回だったことを、振り返りに明記する

## 残すもの

- 課題5の機能追加（コミットは `[no-ai]`）、`api:o8` の大きさ
- 振り返り（`logs/`）。O7の `fetch.sh` と `checklist.md` への反映は、平日にO7のディレクトリで行う
