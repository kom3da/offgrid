## ねらい

これまで、すべてを `postgres`（何でもできる管理者）で操作してきた。実際の運用では、読むだけの人、アプリケーションだけが書ける、という区別が要る。前半で、読み取り専用のロールを作り、「書けない」ことを自分で確かめる。後半で、`pg_dump` でバックアップを取り、別のデータベースに復元し、元と同じ行数であることを確かめる。閉域では、壊れたときに戻せるのは、自分が取ったバックアップだけ。「復元まで試したバックアップ」しか、バックアップとは呼べない。

## このユニットで身につけること

- `\du` で、ロールと属性を読む
- ログインできるロールを作り、そのロールで `psql` に入る
- `GRANT` で、データベース・スキーマ・テーブルの3段階の権限を与える
- 読み取り専用のロールで、`SELECT` はでき、`INSERT`・`UPDATE`・`DELETE`・`CREATE TABLE` は断られることを確かめる
- `REVOKE` で権限を取り消し、あとから作ったテーブルに権限が及ぶかを確かめる
- `pg_dump` でバックアップを取り、`pg_restore` か `psql` で新しいデータベースに復元する
- 復元前後で、全テーブルの行数が一致することを確かめる

## キーワード

- **ロール**：PostgreSQL の「ユーザー」と「グループ」を合わせた呼び名。ログインできるロールが、いわゆるユーザー
- **スーパーユーザー**：すべての権限の検査を素通りするロール。`postgres` がそれ
- **権限（privilege）**：ロールが、あるものに対してできる操作（`SELECT`、`INSERT`、`CONNECT`、`USAGE` など）
- **`GRANT`・`REVOKE`**：権限を与える文と、取り消す文
- **スキーマ**：データベースの中の、テーブルの入れ物。pagila のテーブルは `public` に入っている。テーブルを読むには、その入れ物に入る権限（`USAGE`）も要る
- **`pg_hba.conf`**：「誰が、どこから、どの方法で」つなげるかを決めるファイル。パスワードを聞かれるかどうかは、ここで決まる
- **論理バックアップ**：`pg_dump` が作る、テーブル定義とデータを SQL や専用形式に書き出したもの。別のサーバーにも持っていける
- **`pg_dump`・`pg_restore`**：バックアップを取るコマンドと、専用形式のバックアップを戻すコマンド。どちらもコンテナの中にある

## 課題

1. `\du` で、今あるロールを見る。`postgres` にはどんな属性が付いているか。それぞれの属性の意味を、マニュアルの「ロールの属性」で確かめ、`notes.md` に1行ずつ書く
2. ログインできるロール `d11_reader` を、パスワード付きで作る（`\h CREATE ROLE`。パスワードはダミーでよいが、`notes.md` にも書かない）。`\du` にどう出るか。そのロールで `psql` に入る（`-U d11_reader -d pagila`）。入れたか。パスワードは聞かれたか。聞かれなかったなら、なぜかを `pg_hba.conf` の `local` の行で確かめる（ファイルの場所は `SHOW hba_file;`）
3. `d11_reader` で `film` を `SELECT` する。何が起きるか。エラーメッセージを書き写す。`\dp film` で、権限の欄に何が表示されているかを読む（読み方は `\?` と、`\h GRANT` の末尾の説明）
4. `postgres` に戻り、`d11_reader` に「`pagila` に接続する」「`public` スキーマを使う」「`public` の全テーブルを `SELECT` する」の3つを `GRANT` する。1つずつ与え、そのたびに `d11_reader` 側で `SELECT` を試す。どの権限を与えた時点で読めるようになったか
5. 読み取り専用であることを確かめる。`d11_reader` で、`INSERT`、`UPDATE`、`DELETE`、`CREATE TABLE`、`DROP TABLE`、ビューの作成をそれぞれ試し、すべて断られることと、エラーメッセージを記録する。`BEGIN` の中で試せば、万一通ってしまっても戻せる
6. `postgres` で、新しいテーブルを1つ作る。`d11_reader` はそれを読めるか。予想してから確かめる。読めないなら、「これから作るテーブルにも自動で権限を付ける」方法を、マニュアルの「権限」の節（`ALTER DEFAULT PRIVILEGES`）で探して試す
7. `REVOKE` で、`film` だけ読めないようにする。ほかのテーブルは読めるままか。次に、マニュアルの「定義済みロール」で `pg_read_all_data` を調べ、`d11_reader` にそれを与えると、`film` は読めるようになるか。1つずつ `GRANT` する方法と、定義済みロールを使う方法の違いを `notes.md` に書く
8. `pg_dump` でバックアップを取る。まず、そのまま SQL の形で `backup/pagila.sql` に書き出す（`docker exec pg-offgrid pg_dump -U postgres pagila > backup/pagila.sql`）。ファイルの大きさを見て、`head` と `grep -c` で、テーブル定義の文と、データを入れている文（`INSERT` か、別の文か）がいくつあるかを数える（F3）。次に、`pg_dump --help` で専用形式（custom）で書き出すオプションを探し、`backup/pagila.dump` に書き出す。2つのファイルの大きさを比べる
9. 復元先として `pagila_restore` という空のデータベースを作る。`backup/pagila.dump` を `pg_restore` で復元する（コンテナの中で動かすので、ファイルは `docker exec -i` の標準入力で渡す。読み込み元をファイルではなく標準入力にする方法は `pg_restore --help`）。警告や エラーが出たら、全文を `notes.md` に書き写し、復元が止まったのか、続いたのかを判断する
10. **本題**：復元が正しいことを確かめる。`pagila` と `pagila_restore` の両方で、すべてのテーブルの行数を数え、1つ残らず一致することを確かめる。テーブルの一覧を `\dt` から取り、1テーブルずつ数えてもよいし、シェルのループ（F5）で `psql -tAc` を使ってもよい（`psql --help` で `-t`、`-A`、`-c` の意味を調べる）。結果を `restore-check.md` に、テーブル名・元の行数・復元後の行数の箇条書きで残す。`pg_class` の `reltuples` を使ってはいけない理由も、マニュアルで調べて1行書く
11. `backup/pagila.sql` のほうも、もう1つ別の空のデータベースに `psql` で流して復元する。`ON_ERROR_STOP=1` を付けた場合と付けない場合で、結果はどう違うか。SQL 形式と専用形式で、復元の手順と使えるオプション（テーブルを選んで復元、など）は何が違うか
12. 復元したデータベースで `\du` と `\dp film` を見る。`d11_reader` とその権限は、復元先に付いてきたか。ロールがデータベース単位ではなく、サーバー全体のものであることを、マニュアルの「データベースロール」の冒頭で確かめる。ロールも含めて書き出すコマンドの名前を、「バックアップとリストア」の章で探す

### 発展（任意）

- `pagila_restore` で `film` テーブルを `DROP` し、`backup/pagila.dump` から `film` だけを復元する（`pg_restore --help` でテーブルを選ぶオプションを探す）。外部キーで参照されているテーブルを消そうとすると、何が起きるか
- G17 で作る API 用のロールを想像し、必要な最小の権限（どのテーブルに何を）を `notes.md` に設計する。作るのは G17 でよい
- バックアップを取る `backup.sh` を書く（F5）。ファイル名に日付を入れ、`set -euo pipefail` を付け、`shellcheck` を通す。復元の手順も `README.md` に書く

## 詰まりやすいところ

- `permission denied for schema public` と言われる → テーブルの権限より前に、スキーマの `USAGE` を与えたか。課題4の順番を思い出す
- `GRANT` したのに、まだ読めない → 権限を与えたデータベースと、つないでいるデータベースが同じか。`\c` で今どこにいるかを見る
- `pg_restore` が `already exists` のエラーを大量に出す → 復元先が空か。空でないなら、消して作り直すか、`pg_restore --help` で既存のものを消してから復元するオプションを探す
- `docker exec ... > ファイル` でできたファイルが空、または短い → `docker exec` に `-t` を付けていないか。`-i` と `-t` の意味を `docker exec --help` で確かめる
- 行数を数えるループが、`payment` の親テーブルと子テーブル（D3 の準備で見たもの）で二重に数えている → `\dt` に出るテーブルの種類を見て、どちらを数えるかを決める。元と復元後で同じ決め方なら、比較としては正しい
- パスワードを聞かれて入れない → 課題2で決めたもの。忘れたら `\h ALTER ROLE` で付け直す

## 完了条件の確かめ方

日を改めて、`d11_reader` と `pagila_restore` を消し（`\h DROP ROLE`、`\h DROP DATABASE`。ロールは、権限を先に外さないと消せないことがある）、何も見ずに次を通しで行う。読み取り専用ロールを作り、`SELECT` はでき、`INSERT` は断られることを確かめる → `pg_dump` でバックアップを取り、空のデータベースに復元する → 全テーブルの行数が一致することを `restore-check.md` に記録する。`--help` とマニュアルは見てよい。これができれば完了。
