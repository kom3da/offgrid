## ねらい

長くなった集計を、「まずこれを求め、次にそれを使ってこれを求める」という段階に分けて書けるようになる。1つの巨大な `SELECT` は、書いた本人でも1週間後には読めない。段階ごとに途中結果を確かめながら組み立てる書き方は、閉域で1人で調査するときに、間違いを早く見つけるいちばんの武器になる。あわせて、よく使う問い合わせに名前を付けて残すビューを覚え、ビューが「何を保存しているのか」を実験で確かめる。

## このユニットで身につけること

- `WITH` 句で、問い合わせに名前を付け、外側から使う
- 2つ以上の `WITH` を並べ、後のものから前のものを参照する
- 段階ごとに、途中結果の行数を確かめながら集計を組み立てる
- 同じ問いを、サブクエリの入れ子と `WITH` の両方で書き、読みやすさを比べる
- `CREATE VIEW` で問い合わせに名前を付け、`\dv` と `\d+` で定義を確かめる
- ビューが結果ではなく問い合わせを保存していることを、元のテーブルを変えて確かめる

## キーワード

- **CTE（共通テーブル式）**：`WITH 名前 AS (SELECT ...)` の形で、問い合わせの一部に名前を付けたもの。その文の中だけで使える
- **サブクエリ**：`SELECT` の中に、かっこで書いた別の `SELECT`（D4）。CTE は、これを外に出して名前を付けたもの
- **ビュー**：問い合わせに名前を付けて、テーブルのように `SELECT` できるようにしたもの
- **仮想テーブル**：ビューのこと。データそのものは持たず、使うたびに元のテーブルから計算する
- **依存関係**：ビューが元のテーブルの列に頼っていること。元を変えるときに影響する
- **`CASE` 式**：条件によって値を切り替える式。値を「ランク」などに分類するのに使う
- **検算**：別の方法で出した数字と突き合わせて、集計の正しさを確かめること（D3 の課題12）

## 課題

1. D4 の `monthly-sales-by-store.sql` を読み直し、その問い合わせが「何を求め、次に何を求めているか」を、処理の段階ごとに日本語の箇条書きにする。何段階になったか
2. `\h SELECT` の `WITH` の部分と、マニュアルの節を読む。「`rating` ごとの本数」を CTE にし、外側でその中から本数がいちばん多い `rating` の行だけを取り出す。CTE の名前は、外側のどこに書けるか
3. CTE を2つ並べる。1つ目に「顧客ごとの支払合計」、2つ目に「1つ目を使った、店舗ごとの支払合計の平均」を書き、外側で「自分の店舗の平均より多く払っている顧客」を出す。2つ目の CTE は、1つ目を参照できるか。順番を入れ替えるとどうなるか
4. 課題3と同じ問いを、`FROM` と `WHERE` の中のサブクエリの入れ子で書く。結果の行数は一致するか。どちらが読みやすいか、`notes.md` に理由つきで書く
5. 途中結果を確かめる習慣。課題3の外側の `SELECT` を、`SELECT * FROM 1つ目のCTE名` に一時的に置き換えて実行し、行数を記録する。2つ目の CTE についても同じことをする。各段階の行数が、D4 で予想した行数の感覚と合うか
6. **本題**：段階的な集計を `WITH` で書く。「顧客を支払合計で3つのランク（上位・中位・下位。境目の金額は、支払合計の分布を見て自分で決める）に分け、店舗ごと・ランクごとに、人数と支払合計を出す」。次の手順で組み立て、`customer-rank.sql` に保存する
   - 1段目：顧客ごとの支払合計
   - 2段目：1段目に `CASE` 式でランクの列を足す
   - 3段目：顧客と店舗をつなぎ、店舗とランクでまとめる
   検算として、3段目の支払合計をすべて足した値が `payment` 全体の合計と一致すること、人数をすべて足した値が「支払いが1回以上ある顧客の数」と一致することを確かめる。一致しなければ、どの段階で行が増減したかを、課題5の方法で探す
7. D4 の `monthly-sales-by-store.sql` を、`v_monthly_sales_by_store` という名前のビューにする。`\dv` で一覧に出るか。`\d+ ビュー名` で何が表示されるか。ビューに `WHERE` を付けて、1店舗ぶんだけを取り出す。元の SQL に `ORDER BY` があった場合、ビューに `WHERE` を付けた結果の順番は、保証されているか（D2 の課題6を思い出す）
8. ビューは何を持っているか。「`rating` ごとの本数と平均レンタル料金」のビューを `film` から作る。`BEGIN` してから、`film` の `rental_rate` をすべて 2 倍に `UPDATE` し、ビューを `SELECT` する。値は変わっているか。`ROLLBACK` して、もう一度見る。ビューが保存しているのは、結果か、問い合わせか
9. `SELECT *` の罠。`d10_language` に対して `SELECT *` で作ったビューを用意し、`\d+` で定義を見る。定義に `*` はそのまま残っているか。次に、`d10_language` に列を1つ足す（`\h ALTER TABLE`）。ビューにその列は出てくるか。予想してから確かめる
10. 依存関係。`d10_language` の `name` 列の名前を変える（`\h ALTER TABLE` の `RENAME`）と、課題9のビューはどうなるか。`\d+` の定義はどう変わったか。次に、その列を消そうとすると、何が起きるか。エラーメッセージを書き写し、`CASCADE` が何をするかを `\h ALTER TABLE` で確かめる（実行する前に、消えるものを考える）
11. ビューに書き込めるか。課題9のビュー（1つのテーブルをそのまま写したもの）と、課題8のビュー（集計したもの）のそれぞれに `INSERT` を試す。予想してから確かめ、できる・できないの違いが何から来るかを、`\h CREATE VIEW` の説明で探す
12. `explain.md` に、「サブクエリ・CTE・ビューを、それぞれどんなときに使うか」を、何も見ずに書く。少なくとも、「その場限りの調査」「同じ集計を毎週使う」「途中結果を確かめながら作る」の3つの場面に答える

### 発展（任意）

- `WITH RECURSIVE` を、マニュアルの「`WITH` 問い合わせ」の後半で調べ、1 から 10 までの数を1列に出す。次に、pagila にはない「上司と部下」のような、自分を参照するテーブルを小さく作り、ある人の部下を全部たどる
- マテリアライズドビュー（`\h CREATE MATERIALIZED VIEW`）で課題8の実験をやり直す。結果は普通のビューとどう違うか。最新にするには何が要るか
- `WITH` の中の問い合わせが、外側とまとめて最適化されるかどうかを、`\h SELECT` の `MATERIALIZED` の説明で調べ、`EXPLAIN`（D9）で両方の計画を比べる

## 詰まりやすいところ

- `relation "..." does not exist` と言われ、CTE の名前が使えない → `WITH` を書いた文と同じ文の中で使っているか。文が `;` で切れていないか
- 2つ目の CTE から1つ目が見えない → 書いた順番と、`WITH` の区切りのコンマを確かめる
- 本題の検算が合わない → 段階を1つずつ `SELECT *` で取り出し、行数が増えた・減った段階を探す。JOIN で「多」の側が増えていないか（D4）
- ビューを作れない（`column ... specified more than once`）→ JOIN した結果に同じ名前の列が2つないか。別名を付ける
- ビューを消せない、列を消せない → 依存しているものを `\d+` で確かめる。消す順番を考える
- `CASE` の結果がすべて同じランクになる → 境目の金額と、比較の向き、`CASE` の分岐の順番を確かめる
