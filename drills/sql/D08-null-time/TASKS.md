## ねらい

SQL で、エラーにならないのに結果が間違う原因の上位2つ、NULL と時刻を扱えるようになる。どちらも「動いているように見える」ので、テストでも見逃しやすい。結果を実行前に予想する練習を通して、直感とずれる箇所を、先に体で覚えておく。

## このユニットで身につけること

- NULL を含む比較や計算の結果を、実行前に予想する
- `IS NULL`、`IS NOT NULL`、`COALESCE` を使い分ける
- 集約関数、`ORDER BY`、`NOT IN` が、NULL をどう扱うかを説明する
- `timestamp`（タイムゾーンなし）と `timestamptz`（タイムゾーンつき）の違いを、実験で確かめる
- セッションのタイムゾーン設定を確かめ、切り替える
- 同じ瞬間を、別のタイムゾーンの時刻として表示する

## キーワード

- **NULL**：「値がない・分からない」ことを表す印。0 でも空文字でもない
- **3値論理**：SQL の条件式の結果が、真・偽のほかに「不明（unknown）」を持つこと。`WHERE` は、真の行だけを残す
- **`IS NULL`**：NULL かどうかを調べる、専用の書き方
- **`COALESCE`**：引数を左から見て、最初の NULL でない値を返す関数
- **`timestamptz`**：`timestamp with time zone`。ある「瞬間」を記録する型
- **`timestamp`**：`timestamp without time zone`。カレンダーと時計の「見た目」だけを記録する型
- **UTC**：世界共通の基準の時刻。日本時間（JST）は、UTC より9時間進んでいる
- **`TimeZone` 設定**：セッションごとの、時刻の表示と解釈に使うタイムゾーン

## 課題

1. pagila で、NULL が入っている列を2つ以上探す（`rental` の返却日、`address` の2つ目の住所の列など）。それぞれ、NULL は「何を意味して」入っているか。意味は同じか
2. `rental` で、返却日が NULL の行を、`= NULL` で探した場合と、`IS NULL` で探した場合の行数を比べる。`<> NULL` ではどうか。3つの行数を足すと、全体の行数になるか
3. 真理値表を作る。`true`、`false`、`NULL` の3つの値について、`AND`、`OR`、`NOT` のすべての組み合わせの結果を、予想してから確かめ、`notes.md` に表の形の箇条書きでまとめる。予想と違ったのは、どの組み合わせか
4. **本題**：次の10個の結果を、実行前に `predict.md` に書く。そのあとで実行し、外れたものには理由を書く
   - `NULL = NULL`
   - `NULL <> 1`
   - `1 + NULL`
   - `'abc' || NULL`
   - `NULL AND false`
   - `NULL OR true`
   - `1 IN (1, NULL)`
   - `2 IN (1, NULL)`
   - `2 NOT IN (1, NULL)`
   - `COALESCE(NULL, NULL, 3, 4)`
5. 集約と NULL。`rental` の返却日について、`COUNT(*)`、列を指定した `COUNT`、`MIN`、`MAX` の結果を予想してから確かめる。数値の列に NULL を含む小さなテーブルを自分で作り、`SUM` と `AVG` が NULL をどう扱うかを確かめる。「NULL を 0 として平均する」場合と、結果はどう違うか
6. `rental` を返却日で並べ替えると、NULL の行は先頭に来るか、末尾に来るか。昇順と降順で、それぞれ予想してから確かめる。位置を指定する書き方を、`\h SELECT` で探す
7. `NOT IN` の罠。「貸出が1件もない顧客」を探す問いを、`NOT IN` とサブクエリで書くとする。サブクエリの結果に NULL が1つでも混ざると、全体の結果はどうなるか。小さなテーブルを2つ作って再現する。NULL が混ざっても正しく動く書き方を、D4 で学んだ方法の中から選ぶ
8. `COALESCE` を使い、`rental` の一覧で、返却日が NULL の行には「未返却」と表示する。型が合わないと言われたら、どう直すか
9. `SHOW timezone;` で、今のセッションのタイムゾーンを確かめる。`SELECT now();` の結果と、自分の腕時計の時刻を比べる。ずれているとしたら、何時間か。なぜか
10. 小さなテーブルを作り、`timestamp` の列と `timestamptz` の列を1つずつ持たせる。両方の列に、同じ文字列（タイムゾーンを付けない日時）を入れる。そのあと、セッションのタイムゾーンを `Asia/Tokyo` に変え、もう一度 `SELECT` する。表示が変わったのは、どちらの列か。なぜか。タイムゾーンを変えた状態で、同じ文字列をもう1行入れ、UTC に戻して2行を見比べる
11. 予想してから確かめる：セッションのタイムゾーンが UTC のとき、`2026-01-01 00:00:00+09` を `timestamptz` の列に入れると、どう表示されるか。入れた値と表示された値は、「同じ瞬間」か
12. `AT TIME ZONE` を使って、`rental` の貸出日時を、日本時間と UTC の両方で並べて表示する。「日本時間で、日付ごとの貸出件数」と「UTC で、日付ごとの貸出件数」は、同じになるか。違うとしたら、監視システムの「1日の集計」で、何に気をつけるべきか

### 発展（任意）

- `UNIQUE` 制約のある列に、NULL を2行入れられるか。予想してから確かめる
- `CHECK (x > 0)` のある列に NULL を入れると、どうなるか。D6 の「詰まりやすいところ」の答え合わせをする
- `NULLIF` を `\h` ではなくマニュアルの「条件式」の節で調べ、0 での割り算を避けるのに使ってみる
- 夏時間のあるタイムゾーン（例：`America/New_York`）で、時計が飛ぶ日の前後に `interval '1 day'` と `interval '24 hours'` を足した結果を比べる

## 詰まりやすいところ

- `= NULL` の検索が、エラーにならずに0行を返す → 課題3の真理値表で、その条件式の結果が何になるかを確かめる
- 結果の欄が空で、NULL なのか空文字なのか分からない → 準備の `\pset null` を実行したかを確かめる
- `COALESCE` が、型が合わないというエラーになる → 引数の型をそろえる方法（型の変換）を、マニュアルの「型変換」の話題で探す
- タイムゾーンを変えたのに、次に `psql` に入ると元に戻っている → `SET` が、どの範囲に効く設定かを `\h SET` で確かめる
- `timestamptz` の列に入れた `+09` が、表示では消えている → その型が、内部で何を保存しているかを、マニュアルの「日付/時刻データ型」で確かめる
