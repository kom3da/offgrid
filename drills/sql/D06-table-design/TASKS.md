## ねらい

「どんな列を、どんな型で、どんな制約を付けて持つか」を自分で決め、`CREATE TABLE` に書けるようになる。間違ったデータは、アプリケーションで防ぐより、テーブルの制約で防ぐほうが確実に効く。プログラムにバグがあっても、手で `INSERT` しても、データベースが断ってくれるから。

## このユニットで身につけること

- `text`、`integer`、`numeric`、`timestamptz`、`jsonb` のそれぞれに、何が入り、何が入らないかを試して確かめる
- 主キーを決め、自動で番号を振る列を作る
- 外部キーで、テーブルの間の関係を強制する
- `NOT NULL`、`UNIQUE`、`CHECK`、`DEFAULT` を使い分ける
- 制約に違反する `INSERT` が断られることを、自分で確かめる
- 設計の理由（なぜその型か、なぜその制約か）を文章で残す

## キーワード

- **データ型**：列に入れられる値の種類。型に合わない値は、入れる時点で断られる
- **`numeric`**：桁数を指定できる、誤差のない数。金額などに使う。浮動小数点数（`double precision`）との違いが大事
- **`timestamptz`**：タイムゾーンつきの日時（`timestamp with time zone`）。詳しい性質は D8
- **`jsonb`**：JSON（G11 や F9 で見た、入れ子のデータ形式）を、そのまま入れられる型
- **主キー（`PRIMARY KEY`）**：行を1つに決める列。重複と NULL が許されない
- **外部キー（`FOREIGN KEY`、`REFERENCES`）**：ほかのテーブルに実在する値しか入れられない列
- **`CHECK` 制約**：値が満たすべき条件を、式で書いたもの
- **識別列（identity column）**：追加のたびに、自動で連番が入る列
- **DDL**：テーブルの定義を作る・変える・消す文（`CREATE`、`ALTER`、`DROP`）の総称

## 課題

1. 型の実験用のテーブルを1つ作り、`text`、`integer`、`numeric(10,2)`、`timestamptz`、`jsonb` の列を持たせる。それぞれの列に、合う値と合わない値を入れてみる。断られたときのエラーメッセージを書き写す
   - `integer` の列に、小数、とても大きな数、数字でない文字
   - `numeric(10,2)` の列に、小数点以下が3桁ある数（断られるか、別のことが起きるか）
   - `jsonb` の列に、閉じかっこの足りない JSON
2. `0.1 + 0.2` を、`numeric` として計算した場合と、`double precision` として計算した場合で、結果を比べる。金額を入れる列には、どちらを使うべきか。なぜか
3. pagila の `\d film` と `\d payment` を読み直し、どの列にどの型と制約が使われているかを見る。自分ならこうする、と思う点を1つ挙げる
4. 主キーのあるテーブルを作る。同じ主キーの値を2回入れる、主キーに NULL を入れる、の2つを試す。次に、自動で連番が入る主キーの作り方を、マニュアルの「識別列」の話題で調べて試す。連番の列に、自分で値を指定して入れると、どうなるか
5. 親子の関係にある2つのテーブル（例：部署と社員）を作り、子のテーブルに外部キーを付ける。次のそれぞれで、何が起きるか
   - 親に存在しない値を、子に入れる
   - 子から参照されている親の行を、削除する
   - 外部キーに `ON DELETE` の指定を付けた場合（指定の種類を `\h CREATE TABLE` で探し、2種類を試す）
6. `CHECK` 制約を付ける。「0以上であること」「決まった文字列のどれかであること」「2つの列の大小関係（開始が終了より前）」の3種類を、それぞれ書いて、違反する `INSERT` が断られることを確かめる。制約に名前を付けた場合と付けない場合で、エラーメッセージはどう違うか
7. `NOT NULL` と `DEFAULT` を付けた列に、値を指定せずに `INSERT` すると、どうなるか。`NOT NULL` だけで `DEFAULT` がない場合はどうか
8. `csvstat-output.txt` を見て、「`csvstat` の結果を、実行のたびにデータベースに残す」ために必要な情報を、箇条書きにする。少なくとも、次を含める
   - 実行そのものの情報：いつ実行したか、対象のファイル名、行数、実行時のオプション（オプションは種類が増えるかもしれない）
   - 列ごとの統計：どの実行の、どの列の、どの統計値（件数、最小、最大、平均など、自分の `csvstat` が出すもの）か
9. 課題8の情報を、何枚のテーブルに分けるかを決める。1枚にまとめた場合、同じ値が何度も繰り返される列はどれか。テーブルごとに、列名、型、制約を `design.md` に書く。型と制約の1つ1つに、選んだ理由を1行で付ける
10. **本題**：課題9の設計を `schema.sql` に書く。空の `design` データベースに対して、次の形でエラーなく実行できること

    ```sh
    docker exec -i pg-offgrid psql -U postgres -d design -v ON_ERROR_STOP=1 < schema.sql
    ```

    `schema.sql` は、2回続けて実行してもエラーにならないようにする（先頭で、どうすればよいか）
11. `csvstat-output.txt` の内容を、手で `INSERT` 文に直して `sample-data.sql` に書き、2回ぶんの実行結果を入れる。次に、`violations.sql` に、断られるべき `INSERT` を5つ以上書く（負の行数、存在しない実行を指す統計、同じ実行の同じ列の重複、必須の列が空、など）。1つずつ実行し、すべて断られることを確かめる。断られなかったものがあれば、設計に戻る
12. 「ある実行の、全部の列の統計」を、JOIN を使って1つの結果として表示できることを確かめる

### 発展（任意）

- オプションを `jsonb` の列に入れた場合、その中の特定のキーの値を取り出す方法を、マニュアルの「JSON関数と演算子」の節で探して試す
- 作ったあとのテーブルに、`ALTER TABLE` で列と制約を足す。すでに入っているデータが新しい制約に違反していると、何が起きるか
- `text`、`varchar(n)`、`char(n)` の違いを、マニュアルの「文字型」の節で調べ、長すぎる文字列を入れて比べる

## 詰まりやすいところ

- 外部キーを付けようとしたらエラーになる → 参照される側の列に、主キーか `UNIQUE` があるか、型が同じかを確かめる
- `schema.sql` の2回目の実行が `already exists` で止まる → 作る前に消すか、「なければ作る」書き方を `\h` で探す。消す順番にも注意する
- テーブルを `DROP` しようとすると、ほかのテーブルが依存していると言われる → 外部キーの向きと、消す順番を確かめる
- `CHECK` を付けたのに、違反するはずの値が入ってしまう → その値が NULL でないかを確かめる（NULL と条件式の関係は D8）
- 日時を入れたら、思っていた時刻と違って表示される → 今は記録だけしておく。D8 で扱う

## 完了条件の確かめ方

1. `design` データベースを削除して作り直し、`schema.sql` → `sample-data.sql` の順に、`ON_ERROR_STOP=1` でエラーなく実行できる
2. `violations.sql` の文を1つずつ実行し、5つ以上がすべて断られる
3. `design.md` に、テーブルごとの列・型・制約と、その理由が書いてある。平日にAIに設計のレビューを頼んでよい（修正は自分で行う）

## 残すもの

- `schema.sql`、`sample-data.sql`、`violations.sql`
- `design.md`：設計と理由
- `notes.md`：課題1〜7のエラーメッセージと、分かったこと
- `csvstat-output.txt`（機密や個人情報を含まないこと）

SQL とメモは、リポジトリの中のこのディレクトリに、AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
