## ねらい

100万行のダミーデータを自分で作り、`EXPLAIN (ANALYZE, BUFFERS)` を読んで、「なぜ遅いか」を数字で言えるようになる。そのうえで、与えられた問い合わせのためにインデックスを自分で設計し、前後の時間を記録する。D9 では「インデックスがあると計画が変わる」ことを見た。ここでは、行数の推定と実際のずれ、読んだブロックの数、複数列のインデックスの列の順番まで踏み込む。閉域の現場で「遅い」の相談を受けたとき、これが唯一の調査手段になる。

## このユニットで身につけること

- `generate_series` と `random()` で、要件どおりの分布のダミーデータを100万行作る
- 作業の前に、ホストとコンテナのディスクの空きを確かめる
- `EXPLAIN (ANALYZE, BUFFERS)` の各行から、推定行数と実際の行数、実際の時間、読んだブロック数を読み取る
- 「推定と実際が大きくずれている」ことに気づき、`ANALYZE` で直るかを確かめる
- 与えられた問い合わせに対して、単一列・複数列・部分インデックスのどれを、どの列の順で作るかを決める
- 改善前後の実行時間とブロック数を、同じ条件で測って記録する
- インデックスが書き込みを遅くする分を測り、「作らない」判断もできるようにする

## キーワード

- **`EXPLAIN (ANALYZE, BUFFERS)`**：実際に実行して、各段階の実際の時間・行数と、読み書きしたブロック数を表示する。PostgreSQL 18 では `ANALYZE` だけでもブロック数が出るので、`BUFFERS` を付けた場合と見比べる
- **ブロック（ページ）**：テーブルやインデックスのデータを読み書きする単位。既定は 8KB
- **`shared hit` と `read`**：メモリ上にあったブロックを読んだ数と、ディスクから読んだ数
- **推定行数と実際の行数**：`rows=` の値と、`actual ... rows=` の値。ずれが大きいと、プランナが間違った計画を選ぶ
- **`loops`**：その段階が何回繰り返されたか。`actual` の時間と行数は、1回あたりの平均
- **複数列インデックス**：2つ以上の列を組み合わせたインデックス。先頭の列だけの条件でも効くが、2番目の列だけでは効きにくい
- **部分インデックス**：`WHERE` 付きで、一部の行だけを対象にしたインデックス。小さくできる
- **`\timing`**：`psql` で、各文の実行時間を表示する設定

## 準備

先にディスクの空きを見る。ホストで `df -h`、コンテナの中では `SHOW data_directory;` でデータの置き場所を調べてから `docker exec pg-offgrid df -h その場所`。このユニットのテーブルとインデックスで、合わせて数百 MB 使う。空きが 2GB を切っているなら、先に整理する。

```sh
cd ~/offgrid-log/drills/sql/D14-explain
docker exec -it pg-offgrid psql -U postgres -c 'CREATE DATABASE d14;'
docker exec -it pg-offgrid psql -U postgres -d d14
```

`.sql` ファイルの実行は `-d d14` を付ける。`\timing on` を最初に実行する。時間の記録は `timings.md` に、「問い合わせ、条件（インデックスの有無）、実行時間、`shared hit`/`read`」の箇条書きで残す。

## 課題

1. データ生成の設計。次の要件を満たすテーブル `events` を作り、100万行を入れる SQL を `gen.sql` に書く。D9 の `setup.sql` の形を思い出しつつ、値の作り方はマニュアルの `generate_series` と `random` の説明で調べる（PostgreSQL 18 では `random` に範囲を渡せる。書式はマニュアルで確かめる）
   - `id`：1 から 1,000,000 の連番
   - `occurred_at`（`timestamptz`）：今から過去30日の間にばらつく。連番の順に並んでいなくてよい
   - `host_id`（`integer`）：1 から 200 まで、ほぼ均等
   - `status`（`integer`）：200 がおよそ 90%、404 がおよそ 7%、500 がおよそ 3%
   - `latency_ms`（`integer`）：1 から 5000
   - `path`（`text`）：20種類くらいの文字列のどれか
   - インデックスも主キーも、まだ付けない
   `\timing` で生成にかかった時間、`\dt+` で大きさを記録する。`host_id` と `status` の分布を `GROUP BY` で数え、要件どおりかを確かめる
2. 統計の実験。生成の直後、`ANALYZE` を実行する前に、`host_id` が 42 の行数を `EXPLAIN` で推定させ、`rows=` を記録する。そのあと `ANALYZE events;` を実行して、もう一度出す。推定はどう変わったか。実際の行数と比べる
3. `EXPLAIN (ANALYZE, BUFFERS)` の読み方。`host_id` が 42 の行を全部取り出す問い合わせで実行し、出力の各行について、`notes.md` に次を書き出す：Scan の種類、推定行数、実際の行数、実際の時間、`loops`、`shared hit`、`shared read`。同じ文をもう一度実行すると、`hit` と `read` はどう変わるか。なぜか
4. 調べる対象の問い合わせを決める。次の5つを言葉のとおりに SQL にし、`queries.sql` に番号付きで保存する。それぞれについて、インデックスなしの状態で `EXPLAIN (ANALYZE, BUFFERS)` を実行し、`timings.md` に「改善前」として記録する
   - Q1：ある `host_id` の、ある1時間の間の行
   - Q2：直近24時間の、`status` ごとの件数
   - Q3：ある `host_id` の、最新の10行
   - Q4：直近7日の、`status` が 500 の行
   - Q5：`id` が、ある1つの値の行
5. Q5 のために `id` に主キーを付ける（`\h ALTER TABLE`）。付けるのにかかった時間と、できたインデックスの大きさ（`\di+`）を記録する。Q5 の計画と時間はどう変わったか
6. Q1 と Q3 のためのインデックスを設計する。候補は、`host_id` だけ、`occurred_at` だけ、`(host_id, occurred_at)`、`(occurred_at, host_id)` の4つ。**作る前に**、どれが Q1 と Q3 の両方に効くと思うか、理由つきで `notes.md` に書く。1つずつ作っては測り、消して次を試す。同じ問い合わせは2回以上実行して、2回目以降の数字を使う。予想は当たったか
7. Q3 の計画に `Sort` が出ているか。出ているなら、どのインデックスを作ると消えるか。`LIMIT 10` があるとき、インデックスの並び順がそのまま使えるのはなぜかを、マニュアルの「インデックスと `ORDER BY`」の話題で確かめる
8. Q4 のために、`status` が 500 の行だけを対象にした部分インデックスを作る。`status` 全体のインデックスと、大きさと Q4 の時間を比べる。`status` が 200 の行を探す問い合わせでは、どちらのインデックスも使われるか。使われないなら、なぜか（D9 の選択率）
9. Q2 は、インデックスで速くなるか。`occurred_at` のインデックスがある状態で計画を見る。読んだ行数と、全体の行数の割合はどのくらいか。「速くならない問い合わせ」があることを認め、代わりに何ができるかを考えて `notes.md` に書く（集計結果を別に持つ、など。実装は D15 でよい）
10. **本題**：`index-design.md` を書く。Q1〜Q5 のそれぞれについて、「最終的に残したインデックス」「改善前と改善後の実行時間と `shared hit`/`read`」「なぜそのインデックスにしたか」「試して捨てた候補と、捨てた理由」を書く。改善後は、残したインデックスがすべてある状態で、5つを続けて測り直した数字にする
11. 書き込みの代金。インデックスが全部ある状態で、10万行を追加する時間を測る。次に、主キー以外のインデックスを消して同じ追加を行い、時間を比べる。`\dt+` と `\di+` の合計の大きさは何倍か。「1秒に100行届く監視データ」に、このインデックスの数は妥当かを `index-design.md` の末尾に書く
12. 推定のずれを作る。`host_id` が 1 の行を、`UPDATE` で全部 `host_id` = 2 にする（実行前に行数を数えておく）。すぐに Q1 を `host_id` = 2 で実行し、推定行数と実際の行数を比べる。`ANALYZE` のあとで、もう一度比べる。自動で統計が集められるまでの間に、何が起きうるか

### 発展（任意）

- `EXPLAIN` の出力の見やすい形（`FORMAT` オプション）を `\h EXPLAIN` で調べ、`JSON` 形式で出して `jq`（F9）で実際の時間だけを取り出す
- `path` に前方一致の `LIKE` で検索する問い合わせを足し、B-tree のインデックスが効く場合と効かない場合（`%` の位置）を確かめる
- `latency_ms` が 4000 以上の行を探す問い合わせで、インデックスが使われる境目の値を、しきい値を変えながら探す。`rows=` の推定値と、Seq Scan に切り替わる点の関係を見る
- `work_mem` を `SHOW` で見て、Q2 のような集計で `Sort` や `HashAggregate` がディスクを使っているか（`Disk:` の表示）を確かめる

## 詰まりやすいところ

- 生成が終わらない、またはディスクが足りないというエラーになる → 生成を10万行ずつに分けるか、先に `df -h` を見直す。トランザクションの中で大量に入れているなら、いったん `COMMIT` する
- 分布が要件と違う（500 が 30% ある、など）→ `random()` の結果をどう整数に変えているか（四捨五入か切り捨てか）を、小さい範囲で `SELECT` して確かめる
- 2回測るたびに時間が大きく違う → メモリのキャッシュ（課題3）。`shared read` が 0 に近い状態同士で比べる
- インデックスを作ったのに使われない → D9 の「詰まりやすいところ」を読み直す。`occurred_at` に `now()` からの引き算を書いていないか（列側に関数がかかっていないか）
- `EXPLAIN (ANALYZE)` を `UPDATE` に使って、本当に実行された → `BEGIN` と `ROLLBACK` で包む（D9）
- `\timing` の時間と `Execution Time` が大きく違う → 結果の行数が多いとき、転送と表示の時間が入る。比べるなら `Execution Time`

## 完了条件の確かめ方

`index-design.md` に、Q1〜Q5 のすべてについて、改善前と改善後の実行時間と `shared hit`/`read` が、同じ条件で測った数字として記録されており、Q1・Q3・Q5 は改善後が改善前の 10 分の 1 以下になっていれば完了。加えて、日を改めて、`EXPLAIN (ANALYZE, BUFFERS)` の出力を1つ選び、何も見ずに各行の意味（推定と実際、時間、`loops`、ブロック数）を `explain.md` に書き、平日にAIに採点を頼む（[`prompts/grade-explain.md`](../../../prompts/grade-explain.md)）。
