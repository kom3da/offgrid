## ねらい

`WHERE` で行を絞るとき、データベースが「全部の行を順に読む」のか「索引で目的の行に飛ぶ」のかを、実行計画から読み取れるようになる。閉域の現場で「この画面が遅い」と言われたとき、頼れるのは `EXPLAIN` の出力だけ。インデックスを作れば速くなる、と信じるのではなく、計画が変わったことと、時間が縮んだことを、自分の目で確かめる癖を付ける。

## このユニットで身につけること

- `EXPLAIN` の出力の先頭行を読み、Seq Scan と Index Scan を見分ける
- `CREATE INDEX` でインデックスを作り、`\d` と `\di` で確かめ、`DROP INDEX` で消す
- `EXPLAIN (ANALYZE)` で、推定と実際の行数・時間を並べて読む
- インデックスがあるのに使われない場合（小さいテーブル、当たる行が多すぎる、列に関数をかけている）を、実験で再現する
- インデックスを作る前後で、同じ問い合わせの時間を測って記録する
- インデックスが、書き込みと容量の面で「ただではない」ことを数字で確かめる

## キーワード

- **インデックス（索引）**：列の値から行の場所を引くための、テーブルとは別に持つデータ。本の巻末の索引と同じ
- **実行計画**：データベースが、その問い合わせを「どの順に、どの方法で」処理するかの手順書。`EXPLAIN` で見る
- **プランナ**：実行計画を選ぶ部品。統計情報をもとに、いちばん安いと見積もった計画を選ぶ
- **Seq Scan（シーケンシャルスキャン）**：テーブルの行を先頭から全部読む方法
- **Index Scan**：インデックスで行の場所を引き、その行だけを読む方法
- **Bitmap Heap Scan**：インデックスで当たる行の場所を先に集め、まとめて読む方法。当たる行がそこそこ多いときに出る
- **コスト**：計画の「安さ」の見積もり。単位は秒ではない。`cost=開始..終了` の2つの数字で出る
- **選択率**：条件に当たる行が、全体のどれくらいの割合か。少ないほどインデックスが効く
- **統計情報と `ANALYZE`**：プランナが見積もりに使う、列の値の分布などの情報。`ANALYZE` で集め直す

## 準備

pagila のテーブルは小さいので、インデックスの効き目を見るための大きめのテーブルを1つ作る。作るのが目的ではないので、次をそのまま `setup.sql` に保存して実行してよい（100万行。数秒から数十秒かかる）。

```sh
cd ~/offgrid-log/drills/sql/D09-index
docker exec -it pg-offgrid psql -U postgres -d pagila
```

```sql
CREATE TABLE d09_events AS
  SELECT g AS id,
         (g % 1000) + 1 AS customer_id,
         timestamptz '2026-01-01 00:00:00+00' + g * interval '1 second' AS occurred_at,
         (ARRAY['ok', 'warn', 'error'])[1 + (random() * 2)::int] AS status,
         md5(g::text) AS note
  FROM generate_series(1, 1000000) AS g;
ANALYZE d09_events;
```

`\timing on` を実行しておくと、各文の実行時間が表示される。`.sql` ファイルの実行は D2 と同じ形（`-d pagila` を付ける）。やり直したくなったら `DROP TABLE d09_events;` のあと、もう一度 `setup.sql` を流す。

## 課題

1. `\d film` の末尾の `Indexes:` を読む。どの列にインデックスがあるか。主キーには、自分で作らなくてもインデックスが付いているか（`\d actor` と `\d film_actor` でも確かめる）。`\di` で pagila のインデックスの一覧を出し、数を数える
2. `EXPLAIN` で、`film` を `film_id` で1件探す問い合わせと、`title` で1件探す問い合わせの計画を出す。それぞれの先頭行の Scan の種類は何か。`cost=` の2つの数字と `rows=` は、何を表すか（「EXPLAINの利用」の説明で確かめる）。`rows=` は、実際の行数と一致しているか
3. `title` にインデックスを作り、課題2をもう一度実行する。計画は変わったか。`\d film` の表示はどう変わったか。確かめたら、そのインデックスは消す（`\h DROP INDEX`）
4. 小さいテーブルの実験。`language`（数行しかない）の `name` にインデックスを作り、`name` で1件探す計画を出す。インデックスは使われるか。`SET enable_seqscan = off;` にしてから同じ計画を出すと、どう変わるか。`cost=` の数字を、設定の前後で比べる（設定を元に戻す方法を `\h RESET` で調べる）。なぜプランナは、インデックスがあるのに使わなかったのか
5. `d09_events` にはまだインデックスが1つもない。次の3つの問い合わせについて、`EXPLAIN (ANALYZE)` を実行し、Scan の種類、`rows=` の推定値、`actual` の行数と時間を `notes.md` に記録する
   - `id` が 500000 の行
   - `customer_id` が 42 の行
   - `status` が error の行の件数
6. `id` にインデックスを作り、課題5の1つ目をもう一度実行する。Scan の種類と時間は、どう変わったか。何倍速くなったか。`\di+` で、そのインデックスの大きさを見る。テーブルの大きさ（`\dt+`）と比べる
7. `customer_id` にインデックスを作り、課題5の2つ目をもう一度実行する。Scan の種類は、課題6と同じか。Bitmap Heap Scan が出たら、それが何をしているかをマニュアルで探し、一言で `notes.md` に書く
8. `status` にインデックスを作り、課題5の3つ目をもう一度実行する。インデックスは使われたか。error の行が全体の何％あるかを数え、使われた・使われなかった理由を、選択率という言葉で説明する。次に、`status` が error で、かつ `customer_id` が 42 の行を探すと、どちらのインデックスが使われるか。予想してから確かめる
9. 列に関数をかける実験。`occurred_at` にインデックスを作ってから、次の2つの計画を比べる
   - `occurred_at` を日付に変換した値が、ある1日と等しい行
   - `occurred_at` が、その日の 0 時以上、翌日の 0 時未満の行
   結果の行数は同じはずなのに、計画と時間はどう違うか。なぜか。同じく、`status` を大文字にした値が `ERROR` と等しい行を探すと、課題8のインデックスは使われるか
10. **本題**：`index-report.md` を書く。「インデックスが使われる問い合わせ」「テーブルが小さくて使われない問い合わせ」「列に関数をかけていて使われない問い合わせ」を1つずつ選び、それぞれについて、インデックスなしとありの `EXPLAIN (ANALYZE)` の先頭行と実行時間を並べ、計画が変わった（または変わらなかった）理由を1行で書く
11. インデックスの代金。インデックスが3つ以上ある状態で、`d09_events` に10万行を追加する時間を測る（`setup.sql` の書き方をまねて、`id` が重ならないように `INSERT ... SELECT` する）。次に、インデックスをすべて消してから同じ追加を行い、時間を比べる。`\dt+` と `\di+` の合計の大きさは、インデックスありで何倍になっているか
12. 統計の実験。`d09_events` を消して作り直し、`ANALYZE` を実行する前に、課題5の2つ目の `EXPLAIN` を出す。`rows=` の推定値は、`ANALYZE` の後と比べてどう違うか（先に自動で統計が集められていて、違いが出ないこともある。その場合は、マニュアルの「日常的なバキューム作業」で、自動で統計を集める仕組みの名前だけ確かめる）

### 発展（任意）

- `customer_id` と `status` の2列のインデックスを、列の順番を入れ替えて2通り作り、課題8の後半の問い合わせで、どちらが使われるか、片方の列だけの条件ではどうかを比べる
- `SELECT` する列を `customer_id` だけにすると、計画に Index Only Scan が出るか。出たとき、Index Scan と何が違うかをマニュアルの「インデックスオンリースキャン」の話題で確かめる
- `WHERE status = 'error'` の行だけを対象にした部分インデックスを、マニュアルの「部分インデックス」の話題で調べて作り、大きさと計画を比べる

## 詰まりやすいところ

- インデックスを作ったのに Seq Scan のまま → テーブルの行数、条件に当たる行の割合、列に関数や型変換をかけていないか、`ANALYZE` 済みか、の順に疑う
- `EXPLAIN (ANALYZE)` を `UPDATE` や `DELETE` に使ったら、本当に実行されてしまった → `ANALYZE` を付けると実際に実行される。`BEGIN` と `ROLLBACK` で包む（D5）
- 同じ問い合わせなのに、2回目のほうがずっと速い → 1回目に読んだデータが、メモリに残っている。比べるときは、それぞれ2回以上実行して、2回目以降の時間を使う
- `\timing` の時間と、`EXPLAIN (ANALYZE)` の時間が合わない → それぞれが「何を含めて」測っているか（結果の転送、表示）を考える
- 計画がいつもと違う気がする → `SET enable_seqscan = off;` を戻し忘れていないか。`SHOW enable_seqscan;` で確かめる
- `setup.sql` が終わらない → 100万行なので、数十秒は正常。`docker stats` で CPU が動いていれば待つ

## 完了条件の確かめ方

日を改めて、`d09_events` を作り直し（`setup.sql` は見てよい）、何も見ずに次を通しで行う。インデックスなしで `customer_id` の検索の計画を出し、Seq Scan であることを読み取る → インデックスを作る → 同じ計画を出し、Index Scan（または Bitmap Heap Scan）に変わったことを読み取る → 前後の実行時間を記録する。これができれば完了。あわせて、「インデックスがあっても使われないのは、どんなときか」を3つ、何も見ずに `explain.md` に書き、平日にAIに採点を頼む（[`prompts/grade-explain.md`](../../../prompts/grade-explain.md)）。
