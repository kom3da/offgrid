## ねらい

テーブルの定義は、一度作って終わりではない。列が増え、制約が変わり、名前が変わる。その変更を「番号付きの SQL ファイル」として積み上げ、順に適用すれば、空のデータベースからいつでも同じ形を作り直せるようにする。閉域では、本番のデータベースの形を、誰かの記憶ではなく、リポジトリの中のファイルだけから再現できなければならない。G17 の API のスキーマを題材に、データが入ったままのテーブルを変える手順と、「どこまで適用したか」を記録する仕組みを、自分で設計する。

## このユニットで身につけること

- スキーマの変更を、番号付きの `.sql` ファイルに1つずつ分けて書く
- ファイルを名前順に適用するシェルスクリプトを書き、途中で失敗したら止める
- データが入っているテーブルに、列や制約を足す変更を、既存の行がどうなるかを予想してから適用する
- 動いている API の側から、スキーマ変更の影響（列の追加、名前の変更）を観察する
- 1つのファイルの途中で失敗したとき、前半が残るか残らないかを、トランザクションの有無で確かめる
- 「どのファイルまで適用したか」を記録するテーブルを設計し、2回実行しても安全にする
- 空のデータベースから全部を再構築し、G17 の結合テストが通ることを確かめる

## キーワード

- **マイグレーション**：スキーマ（テーブルの定義）を、ある版から次の版へ変える手順。1つの変更を1つのファイルにする
- **スキーマの版**：「どのマイグレーションまで適用した状態か」。番号で表す
- **冪等（べきとう）**：同じ操作を何回行っても、結果が同じになる性質（G12）。「2回実行しても壊れない」に必要
- **前方（up）と後方（down）**：変更を進める向きと、戻す向き。戻す SQL は、書けないことがある
- **DDL のトランザクション**：PostgreSQL では `CREATE TABLE` や `ALTER TABLE` も `BEGIN`／`ROLLBACK` で戻せる。戻せないデータベースもある
- **`ALTER TABLE`**：既存のテーブルの列・制約・名前を変える文（D6 の発展で少し触れた）
- **適用の記録**：どのファイルを、いつ適用したかを保存するテーブル。名前は自分で決める

## 平日に読むもの

- 『達人に学ぶDB設計徹底指南書』の、物理設計と、テーブル定義の変更に関わる話題
- PostgreSQL公式マニュアル（PDF）の、「データ定義」の章の「テーブルの変更」の節、リファレンスの `ALTER TABLE`（`psql` の中の `\h ALTER TABLE`）、`psql` のリファレンス（コンテナの中の `psql --help` でも、オプションの一覧は読める）
- G17 で書いた自分の `schema.sql` と、ストアの SQL（列名をどう書いているか）

## 準備

```sh
cd ~/offgrid-log/drills/sql/D13-migrations
mkdir -p migrations
docker exec -it pg-offgrid psql -U postgres -c 'CREATE DATABASE d13_fresh;'
```

`migrations/` の中に、番号付きの `.sql` を置く。G17 の API とテストは `../../go/G17-database` にあるものを使い、接続先は環境変数（`DATABASE_URL`、`TEST_DATABASE_URL`）で切り替える。`.sql` ファイルの実行は、これまでと同じ `docker exec -i pg-offgrid psql -U postgres -d DB名 -v ON_ERROR_STOP=1 < ファイル` の形。`g17` データベースには、G17 で入れたデータが残っているはずなので、消さずに使う（残っていなければ、`curl` で何件か登録しておく）。

## 課題

1. G17 の `schema.sql` を読み直す。「なければ作る」の形で、2回流せるようになっているはず。その書き方だと、「あとから列を1つ足す」変更をどう表すか。表せないなら、なぜか。`notes.md` に書く
2. `migrations/0001_create_items.sql` を書く。中身は G17 の `items` と同じ定義でよい。ファイル名の決まり（4桁の番号、アンダースコア、内容を表す短い英語）を `README.md` に書く。空の `d13_fresh` に流し、`\d items` で確かめる
3. `migrate.sh` を書く（F5）。引数にデータベース名を取り、`migrations/*.sql` を名前の順に1つずつ `ON_ERROR_STOP=1` で流す。1つでも失敗したら、そこで止まり、終了コードを 0 以外にする。どのファイルを流したかを1行ずつ表示する。`shellcheck` を通す。`d13_fresh` を消して作り直し、`./migrate.sh d13_fresh` で 0001 が適用されることを確かめる
4. 名前の順の罠。`migrations/` に `9_test.sql` と `10_test.sql` という空のファイルを一時的に置き、`migrate.sh` がどちらを先に流すかを見る。4桁でゼロ埋めする理由を `README.md` に書き、2つのファイルは消す
5. `migrations/0002_add_created_at.sql` を書く。`items` に、登録日時の列（`timestamptz`、`NOT NULL`、既定値は現在時刻）を足す。**先に予想する**：`g17` にはすでに行がある。既存の行のこの列には、何が入るか。`./migrate.sh g17` で適用し、`SELECT` で確かめる。次に、`BEGIN` の中で、既定値なしの `NOT NULL` の列を足そうとすると、何が起きるか（確かめたら `ROLLBACK`）
6. 動いている API への影響。G17 の API を `g17` に向けて起動したまま、課題5を適用した（または、もう一度 0001 の状態から再現する）とき、API は動き続けたか。`GET /items` のレスポンスに、新しい列は出るか。出ないなら、なぜか。ストアの SQL に `SELECT *` を使っている箇所があるなら、列が増えたときに何が起きうるかを `go doc github.com/jackc/pgx/v5.Rows.Scan` の説明から考える
7. 名前の変更。`d13_fresh` に向けた API を起動し、`migrations/0003_rename_value.sql` で `value` 列の名前を `amount` に変える（`\h ALTER TABLE` の `RENAME`）。API の各エンドポイントを `curl` で呼ぶと、何が返るか。エラーの内容はログに出ているか。「データベースを先に変えるか、コードを先に変えるか、両方同時にできないなら、どういう順で変えれば止まらないか」を `notes.md` に書く。試したあと、0003 は「名前の変更」ではなく「列の追加」など、API を壊さない変更に書き直す
8. 途中で失敗するファイル。`migrations/` の外に、2つの文を持つ `broken.sql` を作る。1つ目は正しい `ALTER TABLE`、2つ目はわざと失敗する文（存在しないテーブルへの `ALTER` など）。`d13_fresh` に流し、1つ目の変更が残っているかを `\d items` で確かめる。次に、`psql --help` で「ファイル全体を1つのトランザクションで実行する」オプションを探し、それを付けて（1つ目の変更を戻してから）もう一度流す。結果はどう違うか。`migrate.sh` に、そのオプションを付けるべきか
9. 2回実行するとどうなるか。`./migrate.sh d13_fresh` を続けて2回実行する。2回目に何が起きるか。エラーメッセージを書き写す。これを防ぐには、「どのファイルを適用したか」をデータベース自身に記録しておく必要がある。次を設計して `README.md` に書く
   - 記録テーブルの名前、列（ファイル名か番号か、適用した日時、ほかに要るもの）、制約
   - 記録テーブル自体は、誰がいつ作るか（最初のマイグレーションか、`migrate.sh` か）
   - 適用と記録は、同じトランザクションで行うべきか。分かれていると何が起きうるか
10. **本題**：課題9の設計を `migrate.sh` に組み込む。記録にあるファイルは飛ばし、ないファイルだけを順に適用して記録する。次をすべて満たすことを確かめ、手順を `README.md` に書く
    - `d13_fresh` を消して作り直し、`./migrate.sh d13_fresh` の1回で、`0001` から最後まで全部が適用される
    - 続けてもう1回実行すると、何も適用されず、終了コードは 0
    - 新しいファイル `0004_...` を足して実行すると、それだけが適用される
    - `TEST_DATABASE_URL` を `d13_fresh` に向けて、G17 の結合テストが通る（`go test -race ./...`）
11. 適用済みのファイルを書き換えたら、どうなるか。`0002` の中身を少し変えて `./migrate.sh d13_fresh` を実行し、変更が反映されるかを見る。「一度適用したファイルは変えない。直したければ、次の番号で直す」という決まりを `README.md` に書き、なぜかを1行で添える
12. 卒業制作の `capstone/migrations/` に持ち込む決まりを `notes.md` にまとめる。番号は連番か日時か（2人が同時に作ったらどうなるか）、1ファイルに何個の変更を入れるか、データを書き換える文（`UPDATE`）をマイグレーションに入れてよいか

### 発展（任意）

- `0002` を戻す `down` の SQL を書く。列を消す変更は、戻したときにデータが戻るか。戻せない変更にはどんなものがあるか
- 記録テーブルに、ファイルの内容のハッシュ（`sha256sum`）も保存し、適用済みのファイルが書き換えられていたら `migrate.sh` が警告するようにする
- `CREATE INDEX CONCURRENTLY`（D9 の発展で調べたかもしれない）を、課題8のトランザクションのオプション付きで流すと、何が起きるか。`\h CREATE INDEX` の説明で理由を探す

## 詰まりやすいところ

- `migrate.sh` が、ファイルの並びを日本語ロケールや大文字小文字で変な順に流す → `LC_ALL` と `sort` の関係（F3）。ファイル名は数字とアルファベット小文字だけにする
- `docker exec -i ... < "$f"` をループの中で使うと、2つ目以降のファイルが流れない → ループの標準入力を `docker exec` が食べていないか。`for` と `while read` の違い（F5）
- `ON_ERROR_STOP=1` を付けたのに、スクリプトが止まらない → `psql` の終了コードを、スクリプトが見ているか。`set -euo pipefail` とパイプの関係
- 2回目の実行で `already exists` になる → 課題9。記録の仕組みができていない、または記録の前に落ちている
- 結合テストが `SKIP` になる → `TEST_DATABASE_URL` が正しく渡っているか。G17 の「詰まりやすいところ」を読み直す
- `NOT NULL` の列を足せない（`contains null values`）→ 課題5。既存の行に何を入れるかを、既定値か、先に `UPDATE` するかで決める

## 完了条件の確かめ方

日を改めて、`d13_fresh` を消して作り直し、`./migrate.sh d13_fresh` を1回実行する。全ファイルが順に適用され、2回目の実行では何も起きず、G17 の結合テストが `d13_fresh` に対して通れば完了。加えて、「適用済みのファイルを書き換えてはいけない理由」と「記録テーブルに何を入れ、なぜか」を、何も見ずに `explain.md` に書き、平日にAIに採点を頼む（[`prompts/grade-explain.md`](../../../prompts/grade-explain.md)）。

## 残すもの

- `migrations/0001_...sql` 以降のファイル一式、`migrate.sh`
- `README.md`：ファイル名の決まり、記録テーブルの設計、再構築の手順
- `notes.md`：課題1、5〜9、11、12の観察と考察
- `explain.md`

SQL、スクリプト、メモは、リポジトリの中のこのディレクトリに、AI機能を切ったエディタで書く。この `TASKS.md` はカリキュラムの一部なので、書き換えない。
