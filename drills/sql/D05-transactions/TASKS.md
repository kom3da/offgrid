## ねらい

データを追加・変更・削除できるようになり、間違えたときに元に戻せるようになる。`WHERE` を付け忘れた `UPDATE` は、一瞬で全部の行を書き換える。閉域の現場では、壊したデータを直してくれる人も道具もないことがある。「`BEGIN` してから触り、確かめてから `COMMIT` する」手順を、手が覚えるまで練習する。

## このユニットで身につけること

- `INSERT` で、1行、複数行、一部の列だけを指定して追加する
- `UPDATE` と `DELETE` を、先に同じ `WHERE` の `SELECT` で対象を確かめてから実行する
- `BEGIN`、`COMMIT`、`ROLLBACK` で、複数の変更をひとまとまりにする
- 誤った更新を `ROLLBACK` で取り消し、取り消せたことを確かめる
- 2つの `psql` を同時に開き、確定していない変更が、ほかの接続からどう見えるかを観察する
- トランザクションの途中でエラーが起きたとき、何が起きるかを知る

## キーワード

- **`INSERT`・`UPDATE`・`DELETE`**：行の追加・変更・削除
- **トランザクション**：「全部成功するか、全部なかったことにするか」のどちらかになる、ひとまとまりの処理
- **`BEGIN`**：トランザクションを始める
- **`COMMIT`**：トランザクションの中の変更を確定する。確定したあとは `ROLLBACK` で戻せない
- **`ROLLBACK`**：トランザクションの中の変更を、すべて取り消す
- **自動コミット**：`BEGIN` を書かずに実行した文は、1文ごとにすぐ確定される、という `psql` の既定の動き
- **セッション**：データベースへの1本の接続。`psql` を2つ開けば、セッションは2つ
- **ロック**：ある行を変更中のセッションが、ほかのセッションからの同じ行への変更を待たせる仕組み
- **分離（isolation）**：同時に動くトランザクションが、お互いの途中経過を見ないようにする性質

## 課題

1. `d05_film` に、架空の映画を1行追加する。次に、3行をまとめて1つの文で追加する。次に、タイトルと `film_id` だけを指定して追加する。指定しなかった列には、何が入るか
2. 課題1で追加した映画のうち1本の、レンタル料金を変更する。**先に、同じ `WHERE` を付けた `SELECT` で、対象が1行だけであることを確かめてから** `UPDATE` する。実行後に表示される `UPDATE 1` の数字は、何を表すか
3. 課題1で追加した映画を1本削除する。ここでも、先に `SELECT` で対象を確かめる。`DELETE` と `DROP TABLE` は、何が違うか
4. `BEGIN` を実行してから、`rating` が G の映画のレンタル料金を、すべて 0 にする。`SELECT` で変わったことを確かめてから、`ROLLBACK` する。もう一度 `SELECT` して、元に戻ったことを確かめる
5. 同じ変更を、今度は `COMMIT` で確定する。そのあとで `ROLLBACK` を実行すると、何が起きるか。値は戻るか。表示されるメッセージを書き写す
6. **本題**：誤更新を再現して戻す。`BEGIN` のあと、「1本の映画だけ長さを変えるつもりで、`WHERE` を付け忘れた `UPDATE`」を実行する。表示された行数を見て、間違いに気づく。長さの平均や、値の種類の数を `SELECT` して、被害の大きさを確かめる。`ROLLBACK` し、元に戻ったことを、実行前に記録しておいた数字（長さの合計など）と比べて確かめる。手順と数字を `rollback-log.md` に残す
7. 課題6と同じ誤更新を、`BEGIN` なしで実行した場合、戻す方法はあるか。試す前に考えを書き、それから実際に試す（`d05_film` は作り直せる）
8. ターミナルを2つ開き、両方で `psql` に入る（セッションA、セッションB）。Aで `BEGIN` し、ある映画のタイトルを変更する。まだ `COMMIT` しない。この時点で、AとBのそれぞれから、その映画を `SELECT` する。見える値は、どう違うか。Aで `COMMIT` したあと、Bからもう一度見ると、どうなるか
9. 課題8と同じ状況（Aが変更して、まだ `COMMIT` していない）で、Bから同じ行を `UPDATE` しようとすると、Bの画面はどうなるか。Aで `COMMIT` した瞬間、または `ROLLBACK` した瞬間に、Bで何が起きるか。Bから別の行を `UPDATE` する場合はどうか
10. `BEGIN` のあと、正しい `UPDATE` を1つ実行し、次に、わざとエラーになる文（存在しない列の名前など）を実行する。そのあとで `SELECT` を実行すると、何が表示されるか。ここで `COMMIT` と打つと、何が起きるか。最初の `UPDATE` は、どうなったか
11. 後片付け：`BEGIN` のまま放置したセッションが残っていないことを確かめ、`d05_film` を削除する。プロンプトの記号（`=#` と `=*#` など）が何を表しているかを調べておく

### 発展（任意）

- `SAVEPOINT` を `\h` で調べ、トランザクションの途中まで戻す操作を試す
- `UPDATE` や `DELETE` の文の最後に `RETURNING` を付けると、何が返るか。誤更新の防止に、どう使えるか
- `\set AUTOCOMMIT off` にすると、`psql` の動きはどう変わるか。便利な点と、危ない点を書く

## 詰まりやすいところ

- どの文を実行しても `current transaction is aborted` と言われる → 今のトランザクションの中で、前にエラーが起きていないかを確かめる。抜け方を `\h ROLLBACK` で確かめる
- セッションBが固まって、プロンプトが戻らない → 故障ではない。セッションAの状態（`BEGIN` したままの変更がないか）を確かめる
- `ROLLBACK` したのに、値が戻っていない → `BEGIN` を実行したか、途中で `COMMIT` していないかを、画面の履歴でさかのぼって確かめる
- `WARNING: there is no transaction in progress` と出る → 今、トランザクションの中にいるかどうかを、プロンプトの記号で確かめる
- `INSERT` で、列の数と値の数が合わないと言われる → 列の並びを明示して書いているかを確かめる
