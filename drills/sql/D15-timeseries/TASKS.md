## ねらい

監視データは、「時刻とともに増え続け、新しいものはよく読まれ、古いものはまとめて捨てる」という、ほかのデータとは違う性質を持つ。この性質に合わせて、テーブルを時刻で区切り（パーティション）、時刻の並びに強い小さなインデックス（BRIN）を付け、`date_trunc` で1分ごとにまとめ、古い区切りごと落として捨てる。1000万行の計測データで、卒業制作 watchdeck の中心になる問い合わせ「直近1時間の、サーバーごとの1分平均」を、1秒以内で出せるところまで作る。

## このユニットで身につけること

- 時刻の範囲で分割された（パーティションされた）テーブルを作り、区切りごとの子テーブルを用意する
- 1000万行のダミーの計測データを、ディスクと時間を見積もってから生成する
- 行がどの子テーブルに入ったかを確かめ、時刻の条件で読まれる子テーブルが減る（枝刈り）ことを `EXPLAIN` で見る
- BRIN と B-tree のインデックスを、大きさ・作る時間・問い合わせの時間で比べる
- `date_trunc` で1分ごとに丸めて、サーバーごとの平均を出す
- 古いデータを `DELETE` する場合と、子テーブルごと落とす場合の、時間と容量の違いを測る
- 保持期間と区切りの粒度を、watchdeck 向けに設計して記録する

## キーワード

- **時系列データ**：時刻を主な軸に持つ、追記が中心のデータ。計測値、ログ、取引履歴など
- **パーティション（テーブルの分割）**：1つの大きなテーブルを、見た目は1つのまま、内部で複数の子テーブルに分けること。ここでは時刻の範囲で分ける（`PARTITION BY RANGE`）
- **パーティションキー**：分ける基準の列。ここでは計測時刻
- **枝刈り（partition pruning）**：`WHERE` の条件から、読む必要のない子テーブルを飛ばすこと
- **BRIN**：Block Range INdex。ブロックのかたまりごとに「最小値と最大値」だけを持つ、とても小さいインデックス。時刻順に追記されるデータに向く
- **`date_trunc`**：日時を、分・時・日などの単位に切り捨てる関数（D3 で月に使った）
- **保持期間**：データを何日持つか。過ぎたものは捨てる
- **`DETACH PARTITION`**：子テーブルを親から切り離す。切り離したあとは、普通のテーブルとして消せる

## 平日に読むもの

- PostgreSQL公式マニュアル（PDF）の、「データ定義」の章の「テーブルのパーティショニング」の節（宣言的パーティショニング、パーティションの追加と削除、枝刈り）、「インデックス」の章の「インデックスの種類」の BRIN の部分、「日付/時刻関数と演算子」の `date_trunc` の説明
- `psql` の中の `\h CREATE TABLE`（`PARTITION BY` と `PARTITION OF` の部分）、`\h ALTER TABLE`（`DETACH PARTITION`）、`\h CREATE INDEX`（`USING brin`）
- D14 の `index-design.md` と `timings.md`（測り方を同じにする）

## 準備

**先にディスクと時間を見積もる。** 1000万行のテーブルで 1GB 前後、インデックスを足すと合わせて 2GB を超えることがある。D14 と同じ方法で、ホストとコンテナの空きを確かめ、3GB 以上の余裕がなければ D14 の `d14` を消してから始める。生成には数分から十数分かかるので、1回目の枠の前半に始める。

```sh
cd ~/offgrid-log/drills/sql/D15-timeseries
docker exec -it pg-offgrid psql -U postgres -c 'CREATE DATABASE d15;'
docker exec -it pg-offgrid psql -U postgres -d d15
```

`.sql` ファイルの実行は `-d d15` を付ける。`\timing on` を最初に実行し、計測は D14 と同じ形で `timings.md` に残す。

## 課題

1. pagila の `\d+ payment`（D3 の準備で見たもの）を読み直す。`Partition key` に何が書かれているか。子テーブルはいくつあり、どんな範囲か。`BEGIN` の中で、どの子テーブルの範囲にも入らない日付の支払いを `INSERT` しようとすると、何が起きるか。エラーを書き写して `ROLLBACK` する
2. 計測テーブルを設計する。要件は次のとおり。列名と型を `design.md` に書き、`schema.sql` に書く
   - `server_id`（整数）、`time`（`timestamptz`）、`cpu`、`mem`、`disk`（それぞれ使用率で 0 から 100 の数）
   - `time` の範囲で分割し、1日ごとに子テーブルを持つ。今日を含む過去14日分の子テーブルを、まず手で作る（子テーブルの名前は、日付が読み取れるものにする）
   - 主キーを `(server_id, time)` にする。**先に試す**：主キーを `server_id` だけにしようとすると何が起きるか。エラーメッセージから、パーティションされたテーブルの制約の決まりをマニュアルで探す
3. 行の行き先。範囲の違う日時の行を3行手で入れ、それぞれがどの子テーブルに入ったかを確かめる（子テーブルを1つずつ `SELECT` してもよいし、マニュアルの「システム列」で `tableoid` を調べてもよい）。子テーブルのない日付を入れると、課題1と同じことが起きるか
4. ダミーデータの生成。次の要件で `gen.sql` を書き、1000万行前後を入れる。1日分ずつ（子テーブル1つずつ）に分けて `INSERT` し、1日ぶんの所要時間を測ってから残りを流す
   - サーバーは 100 台（`server_id` は 1 から 100）
   - 10 秒間隔で、直近 12 日分（100 台 × 1日 8,640 行 × 12 日 ≒ 1,037 万行）。最新の行が、生成した時点の「今」に近くなるようにする
   - `cpu`、`mem`、`disk` は、それぞれ 0 から 100 の間でばらつく。`disk` はサーバーごとに、ゆっくり増える形にできればなおよい（必須ではない）
   生成の合計時間、`\dt+`（子テーブルを含む）の合計の大きさを記録する。親テーブルの大きさが 0 と表示されるなら、なぜか
5. 枝刈りを見る。「ある1日の、あるサーバーの行数」を数える問い合わせの `EXPLAIN` を、`time` の条件ありとなしで出す。計画に出てくる子テーブルの数はどう違うか。次に、`time` の条件を `now()` からの引き算で書いた場合と、日時をそのまま書いた場合で、計画の見た目（`Subplans Removed` のような表示が出るか）はどう違うか。マニュアルの「パーティションの枝刈り」で、計画時と実行時の違いを読む
6. 本題の問い合わせ（改善前）：「直近1時間の、サーバーごとの1分平均」を書く。1行が「サーバー、1分の始まりの時刻、`cpu`・`mem`・`disk` それぞれの平均」で、サーバーと時刻の順に並ぶ。「今」は、データの最新の `time` を基準にしてよい（生成から時間がたつと、`now()` 基準では0行になる。その理由も書く）。行数を先に予想し（サーバー 100 台 × 60 分）、`EXPLAIN (ANALYZE, BUFFERS)` の `Execution Time` を「主キーだけの状態」として記録する。`per-minute.sql` に保存する
7. BRIN を試す。`time` に BRIN のインデックスを作る（親に作ると子にどう付くか、`\d+` で見る）。作るのにかかった時間と大きさを、`(server_id, time)` の主キーのインデックスと比べる。課題6の時間はどう変わったか。次に、`time` だけの B-tree も作り、3つの状態（主キーのみ・BRIN・B-tree）で課題6を測り、`timings.md` に並べる
8. BRIN が効かない形。1日分の子テーブルを1つ選び、その中身を時刻の順をばらばらにして入れ直す（`ORDER BY random()` で `INSERT ... SELECT`）。同じ範囲の問い合わせで、BRIN の計画と時間はどう変わったか。なぜか。BRIN が向くのは、どういう入れ方をするデータか
9. 古いデータを捨てる。2つの方法を、時間と容量で比べる
   - いちばん古い日の行を `DELETE` する。かかった時間と、`\dt+` の大きさが減ったかを見る。減っていないなら、マニュアルの「日常的なバキューム作業」で、空きが戻る仕組みと `VACUUM` を読む
   - その次に古い日の子テーブルを、親から切り離してから `DROP TABLE` する。かかった時間と、大きさの変化を見る
   監視データを毎日捨てるなら、どちらを使うか。子テーブルを落とすには、「1日ごとに区切ってある」ことが前提になる。区切りが月単位だったらどうなるか
10. 明日の子テーブルは、誰が作るか。翌日の行を入れようとして失敗する状況を課題3で見た。「毎日、先の日付の子テーブルを作っておく」処理を、SQL で書けるか（`\h CREATE TABLE` の `PARTITION OF` を、日付を変えて実行するだけでよい）。これを自動で動かす方法（cron は O1、アプリの起動時に行うなら C3）を `design.md` に書く。作り忘れたとき、agent からのデータはどうなるか
11. **本題**：課題7の結果から、残すインデックスを決め、課題6を最終状態で3回測る。`Execution Time` が 1 秒以内になっていることを確かめ、`timings.md` に記録する。1秒を切らない場合は、計画のどこで時間を使っているか（子テーブルの数、`Sort`、`HashAggregate`）を読み、`design.md` に原因と対策の案を書く
12. watchdeck の設計を `design.md` にまとめる。保持期間（何日）、区切りの粒度（日・週）、インデックス、古いデータの捨て方、子テーブルの作り方、1分平均を毎回計算するか別テーブルに持つか。それぞれ、このユニットで測った数字を根拠に書く

### 発展（任意）

- 1分平均を別テーブル（`metrics_1m`）に持ち、1時間分をまとめて `INSERT ... SELECT` する。元の行を捨てても、グラフに要る情報は残るか。卒業制作の発展「古いデータを集約する」の準備になる
- 「直近1時間の、サーバーごとの1分平均」に、前の1分との差（D12 の `LAG`）と、CPU の高い順の順位（D12）を足す
- 区切りを1日ではなく1週間にした版を作り、課題6と課題9の数字を比べる。区切りが粗いと得なこと、損なことは何か
- `EXPLAIN` で、100 台分の集計に `Parallel` の付く段階が出るかを見て、マニュアルの「パラレル問い合わせ」の冒頭を読む

## 詰まりやすいところ

- `no partition of relation ... found for row` と言われる → 課題1と3。入れようとした時刻を含む子テーブルがあるか。範囲の終わり側が「含む」か「含まない」かを `\h CREATE TABLE` で確かめる
- 生成が途中で止まった、または遅すぎる → 1日分ずつ入れているか。1つのトランザクションに全部入れていないか。ディスクの空きを見直す
- 課題6が 0 行になる → 「今」の基準（データの最新時刻か `now()` か）。データの最新の `time` を先に `SELECT` する
- 枝刈りが起きず、全部の子テーブルが計画に出る → `time` の列に関数や型変換をかけていないか（D9 の課題9）。条件の型が `timestamptz` と合っているか
- BRIN を作ったのに計画が変わらない、または遅くなった → `EXPLAIN` の `Bitmap Heap Scan` の行を読み、「読んでから捨てた行（`Rows Removed by Index Recheck`）」が多くないかを見る。課題8の状態になっていないか
- `DROP TABLE` した子テーブルの分だけ、`\dt+` の合計が減ったのに、`df -h` の空きが増えない → ファイルの解放とディスクの空きの関係を、慌てずに `docker exec pg-offgrid df -h` でもう一度見る。少し待ってから見る

## 完了条件の確かめ方

`per-minute.sql` を、最終状態のインデックスで `EXPLAIN (ANALYZE, BUFFERS)` 付きで3回実行し、3回とも `Execution Time` が 1 秒以内で、行数が予想（サーバー数 × 60）どおりであれば完了。`timings.md` に、主キーのみ・BRIN・B-tree の3状態の時間と、`DELETE` と子テーブルの削除の時間が記録されていること。加えて、日を改めて、「パーティションで得られること」「BRIN が向くデータと向かないデータ」「古いデータを `DELETE` ではなく子テーブルごと落とす理由」を、何も見ずに `explain.md` に書き、平日にAIに採点を頼む（[`prompts/grade-explain.md`](../../../prompts/grade-explain.md)）。
