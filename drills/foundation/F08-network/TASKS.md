## ねらい

「つながらない」ときに、名前解決・経路・ポートのどこで止まっているかを、自分で切り分けられるようになる。閉域のネットワークでは、DNSが独自だったり、限られたポートしか通らなかったりするのがふつうで、外の世界の「とりあえず再起動」は通用しない。`ip`、`ping`、`ss`、`dig` の4つで、今どこまで届いているかを言えるようにする。

## このユニットで身につけること

- 自分のIPアドレスと、外へ出るときの最初の中継先を調べる
- `ping` の出力から、届いているか、どのくらいかかっているかを読む
- どのポートで何が待ち受けているか、今どこと接続しているかを `ss` で見る
- TCPとUDPの違いを、自分の言葉で言う
- `dig` で名前からIPアドレスを引き、応答の各部分を読む
- 名前解決に関わる設定ファイル（`/etc/hosts`、`/etc/resolv.conf`）の役割を区別する
- 名前解決からTCP接続までの流れを、コマンドの出力を証拠にして説明する

## キーワード

分からない語は、まず `man コマンド名` で調べる。

- **IPアドレス**：ネットワーク上の機器（正確には、その接続口）に付く番号
- **ループバック（`lo`、`127.0.0.1`）**：自分自身を指す、特別な接続口とアドレス
- **デフォルトゲートウェイ**：自分のネットワークの外へ出るときに、最初にパケットを渡す相手
- **ポート**：1台の中で、どのプログラム宛ての通信かを区別する番号
- **TCP・UDP**：届いたことを確かめながら送る方式と、確かめずに送りっぱなしにする方式
- **待ち受け（LISTEN）・接続済み（ESTAB）**：サーバーが接続を待っている状態と、つながっている状態
- **DNS**：名前（`example.com`）から、IPアドレスを調べる仕組み
- **レコード**：DNSに登録されている情報の1件。A、AAAA、CNAMEなどの種類がある
- **パケット**：ネットワークを流れる、データの小さなまとまり

## 課題

1. `ip addr` で、自分のIPアドレスを見つける。`lo` とは何か。`ip route` で、デフォルトゲートウェイ（外へ出るときの最初の中継先）を見つける。プライベートIPアドレスの範囲を調べ、自分のアドレスがそこに入っているかを確かめる
2. `ping -c 4 example.com` を実行し、出力の各部分（応答時間、損失率）を読む。`ping -c 4 127.0.0.1` と比べて、応答時間はどのくらい違うか。`ping -c 4 192.0.2.1` は、どうなるか。応答がないとき、考えられる原因を3つ挙げる
3. ポート：片方のシェルで `python3 -m http.server 8000` を動かす。もう片方で `ss -ltn` を実行し、8000番で待ち受けている行を見つける。`-l`、`-t`、`-n` は、それぞれ何の指定か。`ss -ltnp` では、何が増えるか。`curl 127.0.0.1:8000` でつながることを確かめる
4. 接続を見る：`curl` は一瞬で終わってしまうので、つながっている最中の状態は、`nc 127.0.0.1 8000`（何も打たずに待つ。終了は Ctrl+C）でつないだままにして、もう1つのシェルから `ss -tn` で見る。8000番に関係する行は、何行あるか。それぞれの行の、左右のアドレスとポートは何を表すか。8000ではないほうのポート番号は、誰が決めたものか
5. `/etc/services` から、22、53、80、443、5432番が何のためのポートかを調べる。同じ8000番で、サーバーをもう1つ起動しようとすると、どうなるか
6. TCPとUDPの違いを3点、表にまとめる。`ss -lun` で、UDPで待ち受けているものを見る
7. DNS：`dig example.com` を実行し、ANSWER SECTION を読む。A、AAAA、CNAME、MX、NS の各レコードが何かを調べ、`dig example.com MX` のように、種類を指定して引く。`dig +short` も試す。`dig @1.1.1.1 example.com` の `@` は、何を指定しているか。出力の終わりのほうにある `SERVER` の行は、`@` を付けたときと付けないときで、どう変わるか
8. `/etc/resolv.conf` と `/etc/hosts` の役割を調べる。`/etc/hosts` に `127.0.0.1 myserver.test` を足し、`curl myserver.test:8000` がつながることを確かめる（編集には `sudo` と、F6で選んだエディタを使う。終わったら元に戻す）
9. 課題8で `myserver.test` を足した状態で、`dig myserver.test` と `getent hosts myserver.test` の結果を比べる。なぜ違うか。`curl` は、どちらと同じ調べ方をしていると言えるか
10. `dig +trace example.com` の出力を読む。名前がどの順にたどられていくかを、箇条書きにする（ネットワークによっては失敗する。そのときは `dig +trace @1.1.1.1 example.com` を試し、それでもだめなら飛ばしてよい）
11. **本題**：「名前を引いてから、TCPでつながるまで」の証拠を集める。`dig example.com` の出力を保存する。次に `nc example.com 80` でつないだままにし、もう1つのシェルで `ss -tn` の出力を保存する。`ss` に出ている相手のアドレスは、`dig` のどのレコードの値と一致するか。ポート番号は、どこから来たか
12. 応用：`sudo tcpdump -n -i lo port 8000` を動かしたまま、別のシェルから `curl 127.0.0.1:8000` を実行する（`localhost` だと、先にIPv6でつなごうとして、余計なパケットが混ざることがある）。最初の3つのパケットの `Flags` を読み、TCPの接続がどう始まるかを確かめる（`tcpdump` がなければ `sudo apt install tcpdump`）

### 発展（任意）

- `/etc/resolv.conf` に書かれているアドレスが `127.0.0.53` だったら、その先にいる本当のDNSサーバーを `resolvectl status` で探す
- `man nc` で、UDPを使うオプションと、待ち受ける側になるオプションを探す。2つのシェルの間で、文字を送り合う。待ち受ける側を起動せずに送ると、TCPとUDPで何が違うか
- 自分のIPアドレスの後ろに付いている `/24` のような数は、何を表すか。F1の2進数で考える
- `tracepath example.com` で、途中の中継先を見る（入っていなければ、飛ばしてよい）

## 詰まりやすいところ

- `ss -tn` に、8000番の行が出ない → その瞬間に、接続がまだ続いているかを考える。課題4の `nc` のやり方を読み直す
- `Address already in use` → `ss -ltnp` で、そのポートを誰が使っているかを調べる（止め方はF4）
- `ping` は返ってこないのに、`curl` ではつながる → `ping` が使う通信の種類（ICMP）を調べる。仮想マシンや社内のネットワークでは、それだけが止められていることがある
- `/etc/hosts` を保存できない → `ls -l /etc/hosts` で、誰が書き込めるファイルかを確かめる（F2）
- `/etc/hosts` を変えたのに、`dig` の結果が変わらない → 課題9で確かめる
- `tcpdump` に、予想より多くのパケットが出て読めない → つなぎ先を `127.0.0.1` と書いたかを確かめる。まず `Flags` の部分だけを拾って読む
