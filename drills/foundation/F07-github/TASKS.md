## ねらい

SSH鍵でGitHubにつなぎ、ブランチを使った開発の流れ（分岐、マージ、コンフリクトの解消、プルリクエスト）を一通り経験する。コンフリクトは、AIに任せると「なんとなく直った」で終わりやすいが、閉域の現場では、印の意味を自分で読んで、どちらを残すかを決めるしかない。SSH鍵も、サーバーに入る手段として、GitHub以外のあらゆる場面で使う。

## このユニットで身につけること

- SSHの鍵の組を作り、公開鍵だけを相手に登録して接続する
- `~/.ssh/config` に、接続先ごとの設定を書く
- ブランチを作り、切り替え、マージし、履歴の形を `git log --graph` で読む
- コンフリクトの印を読み、手で解消してコミットする
- `merge` と `rebase` の履歴の違いを、自分の出力で示す
- ブランチをGitHubに送り、プルリクエストを作る
- コミットの取り消し方を、push済みかどうかで使い分ける

## キーワード

分からない語は、`man git-コマンド名`、`man ssh-keygen`、`man ssh_config` で調べる。

- **公開鍵・秘密鍵**：2つで1組の鍵。公開鍵は相手に渡し、秘密鍵は自分の手元だけに置く
- **リモート（`origin`）**：手元のリポジトリが覚えている、やり取りの相手。`origin` は、その名前として最初に付くもの
- **ブランチ**：コミットの列に付けた、動く名前。作業を枝分かれさせるのに使う
- **マージ**：別のブランチの変更を、今のブランチに取り込むこと
- **fast-forward**：枝分かれがなく、ブランチの名前を先へ進めるだけで済むマージ
- **コンフリクト**：同じ場所が別々に変更されていて、Gitが自動では取り込めない状態
- **リベース（`rebase`）**：自分のコミットを、別のコミットの先に付け直すこと
- **プルリクエスト**：GitHubの上で、ブランチの取り込みを提案し、差分を見てもらう仕組み
- **`fetch`・`pull`・`push`**：リモートから受け取る、受け取って取り込む、リモートへ送る

## 課題

1. SSH鍵を作る：`ssh-keygen -t ed25519` で鍵を作る。できた2つのファイルのうち、人に渡してよいのはどちらか。それぞれのパーミッションを `ls -l` で確かめ、なぜそうなっているかを考える（F2）。途中で聞かれるパスフレーズは、何から何を守るためのものか
2. 公開鍵をGitHubに登録し（ブラウザで、GitHubの Settings →「SSH and GPG keys」）、`ssh -T git@github.com` でつながることを確かめる。初めてつなぐときに聞かれる質問は、何を確認しているか。答えたあと、`~/.ssh/known_hosts` には何が増えたか
3. `git remote -v` で今の接続先を見て、`git remote set-url` でSSHのURLに変える。変える前と後のURLは、形がどう違うか。変えたあと、`git fetch` がエラーなく通ることを確かめる
4. `~/.ssh/config` に、`github.com` へつなぐときに使う鍵（`IdentityFile`）を書く。このファイルは何のためにあるか。パーミッションはどうあるべきか
5. ブランチ：`git switch -c feature` でブランチを作り、コミットを2つ積む。`git branch` の `*` は何を表すか。`main` に戻り、ファイルがどう見えるかを確かめる。`git merge feature` で取り込む。`git log --graph --oneline --all` で形を見る
6. マージの2つの形：`main` 側にもコミットがある状態で、別のブランチをマージする。課題5のときと、履歴の形がどう違うか。コミットの数は、それぞれいくつ増えたか
7. **本題** コンフリクト：2つのブランチで、同じファイルの同じ行を、違う内容に変更する。マージして、コンフリクトを起こす。`git status` は何と言っているか。ファイルに入った印（`<<<<<<<`、`=======`、`>>>>>>>`）を読み、手で直してコミットする。解消の途中でやめたくなったら、どうすれば元に戻せるか（`git status` の表示にヒントがある）
8. 同じファイルの「別の行」を2つのブランチで変更した場合は、コンフリクトになるか。予想してから試す。Gitは、どんな単位で「同じ場所」を判断していると言えるか
9. GitHub：ブランチを `git push -u origin ブランチ名` で送る。`gh pr create` でプルリクエストを作り、ブラウザで差分を見て、マージする。手元の `main` を `git pull` で最新にする。`git fetch` と `git pull` の違いは何か。`-u` は、何を覚えさせているか
10. `rebase`：課題6と同じ状況をもう一度作り、今度は `git rebase main` で取り込む。履歴の形は、マージのときとどう違うか。リベースの前と後で、コミットのハッシュはどうなったか。「push済みのブランチをrebaseしてはいけない」と言われる理由を調べる
11. 仕上げ：新しいブランチとファイルで、課題7をもう一度やる。今度は、解消した結果を `main` にマージした状態で、GitHubに `git push` する。ブラウザで、GitHubの側の履歴にマージのコミットがあることを確かめる
12. 取り消し：`git revert` と `git reset`（`--soft`、`--hard`）の違いを、練習用のリポジトリで試す。それぞれのあとで、`git log --oneline` と `git status` はどうなるか。push済みのコミットを取り消すなら、どちらを使うべきか。なぜか

### 発展（任意）

- `git stash` を調べる。コミットしたくない書きかけの変更があるまま、別のブランチに切り替えたいときに使ってみる
- `git config --global alias.名前` で、`log --graph --oneline --all` を短く打てるようにする
- マージし終わったブランチを消す。`git branch -d` と `-D` の違いは何か。GitHubの側に残ったブランチの消し方を `man git-push` で探す
- パスフレーズ付きの鍵で、毎回パスフレーズを聞かれないようにする仕組み（`ssh-agent`、`ssh-add`）を調べる

## 詰まりやすいところ

- `Permission denied (publickey)` → `ssh -vT git@github.com` の出力で、どの鍵のファイルを試しているかを読む。登録したのが公開鍵のほうかも確かめる
- `Bad owner or permissions on ~/.ssh/config` → `ls -l ~/.ssh` で確かめる（F2）
- マージしたのに、コンフリクトが起きない → 両方のブランチで「同じ行」を変えてコミットしたかを、`git log --graph --oneline --all` と `git diff ブランチ名` で確かめる
- マージやリベースの途中で、どうすればよいか分からなくなった → `git status` を読む。次にやること、やめる方法の両方が書いてある
- `git push` が `rejected` になる → `git fetch` のあと `git log --graph --oneline --all` で、手元とGitHubの履歴がどう食い違っているかを見る
- `git merge` でエディタが開いた → 何のメッセージを求められているかを、開いた画面の説明から読む（F6）
