## ねらい

ブラウザとサーバーの間を流れているものを、自分の目で読めるようになる。HTTPは、F8で見たTCPの接続の上を流れる「ただの文字」なので、`curl -v` と `nc` があれば、全部見える。閉域の現場で「APIが返ってこない」と言われたとき、ブラウザの開発者ツールがなくても、どの段階（名前解決・接続・暗号化・HTTP）で止まっているかを出力から言えるようにする。Stage 2でAPIを作るときの土台になる。

## このユニットで身につけること

- `curl -v` の出力から、自分が送ったものと、相手が返したものを見分ける
- リクエストとレスポンスを、行（リクエスト行・ステータス行）、ヘッダ、ボディに分けて読む
- `nc` で、HTTPのリクエストを手で打って、応答を受け取る
- メソッド（GET、HEAD、POST、DELETE）を使い分けて送り、サーバーの反応を見る
- ステータスコードの100の位から、おおまかな意味を言う
- 主なヘッダ（`Host`、`Content-Type`、`Content-Length`、`User-Agent`、`Location`）の役割を言う
- HTTPSの出力から、TLSのやり取りと、その中の証明書の情報を見つける
- `curl -v` の出力を、DNS・TCP・TLS・HTTPの4つの段階に分ける

## キーワード

分からない語は、まず `man curl` と、平日に読む本で調べる。

- **HTTP**：ブラウザとサーバーが、文字でやり取りするときの約束事（プロトコル）
- **リクエスト・レスポンス**：こちらから送る「要求」と、相手が返す「応答」。HTTPは必ずこの1往復
- **メソッド**：要求の1行目にある、「何をしたいか」を表す動詞（GET、POST など）
- **ステータスコード**：応答の1行目にある3桁の数字。結果の種類を表す
- **ヘッダ**：`名前: 値` の形で付く、付加情報。要求にも応答にもある
- **ボディ**：ヘッダの後に続く本文。HTMLや、送りたいデータ
- **URL**：`http://ホスト:ポート/パス?クエリ` の形。どの部分が、要求のどこに現れるかを、このユニットで見る
- **TLS**：通信を暗号化する層。HTTPSは、TLSの上でHTTPを話すこと
- **証明書**：「このサーバーは本当にその名前の持ち主だ」と、第三者（認証局）が保証する電子的な書類
- **リダイレクト**：「別の場所へ行け」という応答。3で始まるステータスコードと `Location` ヘッダで表す

## 課題

1. まず `curl http://localhost:8000/` を実行し、何が表示されるかを見る。次に `curl -v http://localhost:8000/` を実行する。行の先頭の `*`、`>`、`<` は、それぞれ何を表すか。サーバー側のシェルに出た1行を読み、アドレス・日時・要求・数字の部分に分ける
2. 課題1の `-v` の出力の中から、リクエスト行、リクエストヘッダ、ステータス行、レスポンスヘッダ、ボディを見分ける。ヘッダとボディの境目は、どうなっているか。リクエスト行とステータス行は、それぞれ空白で区切られた3つの部分からできている。それぞれ何か。リクエスト行に書かれたバージョンと、ステータス行に書かれたバージョンは、同じか
3. HTTPを手で話す：次を実行し、`curl` のときと同じ応答が返ることを確かめる。`\r\n` と、最後の空行は、何のためにあるか。`echo` ではなく `printf` を使っているのは、なぜか（F3・F5）

   ```sh
   printf 'GET / HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc localhost 8000
   ```

4. パス：`curl -v 'http://localhost:8000/?a=1&b=2'` を実行する。`?a=1&b=2` は、リクエストのどこと、サーバー側のログのどこに現れるか。URLをクォートで囲んでいるのは、なぜか（F4で学んだ `&` の意味）。存在しないパスを要求すると、どうなるか。そのときの `Content-Type` と `Content-Length` は、`index.html` を取ったときと、どう違うか
5. メソッド：`curl -I`（HEAD）、`curl -X POST -d 'a=1'`、`curl -X DELETE` を、自分のサーバーに送る。それぞれのステータスコードと、サーバー側のシェルに出るログを見比べる。`-I` のとき、ボディは返ってくるか。`Content-Length` は出ているか
6. ステータスコード：200、201、204、301、304、400、401、403、404、500、501、503 の意味を、表にまとめる。課題4と5で返ってきたコードは、どれだったか。100の位は、何を表しているか
7. ヘッダ：`Content-Type`、`Content-Length`、`User-Agent`、`Host` の役割を調べる。`Content-Length` の値と、`ls -l index.html` のサイズを比べる。`cp index.html hello.txt` して `hello.txt` を要求すると、`Content-Type` はどう変わるか。サーバーは、何を見て決めているか。`curl -H 'X-Test: 1' -A 'my-client/1.0'` を送り、`-v` の出力で、実際に送られたことを確かめる
8. リダイレクト（外のネットワークが要る）：`curl -I http://github.com` の、ステータスコードと `Location` ヘッダを読む。`-L` を付けると、何が変わるか。`-v` も付けると、要求は何回送られているか
9. HTTPS：`curl -v https://example.com` の出力のうち、HTTPが始まる前の部分（TLSのやり取り）を読む。証明書の発行者と有効期限は、どこに出ているか。証明書は、何を証明しているか。`curl -v http://example.com` と比べて、`*` の行はどう増えたか
10. `curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://example.com` を実行し、`-s`、`-o`、`-w` がそれぞれ何をしているかを調べる。同じことを `http://localhost:8000/` に対して行い、時間を比べる
11. **本題**：`curl -v --http1.1 https://example.com` の出力を `curl-v.txt` に保存する（`2>&1` が必要な理由と、`>` との順番も考える。`--http1.1` は、このユニットで学んだ形式のHTTPで通信させる指定）。保存できたら、`explain.md` に次の2つを書く。見てよいのは、保存した `curl-v.txt` だけ
   - 出力の各行を、DNS・TCP・TLS・HTTPの4つの段階に分ける（TLSの部分は、1行ずつの意味までは書かなくてよい）。HTTPより前の `*` の行は、F8で見たどのコマンドの出力と対応するか
   - HTTPの部分（`>` と `<` の行）は、1行ずつの意味を書く
12. サーバー側のシェルに出たアクセスログを、F3のやり方で集計する（ステータスコードごとの件数）。ログをファイルに残すには、サーバーを起動し直すときに、F4で学んだ標準出力・標準エラーの使い分けを思い出す

### 発展（任意）

- `--http1.1` を付けずに `curl -v https://example.com` を実行し、課題11の出力と比べる。リクエスト行のバージョンは何になっているか。`*` の行に `ALPN` という語があれば、何を決めているのかを調べる
- 課題3と同じリクエストを、`Host:` を `example.com` に変えて `nc example.com 80` に送る。`Connection: close` の行を消すと、どう変わるか（変わらないこともある。`Connection` ヘッダの役割から、なぜ変わりうるのかを考える）
- `man curl` で、応答ヘッダをボディと一緒に表示するオプションと、応答ヘッダをファイルに保存するオプションを探す
- `man curl` で、証明書の検証をあえてスキップするオプションを探し、それを普段使ってはいけない理由を書く

## 詰まりやすいところ

- `Failed to connect` や `Connection refused` → サーバー側のシェルで、`python3 -m http.server` がまだ動いているかを見る。`ss -ltn` で8000番の待ち受けを確かめる（F8）
- `curl-v.txt` が空、または `<h1>` の部分しか入っていない → `-v` の行が、どの出力先（標準出力・標準エラー）に出ているかを考える（F4）。`>` と `2>&1` の順番
- `nc` で送っても、何も返ってこないまま止まる → `\r\n` と、最後の空行が入っているか。`printf` の書式の中で `\r\n` がそのまま送られているかを、`printf ... | xxd` で確かめる（F1）
- `?a=1&b=2` を付けたら、途中で別のことが起きた → シェルが `&` をどう扱うかを考える（F4）。クォートの有無
- `curl -I http://github.com` や `https://example.com` がつながらない → 外のネットワークが要る。`dig` と `ping` で、どこまで届いているかを切り分ける（F8）
- 課題12で、ログをパイプに流せない → サーバーのログが、標準出力と標準エラーのどちらに出ているかを確かめる（F4）
