## ねらい

ここまで「決まり文句」として打ってきたGitのコマンドの意味を理解し、自分の判断でコミットを積めるようになる。ターミナルの中のエディタにも慣れる。閉域のサーバーにはVS Codeをつなげないことが多く、設定ファイルを直す手段は `vim` か `nano` だけになる。変更の履歴も、GitHubがなくても手元のGitだけで管理できることを、体で覚える。

## このユニットで身につけること

- ターミナルの中のエディタで、ファイルを開き、編集し、保存して終了する
- リポジトリを作り、変更を選んでステージに載せ、コミットする
- `git status` と `git diff` で、今の状態と変更の中身を確かめてからコミットする
- `git log` と `git show` で、過去の記録を読む
- まだコミットしていない変更を、取り消す
- `.gitignore` で、記録したくないファイルを外す
- 関係のある変更ごとに、コミットを分ける

## キーワード

分からない語は、`man git-コマンド名`（例：`man git-commit`）か `git コマンド名 -h` で調べる。

- **リポジトリ**：ファイルと、その変更の履歴をまとめて入れておく場所。実体は `.git` ディレクトリ
- **作業ツリー**：今、実際に見えていて編集できるファイルたち
- **ステージ（インデックス）**：次のコミットに入れる変更を、並べておく場所
- **コミット**：ある時点のファイルの状態を、メッセージ付きで記録したもの。記録する操作のことも指す
- **ハッシュ**：コミットごとに付く、英数字の長い名前。先頭の数文字で指定できる
- **`HEAD`**：今いるコミットを指す名前
- **追跡されている（tracked）**：Gitが変更を見張っているファイルの状態
- **`.gitignore`**：Gitに無視させるファイルの名前やパターンを書くファイル

## 課題

1. エディタ：`nano` でファイルを作り、保存して終了する。次に `vimtutor` を30分だけ進める。`vim` で「入力を始める」「入力をやめる」「保存する」「保存せずに終了する」方法を、メモに書く。どちらを普段使うかを決める
2. 設定を確かめる：`git config --global --list` で、Day 0 に設定した名前、メールアドレス、`init.defaultBranch` を探す。この設定は、どのファイルに保存されているか（`man git-config` で探し、`cat` で見る）。`core.editor` という設定を調べ、課題1で決めたエディタにする
3. `git init` でリポジトリを作る。`git status` の1行目で、ブランチ名が `main` になっていることを確かめる（[はじめかた](../../../docs/02-getting-started.md)の `init.defaultBranch` の設定が効いている）。ファイルを1つ作り、`git status` → `git add` → `git status` → `git commit -m` → `git status` の順に実行し、表示がどう変わるかを追う。「作業ツリー」「ステージ」「コミット」の3つの場所の関係を、図に描く
4. `ls -la` で、`git init` が作ったものを見つける。その中を `ls` で眺める（中のファイルは書き換えない）。このディレクトリを消すと、何が失われ、何が残るか。予想を書いてから、練習用にもう1つ作ったリポジトリで確かめる
5. ファイルを変更し、`git diff` を見る。行の先頭の `+` と `-`、`@@` の行は何を表すか。`git add` したあとの `git diff` と `git diff --staged` の違いを確かめる。コミットしたあと、`git log`、`git log --oneline`、`git log --stat`、`git show` を試す
6. 取り消し：変更をまだ `add` していないとき、`add` したあと、それぞれの戻し方を調べて試す（`git restore`、`git restore --staged`）。直前のコミットのメッセージを直す方法（`git commit --amend`）を試す。`--amend` の前と後で、`git log --oneline` のハッシュはどうなるか
7. `.gitignore`：`*.log` と `secret.env` を無視する設定を書き、`git status` で確かめる。すでにコミットしたファイルを `.gitignore` に足すと、どうなるか。`.gitignore` 自体は、コミットするべきか
8. コミットの単位：3つのファイルを変更し、関係のある変更だけを選んで、2回に分けてコミットする。1回目の `git add` のあと、`git status` と `git diff --staged` で、入れるものだけが載っていることを確かめてからコミットする
9. `-m` を付けずに `git commit` を実行する。何が起きるか。1行目に要約、1行空けて3行目から説明、という形のメッセージを書いてコミットし、`git log` と `git log --oneline` での見え方を比べる。何も書かずにエディタを終了すると、どうなるか
10. `explain.md`：毎回の終わりに打ってきた3行（`git add -A`、`git commit -m`、`git push origin main`）が、それぞれ何をしているかを、何も見ずに書く。`-A`、`origin`、`main` が何を指すかも書く（`push` の詳しい仕組みはF7で学ぶ。今の理解で書けばよい）
11. 学習用リポジトリ（`~/offgrid-log`）で、`git log --oneline` を実行し、自分のこれまでの記録を読む。`git show` で、最初のAIなしデーのコミットの中身を見る。`git log --stat` で、いちばん多くのファイルを変えたコミットを探す
12. **本題**：学習用リポジトリで、今日のメモと `explain.md` をコミットする。決まり文句をそのまま打つのではなく、`git status` と `git diff` で中身を確かめ、入れるファイルを自分で選んで `git add` し、[README](../../../README.md)のコミット規約に沿ったメッセージを付ける。関係のない変更が混ざっていたら、コミットを分ける

### 発展（任意）

- `git add -p` を調べ、1つのファイルの中の変更を、2つのコミットに分ける
- `git mv`・`git rm` と、ふつうの `mv`・`rm` のあとで、`git status` の表示はどう違うか
- `git tag` を調べ、練習用のリポジトリで、節目のコミットに名前を付ける。付けた名前で `git show` する
- `vim` で、行の削除、コピーと貼り付け、取り消し（undo）、文字列の検索のしかたを調べ、メモに足す

## 詰まりやすいところ

- `vim` から出られない → まず Esc を押す。そのあとは、課題1のメモか `vimtutor` の最初のレッスンを見る
- `git commit` で、見慣れないエディタが開いた → 画面の下に出ている操作の説明を読む。次からのために、課題2の `core.editor` を見直す
- `git diff` に何も出ない → 変更が今、作業ツリーとステージのどちらにあるかを `git status` で確かめる
- `.gitignore` に書いたのに、`git status` に出続ける → そのファイルが過去にコミットされていないかを、`git log -- ファイル名` で確かめる
- `fatal: not a git repository` → `pwd` で今いる場所を確かめ、`.git` がどのディレクトリにあるかを探す
- `git log` の画面から抜けられない → `man` と同じ操作を試す（F1）
