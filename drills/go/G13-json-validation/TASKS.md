## ねらい

外から届くデータを疑い、おかしな入力を決まった形のエラーで断れるAPIにする。APIに届くのは、正しいクライアントからのリクエストだけではない。検証のないAPIは、壊れたデータをため込み、後から直せなくなる。さらに、サーバーを起動せずにハンドラを試せる `httptest` を覚え、`curl` を手で打たなくても、直すたびに全エンドポイントを確かめられるようにする。

## このユニットで身につけること

- リクエストのJSONを構造体に読み込み、失敗の種類（壊れたJSON、型の違い、空のボディ）を見分ける
- 必須項目、長さ、数値の範囲を検証し、どの項目が、なぜだめなのかを返す
- エラーレスポンスの形を1つに決め、すべてのハンドラで同じ形を返す
- ボディの大きさに上限を付ける
- `httptest` で、サーバーを起動せずにハンドラをテストする
- 正常系と異常系を、テーブル駆動テストで並べる

## キーワード

- **マーシャル／アンマーシャル**：Goの値をJSONの文字列にすること／JSONの文字列をGoの値にすること
- **構造体タグ**：フィールドの後ろに `` `json:"name"` `` の形で書く注釈。JSONでの項目名などを指定する
- **ゼロ値**：値を入れていない変数が持つ値（数値なら0、文字列なら空）。JSONに項目がなかった場合と、見分けにくい
- **入力検証（バリデーション）**：受け取った値が、決めた条件を満たすかを、処理の前に確かめること
- **`httptest.ResponseRecorder`**：`http.ResponseWriter` の代わりに渡すと、ハンドラが書いたステータスコード・ヘッダ・ボディを記録してくれる型
- **`httptest.Server`**：テストの中だけで動く、本物のHTTPサーバー。空いているポートで起動する
- **テストヘルパー**：テストの中の繰り返しをまとめた関数。`t.Helper()` を呼ぶと、失敗した行の表示が呼び出し元になる

## 課題

1. JSONの読み込みが、どんなときに、どんなエラーになるかを調べる。小さなテストを書き、次の入力を構造体に読み込ませて、返ってきたエラーの型とメッセージを `notes.md` に記録する（`%T` で型を表示できる）
   - 空のボディ、`{`、`{"name": 1}`、`{"value": "abc"}`、`[]`、`null`
   - `{"name":"a","value":1}` の後ろに、余分な文字列が続くもの
2. `{"name":"a"}` と `{"name":"a","value":0}` を、今のコードは区別できるか。できないなら、なぜか。「項目がない」と「0が入っている」を区別する方法を、`go doc encoding/json.Unmarshal` の説明から探す
3. 構造体にない項目（例：`{"name":"a","value":1,"admin":true}`）を送ると、今はどうなるか。これをエラーにする方法を `go doc json.Decoder` のメソッドの一覧から探す。エラーにする場合と、黙って無視する場合の、それぞれの利点を書く
4. エラーレスポンスの形を1つ決め、`api.md` に書く。次の3つを含める：プログラムが見分けるための短いコード、人が読むためのメッセージ、項目ごとのエラーの一覧（検証エラーのとき）。決めた形で応答を書く関数を1つ作り、G12で書いたエラー応答を、すべてそれに置き換える
5. 検証を、HTTPから切り離した関数として書く（入力を受け取り、項目ごとのエラーの一覧を返す）。テーブル駆動テストで、境界値を確かめる：`name` が0文字、1文字、50文字、51文字、空白だけ。`value` が -1、0、100、101、小数
6. 日本語の `name`（例：「あ」を50個）は通るか。通らないなら、何を数えているのかを調べる（F1）。「文字数」で数える方法を `go doc unicode/utf8` から探す
7. `POST /items` と `PUT /items/{id}` に、検証を組み込む。検証エラーのステータスコードを400にするか422にするかを決め、理由を `api.md` に書く。項目が2つともだめなとき、エラーは1つだけ返るか、2つとも返るか。使う側（T10の画面）にとって、どちらがよいか
8. `Content-Type` が `application/json` でない `POST` を、どう扱うかを決めて実装する。10MBのボディを送りつけられたら、今のコードは何をするか。上限を付ける方法を `go doc http.MaxBytesReader` で調べ、1MBを超えたら決めた形のエラーを返す
9. `httptest.NewRequest` と `httptest.NewRecorder` を使い、`GET /items/{id}` のテストを1本書く。ハンドラの関数を直接呼ぶ場合と、`ServeMux` を通して呼ぶ場合で、`{id}` の取り出しの結果はどう違うか。なぜか。以降のテストは、どちらの呼び方にすべきか
10. **本題**：5つのエンドポイントすべてに、テーブル駆動のハンドラテストを書く。1ケースは、メソッド、パス、ボディ、期待するステータスコード、期待するエラーコード（エラーのとき）を持つ。各エンドポイントに、正常系を1つ以上と、異常系を2つ以上入れる。レスポンスのボディは、文字列の比較ではなく、JSONとして読み込んでから比べる。なぜ、そのほうがよいか
11. 自分で登録していないパス（`/nope`）や、許可していないメソッド（`PATCH /items/1`）への応答は、課題4で決めた形になっているか。`curl -i` で確かめる。なっていないなら、その応答はどこが返しているか。揃えるか、揃えないかを決めて、`api.md` に書く
12. `httptest.NewServer` でテスト用のサーバーを立て、`http.Get` などの本物のHTTPクライアントで「登録 → 取得 → 更新 → 削除 → 取得（404）」の流れを通すテストを1本書く。課題10の方法と比べ、確かめられることの違いと、実行時間の違いを書く

### 発展（任意）

- テストのたびにストアを新しく作り、テストの実行順を入れ替えても結果が変わらないことを確かめる（`go help testflag` で `-shuffle` を調べる）
- `go test -coverprofile` と `go tool cover -html`（G7）で、テストが通っていない分岐を探し、ケースを足す
- G12の `check.sh` を、今のエラー応答に合わせて更新し、テストと `check.sh` の役割の違いを書く

## 詰まりやすいところ

- テストの中で `{id}` が空になる → リクエストが、パターンを登録した `ServeMux` を通っているかを確かめる（課題9）
- `httptest.NewRequest` に渡したボディが、ハンドラで読めない → ボディを渡す引数の型を `go doc httptest.NewRequest` で確かめる。文字列から `io.Reader` を作る方法は、G8で使った
- 1回目の読み込みは成功するのに、同じボディをもう一度読むと空になる → `io.Reader` が「何回読めるものか」を思い出す（G8）
- 期待したJSONと、文字列としては一致しない（改行や、項目の順番が違う） → 何を比べるべきかを考え直す（課題10）
- 上限を超えたボディのエラーと、壊れたJSONのエラーを見分けられない → `go doc http.MaxBytesReader` に、返されるエラーの型が書いてある。型で見分ける方法は、G6で学んだ
- テストが1本ずつなら通るのに、まとめて実行すると落ちる → テストの間で、同じストアを使い回していないかを疑う

## 完了条件の確かめ方

`go vet ./... && go test -race -cover ./...` を実行し、ハンドラのテストがすべて通る。`go test -v -run ハンドラテストの名前` の出力で、5つのエンドポイントそれぞれに、正常系と異常系のケースがあることを確かめる。検証の条件を1つわざと壊し（例：上限を50から500に変える）、テストが落ちることも確かめてから、元に戻す。
