## ねらい

スライスとポインタだけを材料に、スタック・キュー・連結リストを自分で作れるようになる。「追加と取り出しに、データの量に応じてどれだけ時間がかかるか」を、予想してから実測し、計算量という言葉で説明できるようにする。閉域の現場では、便利なライブラリを後から入れられない。標準ライブラリにない入れ物を、必要なときに自分で書ける力と、「この書き方は、データが10倍になると何倍遅くなるか」を見積もる力を、ここで付ける。

## このユニットで身につけること

- スライスを土台にした、スタック（後入れ先出し）を作り、テストする
- スライスを土台にした、キュー（先入れ先出し）を作り、取り出し方の違いで速さが変わることを実測する
- 構造体とポインタで、単方向の連結リストを作る（`nil` の扱いを含めて）
- 連結リストを土台にしたキューを作り、スライス版と同じインターフェース（G8）で扱う
- 「要素数を10倍にすると、時間は何倍か」を測り、O(1) と O(n) を見分ける
- 空のときの取り出しなど、境界の場合をテストに含める

## キーワード

- **データ構造**：データの並べ方・つなぎ方の型。何を速くしたいかで選ぶ
- **スタック**：最後に入れたものを、最初に取り出す入れ物（LIFO）。入れる操作をpush、取り出す操作をpopと呼ぶ
- **キュー**：最初に入れたものを、最初に取り出す入れ物（FIFO）。入れる操作をenqueue、取り出す操作をdequeueと呼ぶ
- **連結リスト**：値と「次の要素へのポインタ」を持つノードを、数珠つなぎにしたもの。先頭のノードだけを覚えておく
- **ノード**：連結リストの1つの要素。構造体で表す
- **計算量**：データの量 n に対して、処理の手間がどう増えるかの目安
- **O記法**：計算量の書き方。O(1) は n に関係なく一定、O(n) は n に比例、O(n²) は n の2乗に比例
- **境界の場合**：空、要素が1つ、先頭・末尾など、バグが出やすい特別な入力

## 課題

1. `stack/` に、整数を入れるスタックを作る。操作は、push、pop、先頭を見るだけのpeek、要素数の4つ。空のときにpopされたら何を返すかを、先に決める（2つ目の戻り値で知らせるか、`error` を返すか。G6）。決めた理由を `notes.md` に書く
2. スタックのテーブル駆動テストを書く。「操作の列」を入力にして、「取り出される値の列」を期待値にする。ケースには、入れた順の逆に出ること、空からのpop、popした後にまたpushしても壊れないこと、を含める
3. 観察：1000回pushしてから1000回popし、その後の `len` と `cap`（`go doc builtin.cap`）を表示する。`cap` は、popしても減るか。減らないとしたら、そのメモリは誰が持っているか。減らしたいなら、どうすればよいかを考える（G3の、`append` が裏の配列をどう扱うか）
4. スタックの使いどころを1つ試す：`([{}])` のような括弧の列を受け取り、対応が取れているかを返す関数を書く。テストには、`(]`、`(()`、`)(`、空文字列を含める。なぜ、この問題にスタックが向いているのかを書く
5. `queue/` に、スライスを土台にしたキューを作る。enqueueは `append`。dequeueは、先頭を返してから、残りを「先頭を除いたスライス」にする。テストは課題2と同じ形で書く。空からのdequeueの扱いも決める
6. 観察：dequeueの書き方を2通り作る。(a) 先頭を除いたスライスを取り直す。(b) 2番目以降を、1つずつ前に詰め直す（`copy`）。n = 10,000、100,000、1,000,000 個をenqueueしてから全部dequeueし、かかった時間を `time.Since` で測る（`lab/`）。nが10倍になると、時間はそれぞれ何倍になるか。(a) の場合、dequeueした後も `cap` はどうなっているか（課題3と同じ問題が起きるか）
7. `list/` に、単方向の連結リストを作る。まず紙に、「値3つのリストの先頭に1つ足す」「末尾に1つ足す」「真ん中の1つを消す」を、ノードと矢印の絵で描く。それから、先頭に追加、末尾に追加、値を探す、値を1つ消す、要素数、全要素をスライスにして返す、の6つを書く。ノードの型と、リストの型（先頭のノードを覚える）は分ける
8. 連結リストのテストを書く。ケースには、空のリストからの削除、先頭の削除、末尾の削除、存在しない値の削除、要素が1つのリストの削除を必ず含める。テストが `nil pointer dereference` で落ちたら、G7の課題10のとおりにスタックトレースを読み、どの `nil` を触ったかを特定する
9. 観察：「末尾に追加」を、先頭からたどる書き方と、末尾のノードも覚えておく書き方の2通りで作り、n = 1,000、10,000、100,000 で時間を測る。nが10倍になると、時間はそれぞれ何倍になるか。次に、「i番目の要素を返す」をリストとスライスの両方で書き、同じように比べる
10. 連結リストを土台にしたキューを `queue/` に足す。enqueueとdequeueを、それぞれ「先頭からたどらずに」書けるか。スライス版と連結リスト版を、同じインターフェース（G8）で扱えるようにし、課題5のテストを、両方の実装に対して同じテーブルで実行する。課題6と同じ測り方で、連結リスト版も比べる
11. `go doc container/list` を読む。標準ライブラリの連結リストは、値をどんな型で持っているか。取り出した値を `int` として使うには、何が要るか。自分のリストとの違いを2点書く
12. **本題**：何も見ずに `explain.md` に書く。スタックのpush／pop、スライス版キュー（(a) と (b)）と連結リスト版キューのenqueue／dequeue、連結リストの先頭追加・末尾追加（2通り）・i番目の取得について、それぞれの計算量（O(1) か O(n) か）と、そう考えた理由。課題6・9の実測値を根拠として添える

## 詰まりやすいところ

- `panic: runtime error: index out of range [-1]` → 空のときにpop／dequeueされた場合の分岐が、要素を取り出す行より前にあるかを見る
- `nil pointer dereference` で落ちる → リストが空のとき、先頭のノードは何か。ループの条件が、`nil` に達したときに止まるようになっているか
- 削除で、先頭だけ消えない、または末尾だけ消えない → 紙の絵に戻る。「消すノードの1つ前」が存在しない場合は、どの場合か
- 課題6・9で、nを増やしても時間がほとんど変わらない → 測る範囲に、準備（データ作り）の時間まで入っていないか。結果を使わない計算は、省かれることがある。表示に使う
- テストの期待値と結果が、順番だけ違う → LIFOとFIFOのどちらを作っているつもりかを、名前と実装で見比べる
- `cap` が予想と違う数になる → `append` が裏の配列を伸ばす規則は、Goのバージョンや大きさで変わる。数そのものではなく、「減るかどうか」を見る
