## ねらい

G12から育ててきたAPIの保存先を、メモリからPostgreSQLに置き換え、再起動してもデータが消えないようにする。ここで、GoとSQL（Dトラック）が合流する。プログラムからSQLを実行するときに、いちばん重い事故がSQLインジェクション。「値は必ずプレースホルダ（`$1`）で渡す。文字列の連結でSQLを組み立てない」という決まりを、理由を自分の目で見たうえで、手に覚えさせる。

## このユニットで身につけること

- `pgx` でPostgreSQLに接続し、接続先を環境変数で渡す
- 値をプレースホルダで渡して、`INSERT`、`SELECT`、`UPDATE`、`DELETE` を実行する
- 「0行だった」ことを見分け、404に対応させる
- 文字列の連結で作ったSQLが、入力によって別の意味に変わることを観察する
- 複数の書き込みを1つのトランザクションにまとめ、途中で失敗したら全部取り消す
- DBのエラー（接続できない、制約違反）を見分け、内部の情報を漏らさないエラーレスポンスにする
- 本物のDBを使うテストを書く

## キーワード

- **ドライバ**：プログラムからDBに話しかけるためのライブラリ。`pgx` は、PostgreSQL専用のドライバ
- **接続文字列**：接続先のホスト、ポート、ユーザー、パスワード、DB名を、1つにまとめた文字列
- **プレースホルダ**：SQLの中に `$1`、`$2` と書いておき、値は後から別に渡す仕組み。値は、SQLの文法としては解釈されない
- **SQLインジェクション**：入力の中にSQLの断片を混ぜ、開発者が意図しないSQLを実行させる攻撃
- **コネクションプール**：DBへの接続を何本か開いたまま持っておき、使い回す仕組み。`pgx` では `pgxpool`
- **トランザクション**：複数のSQLを「全部成功」か「全部なかったこと」のどちらかにする仕組み（D5）
- **SQLSTATE**：PostgreSQLがエラーの種類ごとに返す、5文字のコード。一覧は、PostgreSQLマニュアルの付録「PostgreSQLエラーコード」
- **結合テスト**：本物のDBなど、外の部品とつないで動かすテスト。部品を偽物に置き換えるテストより遅いが、SQLの誤りを見つけられる

## 準備

**`pgx` の取得にはネットワークが要る。** このユニットだけの例外として、平日のうちに、下の `go get` までを済ませておく。

```sh
cp -r ../G16-context-shutdown/{*.go,static,api.md} .
go mod init offgrid/g17-database
go get github.com/jackc/pgx/v5
docker start pg-offgrid
docker exec -it pg-offgrid psql -U postgres -c 'CREATE DATABASE g17;' -c 'CREATE DATABASE g17_test;'
```

接続文字列は `postgres://ユーザー:パスワード@ホスト:ポート/DB名` の形で、環境変数 `DATABASE_URL`（テスト用は `TEST_DATABASE_URL`）に入れて渡す。パスワードは、F10でコンテナを作ったときに決めたもの。コードと `api.md` には書かず、`.env` に書くなら、`.gitignore` に入れる。

## 課題

1. `DATABASE_URL` を読んで接続し、疎通を確かめ、サーバーのバージョン（`SELECT version()`）を表示して終わる、小さなプログラムを書く。接続と疎通確認の関数は、`go doc github.com/jackc/pgx/v5.Conn` の一覧から探す。次の場合のエラーメッセージを、それぞれ記録する：`DATABASE_URL` が空、パスワードが違う、DB名が違う、`docker stop pg-offgrid` した後
2. `items` 表を作る `schema.sql` を書く（D6）。G13で決めた検証の条件を、`NOT NULL` と `CHECK` 制約でも表す。`id` は、DBに採番させる。`docker exec -i pg-offgrid psql -U postgres -d g17 -v ON_ERROR_STOP=1 < schema.sql` で、`g17` と `g17_test` の両方に流す。2回流しても、エラーにならない書き方にする
3. ハンドラが、ストアの具体的な型ではなく、インターフェース（G8）を通してストアを使うように直す。メソッドは、第1引数に `ctx` を取るようにする（G16）。メモリ版のストアが、そのインターフェースを満たしたまま、G13のテストが通ることを確かめる
4. PostgreSQL版のストアを作り始める。まず、登録。値は `$1`、`$2` で渡し、採番された `id` を、同じSQLの中で受け取る（`INSERT` の `RETURNING` 句。PostgreSQLマニュアルの「INSERT」）。`psql` で `SELECT * FROM items;` を実行し、入っていることを確かめる
5. 1件取得と一覧を実装する。該当する行がないとき、`pgx` は何を返すか。それを `errors.Is` で見分け、G12で決めた「見つからない」エラーに変換する。一覧では、行を1つずつ読むループの後で、確かめるべきものが2つある。`go doc github.com/jackc/pgx/v5.Rows` を読んで探す
6. 更新と削除を実装する。存在しない `id` を指定した `UPDATE` は、SQLとしてはエラーにならない。「1行も変わらなかった」ことを知る方法を、`Exec` の戻り値の型から探し、404に対応させる
7. 観察：文字列の連結は、なぜ禁止なのか。**APIの本体とは別の場所**（`experiments/injection/`）で、実験する。`psql` で、`name` と `secret` の2列を持つ実験用の表 `inj_demo` を作り、3行入れる。コマンドライン引数で受け取った名前を、`+` か `fmt.Sprintf` でSQLの文字列に埋め込んで検索し、結果を表示するプログラムを書く。次の引数で実行し、表示と、`docker logs pg-offgrid` の末尾を記録する
   - `alice`（ふつうの名前）
   - `O'Brien`（ふつうの名前なのに、何が起きるか）
   - `' OR '1'='1`
   - `'; DROP TABLE inj_demo; --`（エラーになるか、表が消えるか。どちらの場合も、入力が「値」ではなく「SQLの一部」として読まれた証拠を、ログから探す）
8. 課題7のプログラムを、プレースホルダを使う形に直し、同じ4つの引数で実行する。結果は、どう変わったか。PostgreSQLには、SQLと値が、どう届いているか。`notes.md` に、「連結では何が起き、プレースホルダではなぜ起きないのか」を、自分の言葉で書く。APIの本体に、`+` や `fmt.Sprintf` でSQLを組み立てている箇所がないことを、`grep` で確かめる
9. HTTPサーバーは、リクエストごとに別のgoroutineでハンドラを動かす（G15）。1本の `pgx.Conn` を、複数のgoroutineから同時に使ってよいか。`go doc github.com/jackc/pgx/v5.Conn` の説明で確かめる。`pgxpool` に切り替え、終了処理（G16）で、プールも閉じる。リクエストの `ctx` が、SQLの実行まで渡っているかも確かめる
10. トランザクション：複数のアイテムを配列で受け取り、まとめて登録する `POST /items/bulk` を足す。1件でも登録に失敗したら、1件も登録されないようにする。3件のうち2件目が `CHECK` 制約に違反するリクエスト（G13の検証を、わざと通り抜けさせる方法も考える）を送り、`psql` で、表に1件も増えていないことを確かめる。トランザクションを使わない版と、結果を比べる。途中で `return` したときに、`ROLLBACK` を漏らさない書き方を、`defer` を使って考える。コミットの後で `Rollback` を呼ぶとどうなるかは、`go doc github.com/jackc/pgx/v5.Tx` で調べる
11. エラー処理：APIを動かしたまま `docker stop pg-offgrid` し、`curl` で各エンドポイントを呼ぶ。何番が返るべきか（500か、503か）を決める。レスポンスに、接続先やSQLの文面が漏れていないこと、ログ（`slog`）には、原因が分かる情報が残っていることを確かめる。制約違反のエラーは、`errors.As`（G6）で `pgx` のエラー型（`go doc github.com/jackc/pgx/v5/pgconn.PgError`）を取り出し、SQLSTATEで見分けて、400番台に対応させる
12. **本題**：PostgreSQL版のストアを使う、結合テストを書く。`TEST_DATABASE_URL` が空なら、テストを飛ばす（`go doc testing.T.Skip`）。テストの前に、表を空にする。次を含める
    - 登録 → 取得 → 更新 → 削除 → 取得（見つからない）
    - `name` が `'; DROP TABLE items; --` のアイテムを、APIのハンドラ経由で登録する。201が返り、取得すると同じ文字列がそのまま返り、`items` 表が存在し続け、行数が1だけ増えている
    - 課題10の、途中で失敗する一括登録の後で、行数が変わっていない

### 発展（任意）

- 同じストアを、標準ライブラリの `database/sql` で書く（ドライバには、`pgx` に含まれる `stdlib` パッケージを使うので、追加の取得は要らない）。`pgx` を直接使う場合との違いを、3点書く（接続の管理、「行がない」の扱い、`ctx` の渡し方）
- SQLの実行に、1回ごとの期限（例：2秒）を付ける。`psql` から `LOCK TABLE` で表をロックしたまま、APIを呼ぶと、どうなるか
- 起動時に、使う側（`-store=memory` か `-store=postgres`）を `flag` で選べるようにする

## 詰まりやすいところ

- ホスト側のプログラムから、DBに接続できない → コンテナを起動したときの `-p` の指定（F10）を `docker ps` で見る。`ss -ltn`（F8）で、ポートが開いているかを確かめる
- `go get` がエラーになる → ネットワークにつながる平日に、済ませておく。閉域で依存をどう持ち込むかは、G18とO7で扱う
- `Scan` で、型が合わない、列の数が合わない、というエラーになる → `SELECT` に書いた列の順番・数と、`Scan` に渡した変数の順番・数・型を、1つずつ見比べる。`SELECT *` を使っていないか
- テストが、1回目は通るのに、2回目は落ちる → 前回のテストのデータが、表に残っていないか。採番が、表を空にした後にどうなるかも確かめる
- `go test ./...` だと落ちるのに、パッケージを1つずつ実行すると通る → 複数のパッケージのテストが、同じDBを同時に使っていないかを疑う。`go help testflag` で、並行実行に関わるオプションを探す
- しばらく動かすと、リクエストが返ってこなくなる → プールから借りた接続や、`Query` で得た行の集まりを、返し忘れている（閉じ忘れている）箇所がないかを探す

## 完了条件の確かめ方

1. `TEST_DATABASE_URL` を設定して `go vet ./... && go test -race -cover -v ./...` を実行する。結合テストが `SKIP` にならずに通り、`'; DROP TABLE items; --` のケースが含まれている
2. APIを起動して `curl` でアイテムを登録し、APIを再起動しても、取得できる
3. 課題10の一括登録の失敗で、表の行数が変わらない。課題11で、DBを止めている間は、決めたエラーが返り、`docker start pg-offgrid` の後は、APIを再起動しなくても、また応答する
4. `grep` で、APIの本体に、SQLを文字列の連結で組み立てている箇所がない
