## ねらい

これまでは「呼ばれる側（サーバー）」を作ってきた。今度は「呼ぶ側（クライアント）」を、相手が落ちていても壊れないように書く。閉域の現場では、監視対象のサーバーがいつ止まり、いつ戻るかは、こちらの都合では決まらない。相手をいつまでも待たない（タイムアウト）、資源を返す（`resp.Body` を閉じる）、失敗したら間隔を空けて出直す（指数バックオフ）、相手が戻ったら勝手に再開する。この4つがそろったクライアントが、卒業制作のagent（C2）の芯になる。

## このユニットで身につけること

- `http.Client` にタイムアウトを設定し、応答しない相手から戻ってこられるようにする
- `resp.Body` を閉じないと何が起きるかを、`ss` で観察し、必ず閉じる書き方を身につける
- 失敗の種類（つながらない、時間切れ、5xx、4xx）ごとに、再試行するかどうかを決める
- 待ち時間を倍々に増やし、上限とばらつき（ジッタ）を付ける関数を書き、テストする
- 再試行の待ちを、`context`（G16）で中断できるようにする
- 同じデータを2回送ったときに何が起きるかを確かめ、冪等性を設計に組み込む
- `httptest` で「最初の2回だけ失敗する相手」「止まっている相手」を作り、再試行をテストする
- N秒ごとにAPIへデータを送り続け、APIの再起動をまたいで動き続けるクライアントを作る

## キーワード

- **タイムアウト**：「この時間までに終わらなければ、あきらめる」という上限。`http.Client` では、リクエスト全体に対して設定できる
- **`resp.Body`**：レスポンスの本文を読むための `io.ReadCloser`。読み終わったら閉じる。閉じないと、接続が使い回されず、資源が漏れる
- **keep-alive**：1つのTCP接続を、複数のHTTPリクエストで使い回す仕組み。本文を最後まで読んで閉じたときだけ、使い回せる
- **リトライ（再試行）**：失敗したリクエストを、もう一度送ること。何を、何回、どの間隔で送り直すかを決める必要がある
- **指数バックオフ**：再試行の間隔を、1秒、2秒、4秒、8秒…と倍々に増やしていくこと
- **上限（cap）**：バックオフの間隔がそれ以上大きくならない値。付けないと、数回の失敗で間隔が何時間にもなる
- **ジッタ**：待ち時間に足す、わざとのばらつき。多数のクライアントが同時に出直すのを避ける
- **一時的なエラー**：もう一度やれば成功するかもしれない失敗（接続できない、503）。入力が間違っている400や401は、やり直しても直らない
- **冪等（べきとう）**：同じリクエストを何回送っても、結果が1回送ったときと同じになる性質（G12）

```sh
go mod init offgrid/g19-http-client-retry
mkdir -p cmd/sender internal/backoff internal/apiclient lab
# 別のシェルで
cd ../G16-context-shutdown && API_TOKEN=dev-token-0000 go run .
```

構成はG18のとおり、`cmd/` と `internal/` に分ける。送るデータは、G12の「アイテム」（`name` と `value`）でよい。`value` には、何でもよい（例：起動からの秒数）。`API_TOKEN`（G14）は環境変数で受け取り、コードに書かない。

## 課題

1. `lab/` で、APIの `/healthz` を `http.Get` で呼び、ステータスコードを表示する。`http.Get` が使っている `http.DefaultClient` のタイムアウトは何秒か（`go doc http.DefaultClient`、`go doc http.Client` の `Timeout` の説明）。次に、`httptest.NewServer`（G13）で「5秒待ってから応答する相手」を作り、タイムアウトなしの `Client` と、1秒の `Client` で呼ぶ。返ってきたエラーの文面を記録する。そのエラーは `*url.Error` に `errors.As`（G6）でき、`Timeout()` は `true` を返すか
2. 観察：`Body` を閉じずに、APIの `/healthz` を200回呼ぶプログラムを書く。動かしながら、別のシェルで `ss -tn`（F8）を使い、ポート8080との接続の数と状態を見る。次に、読み切ってから `Close` する版で、同じことをする。接続の数はどう違うか。`for` の中に `defer` を書くと、いつ閉じられるか（G6の `defer` の評価タイミング）。閉じるだけで、読み切らない場合は、接続は使い回されるか（`go doc http.Client.Do` の最後の段落と、`go doc http.Response` の `Body` の説明）
3. `internal/apiclient/` に、APIへアイテムを1件POSTする関数を書く。引数に `ctx` を取り（`http.NewRequestWithContext`）、`Client` は呼び出し側から渡す。`Authorization` ヘッダ（G14）を付ける。成功（201）と、それ以外を区別して返す。`httptest.NewServer` で、201を返す相手と、401を返す相手のテストを書く
4. 「最初の2回は503、3回目から201」を返す `httptest` の相手を作る（呼ばれた回数は、G15の `Mutex` で守る）。課題3の関数を、失敗したら100ミリ秒待って最大5回まで送り直す形で包む関数を書き、この相手で3回目に成功することをテストで確かめる。各試行を `slog`（G14）で記録する
5. `internal/backoff/` に、「何回目の失敗か」を受け取って、次に待つ時間を返す関数を書く。1回目1秒、2回目2秒、3回目4秒…と倍にし、上限（例：30秒）を付ける。テーブル駆動テストで、1〜10回目の値を確かめる。上限を外すと、10回目、20回目、30回目の待ち時間は何秒か（`time.Duration` は整数。あふれると何が起きるか）
6. 観察（ジッタ）：止まっている相手（`httptest.NewServer` を `Close` した後のURL）に対して、10個のクライアントを同時に起動し、それぞれの再試行の時刻を記録する（`lab/`）。10個の再試行は、いつ、どのくらい重なるか。`math/rand/v2` で、待ち時間に0〜50%のばらつきを足すと、どう変わるか。相手が復旧した直後に、この10個（本番では100台のagent）が同時に来ると、相手には何が起きるか。ジッタの計算をテストするには、どうすればよいか
7. 再試行するかどうかを、失敗の種類ごとに決める：接続できない、タイムアウト、500、503、400、401、404、409。それぞれについて「再試行する／しない」と理由を `notes.md` に書き、判定する関数にしてテストする。`503` に `Retry-After` ヘッダが付いていたら、何を優先すべきか（MDNで調べる）
8. 冪等性：課題3の関数で、同じ `name` と `value` のアイテムを2回POSTし、`GET /items` の一覧を見る。何件あるか。次に、「サーバーは登録に成功したが、レスポンスが届く前にクライアントがタイムアウトした」場合、再試行すると何が起きるか。`httptest` で「登録してから3秒待って応答する相手」を作り、1秒のタイムアウトのクライアントに再試行させて、相手側の登録件数を数える。自分のクライアントで、これを許容するか、防ぐかを決める（防ぐ方法の候補を2つ挙げ、サーバー側の変更が要るかも書く。実装は発展）
9. 再試行の待ちを、`ctx` で中断できるようにする。`time.Sleep` ではなく、`select` で「タイマーか、`ctx.Done()` か」を待つ（G16）。30秒の待ちの途中で `cancel` すると、すぐに戻り、`ctx.Err()` を含むエラーが返ることをテストする。`time.After` と `time.NewTimer` の違いを `go doc` で読み、どちらを使うか決める
10. **本題**：`cmd/sender/` に、N秒ごと（`flag`）にアイテムをPOSTし続けるプログラムを書く。失敗したら課題5・7・9の方針で再試行し、上限回数を超えたらその回のデータはあきらめて、次の周期に進む。Ctrl+Cで、待ちの途中でも止まる（G16の `signal.NotifyContext`）。動かしたまま、APIをCtrl+Cで止め、30秒ほど待ってから、また起動する。`sender` のログに、何が記録されるか。APIを再起動した後、`sender` を触らずに送信が再開するか。止まっていた間のデータは、何件失われたか。それを許容してよい理由を、卒業制作の非機能要件（`docs/15-track-c-capstone.md`）から探して書く
11. `sender` のテストを書く。「止まっている／動いている」を、テストから切り替えられる `httptest` の相手を作り（フラグを `Mutex` で守る）、止まっている間は失敗し、動かした後の周期で成功することを確かめる。テストが何十秒もかかるなら、周期と待ち時間の基準を、外から小さくできる作りになっているかを見直す。`go test -race` で警告が出ないこと
12. `explain.md` に、何も見ずに書く：`resp.Body` を閉じないと何が起きるか、指数バックオフに上限とジッタが要る理由、再試行してよい失敗とよくない失敗、再試行と冪等性の関係

### 発展（任意）

- `Idempotency-Key` のようなヘッダで、同じ送信を2回受け取ってもサーバーが1件にする仕組みを、G17のAPI側と合わせて作る。キーはどこで作り、サーバーはどこに覚えておくか
- `http.Transport` の各タイムアウト（`go doc http.Transport` のフィールド一覧）を調べ、「ヘッダは返すが本文を少しずつしか送らない相手」に対して、`Client.Timeout` と、どう違う効き方をするかを実験する
- `Retry-After` ヘッダを解釈し、指定された秒数を待つようにする
- 送れなかったデータをメモリにためておき、復旧後にまとめて送る（卒業制作の発展にある機能）。ためる上限は、どう決めるか

## 詰まりやすいところ

- しばらく動かすと `too many open files` や、接続が増え続ける → `Body` を閉じ忘れている経路（エラーのときの早期 `return`）がないかを見る。課題2の `ss` で数える
- テストが、ときどき落ちる → 待ち時間と相手の遅延の差が小さすぎないか（G16の詰まりやすいところ）。テストの中の「呼ばれた回数」が `Mutex` で守られているか
- 再試行しているのに、いつまでも成功しない → 401や400を再試行していないか。ログに、ステータスコードとエラーの文面を出す
- `context deadline exceeded` と `Client.Timeout exceeded` が混ざる → どちらの期限が先に切れたか。`ctx` の期限と `Client.Timeout` の、両方を設定していないか
- Ctrl+Cを押しても、待ちが終わるまで止まらない → `time.Sleep` が残っていないか。`select` で `ctx.Done()` を待っているか
- `httptest.NewServer` を `Close` した後に、まれに成功する → `Close` の前に送ったリクエストの応答が、後から届いていないか
