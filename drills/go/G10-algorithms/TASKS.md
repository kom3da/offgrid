## ねらい

同じ結果を出す2つの書き方が、データが増えたときにどれだけ差が付くかを、自分の計測で示せるようになる。題材は、探索（線形探索と二分探索）と並べ替え（バブルソートと標準の `slices.Sort`）。閉域の現場で「ログが100万行になったら急に終わらなくなった」という問題を前にしたとき、計算量の見積もりと、`testing` パッケージのベンチマークで数字を取る手順が、そのまま武器になる。

## このユニットで身につけること

- 線形探索と二分探索を自分で書き、境界の場合をテストする
- 二分探索の前提（並んでいること）が崩れると何が起きるかを観察する
- 比較の回数を数えて、n と log n の違いを数字で見る
- `testing.B` でベンチマークを書き、`go test -bench` の出力を読む
- バブルソートを自分で書き、`slices.Sort` の結果と一致することをテストで確かめる
- 入力を10倍にしたときの実測値から、O(1)・O(log n)・O(n)・O(n²) を見分ける

## キーワード

- **アルゴリズム**：問題を解く手順。同じ答えを出す手順が複数あり、速さや使うメモリが違う
- **線形探索**：先頭から順に、見つかるまで1つずつ比べる探し方
- **二分探索**：並んだデータの真ん中を見て、探す値がどちら側にあるかで、範囲を半分ずつ狭めていく探し方
- **前提条件**：そのアルゴリズムが正しく動くために、入力が満たしていなければならないこと
- **バブルソート**：隣どうしを比べて、順番が逆なら入れ替える、を繰り返す並べ替え
- **安定な並べ替え**：同じ大きさの要素の、元の順番が保たれる並べ替え
- **ベンチマーク**：同じ処理を何度も実行して、1回あたりの時間を測るテスト。Goでは `testing.B` と `go test -bench`
- **ns/op**：ベンチマークの出力の単位。1回の実行にかかったナノ秒（10億分の1秒）
- **最悪の場合**：そのアルゴリズムがいちばん時間のかかる入力。計算量は、ふつう最悪の場合で言う

`search/` と `sort/` は、`main` のないパッケージにする（G9と同じ）。ベンチマークもテストも、`_test.go` に書く。実験用のデータは、`math/rand` で作る（`go doc rand.Perm` が便利。乱数の種を固定すると、毎回同じデータになる）。

## 課題

1. `search/` に、整数のスライスと探す値を受け取り、見つかった位置（見つからなければ -1）を返す線形探索を書く。テーブル駆動テスト（G7）のケースには、先頭・真ん中・末尾で見つかる、見つからない、空のスライス、同じ値が2つある（どちらの位置が返るか）、を含める
2. 二分探索を書く前に、紙で追う：`[2 5 8 12 16 23 38 56]` から 23 を探すとき、「見ている範囲の左端・右端・真ん中」が、1回ごとにどう変わるかを書く。次に 7 を探した場合も書く。それから、ループで書く（再帰は使わなくてよい）。テストは課題1と同じケースに加えて、要素が1つ、探す値が最小より小さい、最大より大きい、を足す
3. 観察：二分探索に、並んでいないスライスを渡す。正しい位置を返す場合と、返さない場合を、それぞれ1つ見つける。なぜ「並んでいること」が前提なのかを、課題2の紙の手順から説明する。前提を関数の中で確かめる（`go doc slices.IsSorted`）と、何を失うか
4. `go doc slices.Index` と `go doc slices.BinarySearch` を読む。自分の2つの関数と、同じ入力で結果を比べるテストを書く。`slices.BinarySearch` は、見つからなかったとき、2つの戻り値で何を伝えているか。その「位置」は、何に使えるか
5. 比較の回数を数える：2つの探索に、「値を比べた回数」を数える仕組みを足す（戻り値を増やすか、数える用の版を別に書く）。n = 1,000、10,000、100,000、1,000,000 の並んだスライスで、**存在しない値**（最悪の場合）を探し、回数を記録する。nが10倍になると、回数はそれぞれ何倍か。二分探索の回数は、`math.Log2` で計算した値と、どう関係しているか
6. ベンチマーク：`go doc testing.B` を読み、線形探索と二分探索のベンチマークを書く。nを変えたものは、`b.Run` で分ける。データを作る時間は測定に入れない（`go doc testing.B.ResetTimer`）。探す値は最悪の場合にする。`go test -bench . -benchmem -run '^$' ./search` で実行し、出力の各列（回数、ns/op、B/op、allocs/op）が何を表すかを `notes.md` に書く。結果を捨てる書き方だと、コンパイラが計算ごと省くことがある。結果をパッケージ変数に入れておく
7. 課題6の結果を、課題5の比較回数と並べる。ns/op は、比較回数と同じ倍率で増えているか。ずれているなら、何が原因として考えられるか（CPUのキャッシュ、測定の揺れ）。`-count=3` で3回測り、揺れの幅も記録する
8. `sort/` に、バブルソートを書く。テストのケースには、空、要素1つ、すでに並んでいる、逆順、同じ値を含む、負の数を含む、を入れる。さらに、乱数で作った100個のスライスについて、自分のバブルソートの結果と、`slices.Sort` の結果が一致する（`slices.Equal`）ことを確かめるテストを書く。並べ替えは入力を書き換えるので、比べる前に複製が要る（`go doc slices.Clone`）
9. バブルソートと `slices.Sort` のベンチマークを、n = 100、1,000、10,000 で書く。並べ替えは入力を壊すので、1回ごとに複製を渡す必要がある。複製の時間を測定から外す方法を `go doc testing.B` から探す（`StopTimer`／`StartTimer`）か、複製の時間込みで測ることにして、その旨を書く。n = 100,000 のバブルソートは、実行する前に、n = 10,000 の結果から所要時間を見積もる。見積もりに納得してから、実行するか決める（`-benchtime` と `-timeout` を `go help testflag` で調べる）
10. **本題**：課題5〜9の数字を `notes.md` にまとめる（nを10倍にしたとき、それぞれ何倍になったか）。それを根拠に、何も見ずに `explain.md` に書く：O記法とは何か、線形探索・二分探索・バブルソート・`slices.Sort` がそれぞれ何に当たるか、「nが10倍なら時間はどうなるか」を自分の実測値で示す。理論と実測がずれた箇所があれば、それも書く
11. バブルソートに、「1周のあいだ1度も入れ替えなかったら終わる」を足す。すでに並んだ入力と、逆順の入力とで、ベンチマークの結果はどう変わるか。`slices.Sort` は、並んだ入力で速くなるか
12. 並べ替えの安定性：「名前と点数」の構造体のスライスを、点数だけで並べ替える。同じ点数の要素の順番は、`slices.SortFunc` と `slices.SortStableFunc` で違うか（`go doc` で2つの違いを読む）。G11で「件数が同じIPアドレス」の順番を決めるときに、この違いがどう効くかを書く

## 詰まりやすいところ

- 二分探索が終わらない、または1つ隣の位置を返す → 紙の手順に戻る。範囲の右端が「含む」のか「含まない」のかを、ループの条件と真ん中の計算のすべてで、そろえているか
- ベンチマークが `0 ns/op` や、ありえないほど速い → 結果が使われていないので、計算ごと省かれていないか（課題6の最後の一文）
- `go test -bench` を実行しても、ベンチマークが1つも動かない → 関数名の始まりと引数の型を `go doc testing` で見比べる。`-bench` の後ろの正規表現に、何を渡しているか
- ベンチマークの結果が、実行するたびに大きく変わる → 同時に動いている重い処理（ブラウザ、`docker`）を疑う。`-count` で複数回測り、幅を見る
- バブルソートのテストで、期待値のスライスまで並べ替わってしまう → 入力と期待値が、同じ裏の配列を指していないか（G3の、スライスの共有）
- `-benchtime` を伸ばしたら、ベンチマークが `-timeout` で止められた → 既定のタイムアウトを `go help testflag` で調べ、見積もりに合わせる
