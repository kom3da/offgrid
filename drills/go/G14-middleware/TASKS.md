## ねらい

すべてのリクエストに共通する処理（ログ、認証、ヘッダの追加）を、ハンドラの外側に「ミドルウェア」としてまとめる。閉域の現場では、障害が起きても外部の監視サービスには頼れず、手元のログだけが手がかりになる。「いつ、誰が、何を要求し、何番が返ったか」を、機械でも集計できる形で残せるようにする。

## このユニットで身につけること

- `http.Handler` を受け取り、`http.Handler` を返す関数として、ミドルウェアを書く
- 複数のミドルウェアを重ね、重ねる順番で動きが変わることを確かめる
- リクエストごとに一意なIDを付け、レスポンスヘッダとログの両方に出す
- `log/slog` で、キーと値の組からなる構造化ログを出す
- ハンドラが書いたステータスコードを横取りして、アクセスログに記録する
- `Authorization` ヘッダのトークンを確かめ、合わなければ401を返す
- CORSのヘッダを付け、プリフライトリクエストに応答する
- ミドルウェアを、1つずつ単体でテストする

## キーワード

- **ミドルウェア**：ハンドラを包み、前後に処理を足すもの。包んだ結果もハンドラなので、何重にも重ねられる
- **リクエストID**：1つのリクエストに付ける一意な文字列。ログの行を、リクエスト単位でたどるために使う
- **構造化ログ**：文章ではなく、`key=value` やJSONの形で出すログ。`grep` や `jq` で、項目ごとに絞り込める
- **ログレベル**：ログの重要度（`slog` では Debug、Info、Warn、Error）。どこまで出すかを切り替えられる
- **Bearerトークン**：`Authorization: Bearer 文字列` の形で送る合言葉。知っている人だけが、APIを使える
- **オリジン**：スキーム・ホスト・ポートの組。ブラウザは、別のオリジンへの `fetch` の結果を、サーバーの許可なしにはJavaScriptに渡さない
- **CORS**：別のオリジンからの呼び出しを、サーバーがレスポンスヘッダで許可する仕組み
- **プリフライト**：ブラウザが、本番のリクエストの前に自動で送る `OPTIONS` リクエスト。「このメソッドとヘッダで送ってよいか」を尋ねる

## 課題

1. いちばん小さなミドルウェアを書く：次のハンドラを呼ぶ前に `before`、呼んだ後に `after` と標準エラー出力に出すだけのもの。`ServeMux` 全体を包んで起動し、`curl` を1回送って、出力の順番を確かめる
2. 課題1のミドルウェアを、出力する文字を変えて2つ（A、B）作り、Aの中にBを重ねる。出力の順番を、実行する前に予想して `notes.md` に書き、確かめる。重ねる順番を逆にすると、どうなるか。ミドルウェアの中で次のハンドラを呼ばなかったら、クライアントには何が返るか
3. リクエストIDのミドルウェアを書く。推測されにくいIDを、標準ライブラリだけで作る方法を調べる（`go doc crypto/rand`、`go doc encoding/hex`）。IDは、レスポンスの `X-Request-ID` ヘッダに入れる。クライアントが `X-Request-ID` を付けて送ってきたとき、それを信用してそのまま使うか、無視して付け直すかを決め、理由を書く
4. `log/slog` を試す。同じ1行のログを、`slog.NewTextHandler` と `slog.NewJSONHandler` のそれぞれで出し、出力を見比べる。ログレベルをDebugにして出したログは、既定の設定で表示されるか。表示させる方法を `go doc slog.HandlerOptions` で調べる
5. アクセスログのミドルウェアを書く。1リクエストにつき1行、メソッド、パス、ステータスコード、かかった時間、リクエストIDを、JSONで出す。ステータスコードは、`http.ResponseWriter` をそのまま次に渡すだけでは分からない。`http.ResponseWriter` インターフェース（G8）を満たす自分の型で包み、書き込まれた値を覚えておく方法を考える。ハンドラが `WriteHeader` を1回も呼ばずにボディを書いたとき、ログのステータスコードは何になっているべきか
6. 認証のミドルウェアを書く。`Authorization: Bearer <トークン>` が `API_TOKEN` と一致しなければ、401を、G13で決めたエラーレスポンスの形で返す。次を決めて、`api.md` に書く
   - 守る範囲（`/items` 以下は守る。`static/` と `/healthz` は、どうするか）
   - `API_TOKEN` が空のまま起動されたとき、どうふるまうか
   - 401のときに付ける `WWW-Authenticate` ヘッダの役割
7. トークンの比較に `==` を使った場合と、`go doc crypto/subtle.ConstantTimeCompare` を使った場合の違いを調べる。なぜ、後者が用意されているのか。また、アクセスログに `Authorization` ヘッダの値が出ていないことを確かめる
8. CORSのミドルウェアを書く。許可するオリジン（例：`http://localhost:5173`）を設定で渡し、リクエストの `Origin` ヘッダと一致したときだけ、`Access-Control-Allow-Origin` を付ける。`curl -i -H 'Origin: http://localhost:5173'` と、許可していないオリジンとで、レスポンスヘッダを比べる。`Vary` ヘッダは、何のために付けるのか
9. プリフライトを、`curl` で再現する：`-X OPTIONS` に、`Origin`、`Access-Control-Request-Method: POST`、`Access-Control-Request-Headers: authorization, content-type` を付けて `/items` に送る。ブラウザは、プリフライトに `Authorization` ヘッダを付けない。このとき、認証とCORSのミドルウェアを、どちらを外側に重ねると、プリフライトが通るか。逆にすると、何番が返るか。G12のパターン（`GET /items` など）だけを登録した `ServeMux` に、`OPTIONS` が直接届くと、何番が返るか
10. **本題**：4つのミドルウェアそれぞれに、`httptest` で単体テストを書く。次のハンドラには、「呼ばれたかどうか」を記録するだけのダミーを使う。少なくとも、次を確かめる
    - リクエストID：ヘッダが付く。2回呼ぶと、違う値になる
    - アクセスログ：出力先を `bytes.Buffer` に差し替え、1行をJSONとして読み込んで、メソッド・パス・ステータスコードが入っている。`WriteHeader` を呼ばないハンドラ、404を返すハンドラの両方
    - 認証：ヘッダなし、`Bearer` のない形式、違うトークン、正しいトークン。失敗したとき、次のハンドラが呼ばれていない
    - CORS：許可したオリジン、許可していないオリジン、`Origin` なし、プリフライト
11. すべてを重ねてサーバーを起動し、`curl` で正常・401・404を1回ずつ送る。出力されたログをファイルに保存し、`grep` か `jq` で、特定のリクエストIDの行だけ、ステータスコードが400以上の行だけを取り出す（F3）。テキスト形式のログで同じことをする場合と、手間を比べる

### 発展（任意）

- ハンドラの中でpanicが起きても、サーバー全体は落ちないことを確かめる（`net/http` の既定の動き）。そのときクライアントには何が返るか。panicを受け止めて、500を決めた形で返し、Errorレベルでログに残すミドルウェアを書く（`go doc builtin.recover`）
- 任意個のミドルウェアを、読みやすい順番で重ねるための小さな関数を書く
- `static/` のHTMLにも、アクセスログとリクエストIDが付いているかを確かめ、付けるべきかどうかを考える

## 詰まりやすいところ

- アクセスログのステータスコードが、いつも0になる、または実際と違う → ハンドラが `WriteHeader` を呼ばない場合に、`net/http` が何番を返すかを `go doc http.ResponseWriter` で確かめる
- アクセスログにリクエストIDが入らない → 2つのミドルウェアの、重ねる順番を確かめる。IDを、後ろのミドルウェアがどこから読めるかを考える
- プリフライトが401や405になる → 課題9の順番を見直す。`OPTIONS` が、どの層で応答されているかを、課題1の出力で追う
- テストで、ログが画面に出てしまい、`bytes.Buffer` に入らない → ミドルウェアが、どのロガーを使っているかを見る。出力先を、外から渡せる作りになっているか
- 環境変数を設定したのに、トークンが空として扱われる → 設定したシェルと、サーバーを起動したシェルが同じかを確かめる。`export` の有無を確かめる（F5）
- 正しいトークンを送っているのに401になる → `curl -v` で、実際に送られたヘッダの行を見る。`Bearer` の後ろの空白と、引用符の位置を確かめる

## 完了条件の確かめ方

`go vet ./... && go test -race -cover ./...` が通り、`go test -v` の出力に、リクエストID・アクセスログ・認証・CORSの4つのミドルウェアの単体テストが、それぞれ表示される。認証のミドルウェアの中の比較を、わざと「いつも通す」に書き換えると、テストが落ちることを確かめてから、元に戻す。
