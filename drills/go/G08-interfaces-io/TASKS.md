## ねらい

「ファイルから読む」と「標準入力から読む」を、同じ1つの関数で扱えるようになる。Goの標準ライブラリは、`io.Reader` と `io.Writer` という、小さな2つのインターフェースを中心にできている。この2つが分かると、`go doc` だけで標準ライブラリを読み進められるようになり、ファイルを用意しなくても、入出力のあるコードをテストできるようになる。

## このユニットで身につけること

- インターフェースを定義し、複数の型を、同じ変数や引数で扱う
- 「メソッドを持っていれば、宣言なしで満たされる」というGoの仕組みを確かめる
- `io.Reader` と `io.Writer` の定義を読み、それを満たす型を探す
- 読む元を `io.Reader`、書く先を `io.Writer` として受け取る関数を書く
- 文字列とバッファを使って、ファイルなしで入出力をテストする
- `grep` 風のフィルタを作り、本物の `grep` と結果を比べる

## キーワード

- **インターフェース**：「このメソッドを持っていること」という条件だけを決めた型。条件を満たす値なら、どんな型でも入れられる
- **満たす（実装する）**：ある型が、インターフェースの求めるメソッドを、すべて持っていること。Goでは、宣言を書かなくても、自動で判定される
- **`io.Reader`**：バイト列を読み出せるもの。`Read` メソッドを1つだけ持つ
- **`io.Writer`**：バイト列を書き込めるもの。`Write` メソッドを1つだけ持つ
- **`fmt.Stringer`**：`String()` メソッドを持つもの。`fmt` の表示に使われる
- **フィルタ**：入力を受け取り、加工して出力するプログラム（F3）
- **`bytes.Buffer`**：メモリの上の、読み書きできる入れ物。`io.Reader` も `io.Writer` も満たす

## 課題

1. `lab/` で、面積を返すメソッドを持つ、長方形と円の2つの構造体を作る。「面積を返すメソッドを持つ」というインターフェースを定義し、2つをそのインターフェースのスライスに入れて、ループで面積を表示する。片方の型からメソッドを消すと、コンパイラは何と言うか。「この型は、このインターフェースを満たす」という宣言を、どこかに書いたか
2. G4の口座の構造体（写してよい）に、`String()` メソッドを付ける。`fmt.Println` の表示は、どう変わるか。`go doc fmt.Stringer` を読み、なぜ変わるのかを説明する。レシーバをポインタにした場合、値を渡したときと、ポインタを渡したときとで、表示はどう違うか
3. `go doc io.Reader` と `go doc io.Writer` を読む。メソッドは、それぞれいくつあるか。次のものが、どちらを満たすかを `go doc` で確かめて、一覧にする：`*os.File`、`os.Stdin`、`os.Stdout`、`strings.NewReader` の戻り値、`*bytes.Buffer`
4. `io.Reader` を受け取って、行数を返す関数を書く。同じ関数に、開いたファイル、`os.Stdin`、`strings.NewReader` で作った値を渡して、どれでも動くことを確かめる（`bufio.NewScanner` の引数の型を、`go doc` で見る）
5. `io.Writer` を受け取って、九九の表を書き出す関数を書く（`go doc fmt.Fprintf`）。`os.Stdout`、`os.Create` で作ったファイル、`*bytes.Buffer` を渡す。`bytes.Buffer` に書いた内容を、文字列として取り出して、長さを表示する
6. `mygrep` の中心になる関数を書く：読む元を `io.Reader`、書く先を `io.Writer`、探す文字列を引数で受け取り、その文字列を含む行だけを書き出す。エラーは、`error` で返す。この関数のテーブル駆動テストを、ファイルを使わずに書く（入力は文字列から、出力はバッファで受ける）。ケースには、一致なし、全行一致、空の入力、最後の行に改行がない、を含める
7. `main` を書く。使い方は `mygrep [オプション] 文字列 [ファイル...]`。ファイルの指定がなければ、標準入力から読む。複数のファイルが指定されたら、本物の `grep` と同じように、行の前にファイル名を付ける。引数が足りなければ、使い方を標準エラー出力に出す
8. オプションを足す：`-n`（行番号）、`-v`（含まない行）、`-i`（大文字と小文字を区別しない）、`-c`（件数だけ）。それぞれに、テストを足す。オプションが増えたとき、中心の関数の引数をどうまとめるかを考える（G4の構造体）
9. 終了コードを、本物に合わせる。`man grep` の終了ステータスの説明を読み、「一致あり」「一致なし」「エラー」のそれぞれで、`echo $?` を比べる
10. **本題**：ビルドした `mygrep` と本物の `grep` の出力を、`diff` で比べる。次の場合で、すべて差がないこと（`grep` 側には、正規表現ではなく文字列として探すオプションを付ける。`man grep` で探す）
    - ファイルを指定：`" 404 "` を `testdata/access.log` から探す
    - 標準入力：同じ検索を、`cat` からのパイプと、`<` のリダイレクトで行う
    - `-n`、`-v`、`-i`、`-c` を、それぞれ付ける
    - 2つのファイル（`access.log` と `small.log`）を指定する
11. G5の `mywc` の、数える関数を、`io.Reader` を受け取る形に書き直す。G7で書いたテストのうち、`testdata/` のファイルを使わなくて済むようになるのは、どれか。書き直す前と後で、`compare.sh` の結果が変わらないことを確かめる

### 発展（任意）

- 文字列ではなく、正規表現で探す `-E` を足す（`go doc regexp`）。F3の課題8のパターンで、本物の `grep -E` と比べる
- `go doc io` の一覧から、`io.Copy`、`io.MultiWriter`、`io.TeeReader` を読む。`mygrep` の出力を、画面とファイルの両方に、同時に書くようにする
- 読んだバイトを、すべて大文字にして返す `io.Reader` を、自分で作る（A Tour of Goの、Readersの練習問題が参考になる）
- `nil` のポインタを `error` 型の戻り値として返すと、呼び出した側の `err != nil` は、どうなるか。予想してから確かめ、Goの公式FAQの「nil error」の項目を読む

## 詰まりやすいところ

- `does not implement ...（missing method ...）` と出る → メッセージにあるメソッドの名前、引数、戻り値を、インターフェースの定義と、1文字ずつ見比べる
- `method has pointer receiver` と出る → メソッドのレシーバが、値かポインタか。渡しているのが、値か、`&` を付けたポインタかを確かめる（G4）
- テストでは通るのに、端末で動かすと、何も出ずに止まる → 標準入力を待っていないか。引数の数え方（フラグを除いた残り）を確かめる
- 出力が、最後の1行だけ `grep` と違う → 入力の最後の行に改行がない場合に、それぞれが何を出力するかを、`od -c` で見る
- `-i` で一致しない → 大文字と小文字をそろえるのを、探す文字列と、行の、両方に行っているか。出力する行まで、書き換えていないか
- `diff` で、ファイル名の付き方だけが違う → ファイルが1つのときと、2つ以上のときの `grep` の出力を、もう一度見る

## 完了条件の確かめ方

```sh
go vet ./... && go test -race -cover ./...
go build -o mygrep ./mygrep
./mygrep ' 404 ' testdata/access.log | head -3
./mygrep ' 404 ' < testdata/access.log | head -3
```

- テストがすべて通り、`mygrep` のパッケージのカバレッジが80%以上
- 標準入力とファイルの、両方で動く。課題10の比較を、シェルスクリプト `compare.sh` にまとめてあり、すべての場合で、差がなく、終了コードも一致する
