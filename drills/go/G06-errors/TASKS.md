## ねらい

失敗したときに、「何が・どこで・なぜ」失敗したかが伝わるプログラムを書けるようになる。閉域の現場で障害が起きたとき、手がかりは、プログラムが出したエラー文だけになる。`error: invalid value` とだけ出すツールと、ファイル名と項目名まで出すツールとでは、調査にかかる時間がまるで違う。

## このユニットで身につけること

- `error` を返す関数を書き、呼び出した側で必ず確かめる
- `errors.New` と `fmt.Errorf` でエラーを作る
- `%w` で、元のエラーを包んで（ラップして）、文脈を足す
- `errors.Is` で、エラーの種類を判定する
- 自分でエラーの型を作り、`errors.As` で取り出す
- ファイル名・行番号・項目名を含むエラー文を組み立てる
- エラーを握りつぶさない（`_` で捨てない）

## キーワード

- **`error`**：Goでエラーを表す型。`Error()` というメソッドを持つ値なら、何でも `error` として扱える（この仕組みはG8で詳しく学ぶ）
- **ラップ**：元のエラーを中に持ったまま、説明を足した新しいエラーを作ること。`fmt.Errorf` の `%w` で行う
- **センチネルエラー**：`os.ErrNotExist` のように、あらかじめ変数として用意された、比較のためのエラー
- **`errors.Is`**：エラーが、特定のエラーと同じか（包まれた中身も含めて）を調べる
- **`errors.As`**：エラーの中から、特定の型のエラーを探して取り出す
- **文脈**：エラーに足す、「何をしようとしていたか」の情報（ファイル名、行番号、項目名など）
- **panic**：続行できない異常で、プログラムが止まること。ふつうの失敗には `error` を使い、panicは使わない


本題のローダーが読む設定ファイルは、1行に1項目の `項目名=値` の形式にする。`#` で始まる行と、空行は無視する。項目は次の4つ。

- `host`：文字列。必須（値はダミーにする。例：`app.test`）
- `port`：整数。1〜65535
- `timeout_sec`：整数。0以上
- `debug`：真偽値（`true` か `false`）

`testdata/` に、正しいファイル `good.conf` を、自分で書いて置く。

## 課題

1. 存在しないファイルを `os.Open` で開き、返ってきたエラーを `%v`、`%T`、`%#v` で表示する。エラーの本当の型は何か。その型が持っているフィールドを、`go doc` で調べる
2. 文字列を受け取り、ポート番号として正しければ `int` を、正しくなければ `error` を返す関数を書く（`go doc strconv.Atoi`）。`"8080"`、`"abc"`、`"0"`、`"70000"`、`""` を渡して、結果を表示する。呼び出した側は、必ず、エラーを先に確かめる形にする
3. 課題1のエラーに、`fmt.Errorf` で「設定を読み込めない」という説明を足して返す関数を書く。`%v` で足した場合と、`%w` で足した場合とで、`errors.Is(err, os.ErrNotExist)` の結果はどう変わるか。なぜか。`errors.Unwrap` の結果も、それぞれ表示する
4. 「値が範囲の外」を表すセンチネルエラーを、自分で1つ定義する。課題2の関数から、それを `%w` で包んで返す。呼び出した側で、`==` で比べた場合と、`errors.Is` で比べた場合の結果の違いを確かめる
5. `strconv.Atoi("abc")` が返すエラーから、`errors.As` で `*strconv.NumError` を取り出し、フィールドを表示する。`errors.As` の2つ目の引数には、何を渡す必要があるか。間違えると、どうなるか
6. 自分のエラー型を作る：ファイル名、行番号、項目名、元のエラーを持つ構造体に、`Error()` メソッドを付ける。`errors.Is` と `errors.As` が、中の「元のエラー」までたどれるようにするには、もう1つ、どんなメソッドが要るか。`go doc errors` の説明文から探す
7. 設定を入れる構造体と、ファイルのパスを受け取って、その構造体と `error` を返すローダーを、`config/` に書く（`main` と同じ `package main` でよい。ファイルは分けてもよい）。まず、`good.conf` を読んで、4項目を表示できるようにする（ファイルの読み方はG5）
8. **本題**：次の3つの場合に、ローダーが返すエラー文に、**ファイル名と項目名**（ファイルが存在しない場合は、ファイル名）が含まれるようにする。それぞれの設定ファイルを `testdata/` に作る。`main` には、`-v` フラグを付けたときだけ、下の `errors.Is` と `errors.As` の判定結果を1行ずつ表示する処理を足す
   - 存在しないファイル：`errors.Is` で `os.ErrNotExist` と判定できる
   - 不正な値（`port=70000`）：`errors.Is` で、課題4のセンチネルエラーと判定できる
   - 型違い（`port=abc`）：`errors.As` で、課題6の型と `*strconv.NumError` の両方を取り出せる
9. 次の場合にも、行番号つきのエラーにする：`=` がない行、知らない項目名、同じ項目が2回ある、必須の `host` がない（この場合、行番号はどうするか）、`debug=yes`
10. `main` では、エラーを標準エラー出力に1行で出し、終了コード1で終わる。存在しないファイルのときだけ、「`-init` を付けると、ひな形を作れる」のような案内を足す（案内を出すだけでよい。判定は `errors.Is`）。エラー文が `config: config: open ...` のように、くどくなっていないかを見直す
11. `defer` の観察：`defer` で変数を表示する文を書き、そのあとで変数の値を変える。表示されるのは、どちらの値か。`defer` を3つ書くと、どの順で実行されるか。予想してから確かめる
12. 自分のコード（G5も含む）に、エラーを捨てている場所がないかを探す。`_ =` や `_ :=` を `grep` で探し、戻り値の `error` を受け取っていない呼び出しを、目で探す。見つけたものを、どう直すかを決める

## 詰まりやすいところ

- `errors.Is` が `false` になる → 途中で包むときに使った書式が、`%w` か `%v` かを確かめる。自分のエラー型に、中身をたどるためのメソッドがあるかを確かめる
- `errors.As` でpanicする、または、いつも `false` になる → 2つ目の引数の型を見る。`Error()` メソッドのレシーバが値かポインタか（G4）と、取り出そうとしている型が合っているかを確かめる
- `declared and not used: err` と出る、または、古いエラーを調べてしまう → `:=` で、`err` を新しく作り直していないか。G2のスコープを思い出す
- 行番号が1つずれる → 数え始めの値と、コメント行・空行でも数を増やしているかを確かめる
- エラー文に同じ言葉が何度も出る → 各関数が「自分のしていたこと」だけを足しているかを、呼び出しの順に並べて見る
- `port= 8080` のような、空白の入った行で失敗する → 値の前後の空白をどう扱うかを決める。`go doc strings` で、取り除く関数を探す

## 完了条件の確かめ方

```sh
go vet ./...
go run ./config testdata/no-such-file.conf; echo "exit=$?"
go run ./config testdata/bad-range.conf;    echo "exit=$?"
go run ./config testdata/bad-type.conf;     echo "exit=$?"
```

（ファイル名は、自分で付けたものに読み替える。）3つとも、エラー文は標準エラー出力に出て、終了コードは0以外。1つ目のエラー文にはファイル名が、2つ目と3つ目にはファイル名と `port` が含まれる（`2>&1 | grep` で確かめる）。`-v` を付けて実行すると、課題8の `errors.Is` と `errors.As` の判定結果が表示され、すべて期待どおりになる。テストにするのは、G7で行う。
