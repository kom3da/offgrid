## ねらい

自分のコードが正しいことを、テストで確かめられるようになる。そして、正しくないときに、原因の行まで自力でたどり着けるようになる。AIに「このエラーを直して」と頼めない環境では、失敗したテストの出力とスタックトレースを読む力が、そのまま直す速さになる。ステージ通過の実技も、「元のテストがすべて通る」ことで合否を決める。

## このユニットで身につけること

- `_test.go` にテストを書き、`go test` で実行する
- 入力と期待する結果を並べた、テーブル駆動テストを書く
- テスト用のファイルを `testdata/` に置いて使う
- カバレッジを測り、テストが通っていない行を見つける
- テストしやすいように、処理を `main` から切り出す
- 失敗したテストの出力と、panicのスタックトレースから、原因の行を特定する
- printデバッグと、デバッガ `dlv` で、実行中の変数の値を確かめる

## キーワード

- **テスト**：コードが期待どおりに動くかを確かめるための、別のコード。Goでは、`testing` パッケージと `go test` を使う
- **テーブル駆動テスト**：テストケース（名前、入力、期待する結果）をスライスに並べ、ループで1つずつ確かめる書き方
- **サブテスト**：`t.Run` で、名前を付けて分けた、小さなテスト。失敗したケースが、名前で分かる
- **カバレッジ**：テストの実行中に、コードの何％の文が通ったかの割合
- **`testdata/`**：テスト用のファイルを置くディレクトリ。`go` コマンドは、この名前のディレクトリを、パッケージとして扱わない
- **スタックトレース**：プログラムが止まった時点で、どの関数が、どの関数から呼ばれていたかの記録
- **printデバッグ**：変数の値を途中で表示して、動きを確かめる方法
- **デバッガ**：プログラムを途中で止めて、1行ずつ進めたり、変数を見たりする道具。Goでは `dlv`（Delve）

## 課題

1. `first/` に、G2の素数判定の関数を写し、`first/prime_test.go` に、最初のテストを1つ書く（テスト関数の名前と引数の決まりは `go doc testing`）。`go test ./first` と `go test -v ./first` の出力の違いを見る。次に、期待する値をわざと間違えて、失敗させる。出力のどこに、ファイル名、行番号、自分で書いたメッセージが出るか
2. `t.Errorf` と `t.Fatalf` の違いを、1つのテストの中に確認を3つ並べて、確かめる。失敗のメッセージには、「入力・実際の値・期待した値」の3つを入れる。入れなかった場合と比べて、何が困るか
3. 課題1のテストを、テーブル駆動に書き直す。ケースには、0、1、2、負の数、大きな素数、大きな合成数を含める。`t.Run` でケースに名前を付け、`go test -v` の出力と、`go test -run` で1つのケースだけを実行する方法を確かめる
4. カバレッジ：`go test -cover ./first` の数字を見る。`-coverprofile` でファイルに書き出し、`go tool cover` で、通っていない行を表示する（関数ごとの一覧と、HTMLでの表示の、2つのオプションを `go tool cover -help` で探す）。テストケースを1つ消すと、数字と、色の付く行はどう変わるか
5. G2にテストを付ける。FizzBuzzが、画面に表示するだけの作りになっていたら、「数を受け取って、文字列を返す関数」と「それを呼んで表示する `main`」に分けてから、テストを書く。九九も、同じ考え方で分ける。分ける前と後で、プログラムの出力が変わっていないことを、G2で保存した `.txt` との `diff` で確かめる
6. G3（単語の集計）とG4（銀行口座）にテストを付ける。G4は、失敗する場合（残高不足、0以下の額、同じ口座への振込）を必ず含める。スライスやマップの結果を比べる方法を、`go doc slices.Equal`、`go doc maps.Equal`、`go doc reflect.DeepEqual` で調べる
7. G5（`mywc`）にテストを付ける。数える処理を、`main` から関数に切り出し、`testdata/` の小さなファイル（空、改行なしで終わる、日本語を含む）で確かめる。テストの実行中のカレントディレクトリは、どこになるか。`testdata/` への相対パスは、どこから見た道順で書けばよいか
8. G6（設定ローダー）にテストを付ける。正常な場合と、3つの異常な場合（存在しない、不正な値、型違い）に加えて、G6の課題9の場合も入れる。エラーの確認は、エラー文の文字列を丸ごと比べるのではなく、`errors.Is` と `errors.As`、それと「ファイル名と項目名を含むか」（`go doc strings.Contains`）で行う。なぜ、丸ごと比べないほうがよいか
9. **本題**：G2〜G6のそれぞれのディレクトリで、`go test -cover ./...` のカバレッジが80%以上になるまで、テストを足す。通っていない行を `go tool cover` で見て、「テストを足すべき行」か、「`main` を薄くして、外に出すべき処理」かを、1つずつ判断する
10. panicを読む：`crash/main.go` に、`main` → 関数A → 関数B → 関数Cと呼び出し、Cの中で、範囲の外のスライスの要素を読むプログラムを書く。表示されたスタックトレースを `notes.md` に貼り、次を読み取る：panicのメッセージ、止まった行、呼び出しの順番、各行のファイル名と行番号。`nil` のマップへの書き込みと、`nil` のポインタの先を読む場合でも、同じことをする（`goroutine 1 [running]` という行は、G15で学ぶ。今は「`main` から始まった流れ」と読んでおく）
11. printデバッグ：テストを付ける途中で見つかった、自分のバグを1つ選ぶ（なければ、G2〜G6のどれかの条件式を、わざと1か所変える）。先に、仮説を `notes.md` に書く。それから、`fmt.Fprintf(os.Stderr, ...)` か、テストの中の `t.Logf` で、値を表示して確かめる。終わったら、表示の行を消す。`git diff` で、消し忘れがないかを見る
12. `dlv`：`dlv debug ./crash` で起動し、`help` を読む。次の操作を、それぞれ試す：関数Cにブレークポイントを置く、そこまで実行する、1行進める、関数の中に入る、変数を表示する、ローカル変数の一覧を見る、スタックを表示する、終了する。`dlv test` で、テストを対象に、同じことをする

### 発展（任意）

- `go test -run` と `-count=1` の意味を `go help testflag` で調べる。`(cached)` と表示されるのは、どんなときか
- テストの中で使う補助の関数に、`t.Helper()` を付けた場合と、付けない場合とで、失敗したときに表示される行番号はどう変わるか
- 一時ディレクトリを使うテストを書く（`go doc testing.T.TempDir`）。`mywc` に、テストの中で作ったファイルを読ませる
- `main` まで含めて確かめるために、ビルドした実行ファイルを、シェルスクリプト（F5）からテストする。G5の `compare.sh` との役割の違いを考える

## 詰まりやすいところ

- `[no test files]` のままになる、またはテストが実行されない → ファイル名の終わり、関数名の始まり、引数の型を、`go doc testing` の説明と見比べる
- カバレッジが上がらない → `go tool cover` で通っていない行を見る。`main` 関数と、`os.Exit` を呼ぶ行が、多くを占めていないか
- テストから `testdata/` のファイルが見つからない → テストの中で、カレントディレクトリを表示してみる（`go doc os.Getwd`）
- マップを使う関数のテストが、通ったり、通らなかったりする → G3の課題8を思い出す。順番に頼った比べ方をしていないか
- スタックトレースが長くて、どこを見ればよいか分からない → 自分のファイル名が出ている行だけを、上から拾う。いちばん上が、止まった場所
- `dlv` で、変数が表示されない、または、行が飛ぶ → `dlv` に起動を任せているか（自分で `go build` したものを渡していないか）を確かめる。`dlv help` で、起動のしかたの違いを読む
- `-race requires cgo` と出る → G1の「詰まりやすいところ」を見る

## 完了条件の確かめ方

G2〜G6のそれぞれのディレクトリで、次を実行する。

```sh
go vet ./... && go test -race -cover ./...
```

- すべてのテストが通り、表示される `coverage:` が、どのパッケージでも80%以上（`lab/` のような観察用のパッケージは、対象から外してよい。外したものは `notes.md` に書く）
- どのユニットのテストも、テーブル駆動のテストを1つ以上含み、異常な場合のケースがある
- 課題10の3種類のスタックトレースについて、止まった行と、呼び出しの順番を `notes.md` に書いてある

`-race` は、並行処理の問題を見つけるためのオプション。意味はG15で学ぶ。今は、付けたままにしておけばよい。
