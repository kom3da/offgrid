## ねらい

Goの標準ライブラリ `net/http` だけで、データの登録・取得・更新・削除（CRUD）ができるWeb APIを作る。閉域の現場では、Webフレームワークを後から入れられないことが多い。標準ライブラリだけで書ける力があれば、Goが入っている環境ならどこでもAPIを立てられる。ここで作るAPIは、T4（フロントエンド）、G13〜G20、卒業制作の土台として、何度も使い回す。

## このユニットで身につけること

- `net/http` でサーバーを起動し、`curl` で応答を確かめる
- `ServeMux` に、メソッドとパスのパターン（`GET /items/{id}` の形）でハンドラを登録する
- パスの中の値（`{id}`）を取り出し、数値に変換し、失敗したときの応答を決める
- ステータスコードとヘッダを、操作の意味に合わせて選ぶ（200、201、204、400、404、405）
- HTTPの処理と、データを持つ部分（ストア）を分けて書き、ストアだけをテストする
- 同じサーバーから、静的ファイル（HTML）のディレクトリも配信する

## キーワード

分からない語は、まず `go doc net/http.名前` で調べる。

- **ハンドラ**：1つのリクエストを受け取り、レスポンスを書く関数や型。`http.Handler` インターフェースを満たすもの
- **ServeMux（マルチプレクサ）**：リクエストのメソッドとパスを見て、どのハンドラに渡すかを決める振り分け役
- **パターン**：`ServeMux` に登録する文字列。Go 1.22から、メソッドと `{名前}` の形のワイルドカードを書ける
- **REST**：URLで「もの（リソース）」を表し、HTTPのメソッドで「操作」を表すAPIの設計の考え方
- **CRUD**：Create（作る）、Read（読む）、Update（更新する）、Delete（消す）の4つの操作
- **冪等（べきとう）**：同じリクエストを何回送っても、結果が同じになる性質
- **インメモリ**：データをファイルやDBではなく、プログラムの変数（メモリ上）に持つこと。プログラムを止めると消える
- **同一オリジン**：スキーム・ホスト・ポートの3つが同じであること。T4で、ブラウザの制限に関わってくる

## 準備

このディレクトリで作業する。扱うデータは「アイテム」。1件は、`id`（サーバーが付ける整数）、`name`（文字列）、`value`（数値）を持つことにする。

```sh
go mod init offgrid/g12-net-http
mkdir static
printf '<h1>offgrid</h1>\n' > static/index.html
go version   # 1.22以上であることを確かめる
```

作るエンドポイントは、`GET /items`（一覧）、`POST /items`（登録）、`GET /items/{id}`（1件取得）、`PUT /items/{id}`（更新）、`DELETE /items/{id}`（削除）の5つ。シェルを2つ開き、片方でサーバーを動かし、もう片方から `curl -i` で確かめる。

## 課題

1. `GET /healthz` に `ok` と返すだけのサーバーを書き、`localhost:8080` で起動する。`curl -i` で、ステータス行・ヘッダ・ボディを読む（F9の復習）。サーバーをもう1つ同じポートで起動すると、何が起きるか。`http.ListenAndServe` の戻り値を捨てていると、そのとき何が見えなくなるか
2. `go doc http.Handler`、`go doc http.HandlerFunc`、`go doc http.ResponseWriter` を読む。ハンドラの中で、「ボディを書いた後にステータスコードを設定する」と、`curl -i` の結果とサーバー側の出力はどうなるか。ヘッダ、ステータスコード、ボディは、どの順で書く必要があるか。なぜか（F9で見た、HTTPのレスポンスの形から考える）
3. パターン構文を試す。`GET /items/{id}` だけを登録し、`id` の値をそのまま返すハンドラを書く。次のリクエストの結果を、予想してから確かめる
   - `GET /items/42`、`GET /items/abc`、`GET /items/`、`GET /items/1/2`
   - `POST /items/42`（ステータスコードは何か。レスポンスの `Allow` ヘッダには何が入っているか）
   - 登録するパターンからメソッドを外すと、上の結果はどう変わるか
4. アイテムを表す型と、それをメモリ上に持つ「ストア」の型を作る。ストアには、登録・1件取得・一覧・更新・削除の操作を持たせ、`net/http` をimportしないファイルに書く。「見つからない」ことを、呼び出し側が `errors.Is` で見分けられるようにする（G6）。ストアのテーブル駆動テストを書く（G7）
5. `GET /items` と `GET /items/{id}` を実装する。レスポンスはJSONにし、`Content-Type` を正しく付ける。存在しない `id` のとき、`id` が数値でないとき、それぞれ何番を返すべきかを決め、理由を `notes.md` に書く
6. `GET /items` を何回か呼び、並び順が毎回同じかを確かめる。違うなら、なぜか（G3）。いつも `id` の小さい順に返るようにする
7. `POST /items` を実装する。成功したら201を返し、作ったアイテムをボディで返す。`Location` ヘッダは、何のためにあるか調べて付ける。JSONとして壊れたボディを送ったときは400を返す（項目ごとの細かい検証は、G13でやる）
8. `PUT /items/{id}` と `DELETE /items/{id}` を実装する。同じ `DELETE` を2回送ると、1回目と2回目の応答はどうなるか。`PUT` と `POST` を、それぞれ2回ずつ送ったときの一覧の違いを確かめ、「冪等」という言葉で説明する
9. **本題**：5つのエンドポイントすべてについて、正常な場合と失敗する場合の `curl` コマンドと、期待するステータスコードを `api.md` にまとめる。それを上から順に実行して確かめるシェルスクリプト `check.sh` を書く（F5。`curl` の `-s`、`-o`、`-w` はF9で使った）。サーバーを起動し直した直後の状態で、期待と1つでも違えば、終了コードが0以外になるようにする
10. `static/` の中身を、同じサーバーの `/` から配信する（`go doc http.FileServer`、`go doc http.Dir`）。ブラウザで `http://localhost:8080/` を開いて確かめる。`/` を登録しても、`GET /items` がAPIのハンドラに届くのはなぜか。`go doc http.ServeMux` の、優先順位の説明を読んで書く。`GET /nonexistent` は、どちらが応答しているか
11. `static/` の外にあるファイル（例：`main.go`）を、URLの工夫で読み出せないかを試す。`man curl` で `--path-as-is` の意味を調べ、`/../main.go` を要求する。結果はどうなるか。`static/` の中に `.env` のようなファイルを置くと、どうなるか。配信するディレクトリに置いてよいものの決まりを、`notes.md` に書く
12. サーバーを止めて起動し直すと、登録したデータはどうなるか。それで困る場面と、困らない場面を1つずつ挙げる（G17でPostgreSQLに置き換える）

### 発展（任意）

- `name` の一部で一覧を絞り込めるようにする（`GET /items?q=abc`）。クエリ文字列の取り出し方を `go doc net/url.Values` で調べる
- `http.ListenAndServe` に渡すアドレスを `:8080` にした場合と `127.0.0.1:8080` にした場合の違いを、`ss -ltn`（F8）で確かめる
- ポート番号と `static/` の場所を、`flag`（G5）で変えられるようにする
- `HEAD /items` を送ると、何が返るか。自分で登録していないのに応答があるなら、なぜかを `go doc http.ServeMux` で調べる

## 詰まりやすいところ

- 起動時にpanicする（patternが衝突している、という内容） → 登録したパターンを並べ、同じリクエストに、同じ具体さで当たるものが2つないかを見る
- `curl -X POST -d '...'` で送ったJSONが読めない、または想定と違う `Content-Type` で届く → `curl -v` で、実際に送られたヘッダを見る。`-H` の使い方はF9
- `{id}` が空文字列になる → パターンの `{ }` の中の名前と、取り出すときに渡している名前を見比べる。取り出すメソッドは `go doc http.Request` の一覧から探す
- レスポンスのJSONが `{}` になる、または項目が出てこない → 構造体のフィールド名の、先頭の文字を見る。`go doc encoding/json.Marshal` の、どのフィールドが出力されるかの説明を読む
- ヘッダを設定したのに、`curl -i` に出てこない → ヘッダを設定した行と、ステータスコードやボディを書いた行の、順番を見る
- ブラウザで `/` を開くと、`index.html` ではなくファイルの一覧が出る、または404になる → サーバーを起動したときのカレントディレクトリと、`http.Dir` に渡したパスの関係を疑う

## 完了条件の確かめ方

サーバーを起動し直し、`./check.sh` を実行する。5つのエンドポイントの正常系・異常系がすべて期待どおりで、終了コードが0になる。ブラウザで `http://localhost:8080/` を開くと、`static/index.html` が表示される。`go vet ./... && go test -race -cover ./...` が通る。

## 次につながるユニット

- G13（JSON・入力検証・テスト）：このAPIに、入力の検証と、`httptest` を使ったハンドラのテストを足す
- T4（非同期処理）：`static/` に置いたHTMLとJavaScriptから、このAPIを `fetch` で呼ぶ。同じサーバーから配信するので、同一オリジンになる
- G15（goroutineとchannel）：`net/http` は、リクエストを同時に処理している。今回のストアが同時アクセスに耐えられるかを、`go test -race` で確かめ直す
