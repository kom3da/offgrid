## ねらい

複数の仕事を同時に進めるプログラムを、安全に書けるようになる。題材は、複数のURLが生きているかを確かめる死活監視。1件ずつ順番に確かめると、遅い相手が1つあるだけで全体が待たされる。並行処理のバグは、たまにしか起きず、再現しにくい。だから「動いた」で終わらせず、`go test -race` という道具で確かめる習慣を、ここで付ける。

## このユニットで身につけること

- `go` 文でgoroutineを起動し、`sync.WaitGroup` で終わるのを待つ
- 複数のgoroutineが同じ変数を書き換えると何が起きるかを観察し、`-race` の報告を読む
- `sync.Mutex` で、共有するデータを守る
- channelで、goroutineの間に値を受け渡す。バッファの有無と、`close` の意味を確かめる
- 決まった数のワーカーに仕事を配る「ワーカープール」を作る
- 並行数を変えて、かかる時間を実測する
- デッドロックと、閉じ忘れたchannelでの待ち続けを、症状とエラーメッセージから見分ける

## キーワード

- **goroutine**：Goのランタイムが管理する、軽い実行の単位。関数呼び出しの前に `go` を付けると、呼び出し元と並行に動く
- **並行と並列**：並行は、複数の仕事を切り替えながら進める「構造」のこと。並列は、複数のCPUコアで、本当に同時に実行すること
- **データ競合（data race）**：複数のgoroutineが、同じ変数に同時にアクセスし、少なくとも片方が書き込みであること。結果が予測できなくなる
- **`sync.WaitGroup`**：「あと何個のgoroutineが終わっていないか」を数え、0になるまで待つための型
- **`sync.Mutex`**：同時に1つのgoroutineだけが通れる鍵。`Lock` から `Unlock` までの間は、他のgoroutineが待たされる
- **channel**：goroutineの間で値を受け渡すための管。送る側と受け取る側の、待ち合わせにもなる
- **バッファ付きchannel**：決まった個数まで、受け取り手がいなくても送れるchannel
- **ワーカープール**：決まった数のgoroutine（ワーカー）が、1つのchannelから仕事を取り出して処理する構成
- **デッドロック**：互いに相手を待ち続けて、どれも先に進めなくなった状態
- **レース検出器**：`-race` を付けると有効になる、データ競合を実行時に見つける仕組み。G1からコマンドに付けてきた `-race` の正体

## 課題

1. `main` の中で、「1秒待ってから1行出力する関数」を、`go` を付けて起動する。何が出力されるか。`go` を外すと、どうなるか。違いの理由を、「`main` が終わると、プログラムはどうなるか」から説明する
2. 課題1を、`sync.WaitGroup` で「終わるまで待つ」ように直す。同じ関数を10個起動し、全部が終わるまでの時間を測る（`time.Since`）。10秒か、約1秒か。出力の順番は、毎回同じか
3. 1つの整数の変数を、1000個のgoroutineから1ずつ増やす。全部終わった後の値を、何回か実行して記録する。1000にならない回はあるか。同じプログラムを `go run -race` で実行し、報告を読む：どのファイルの何行目の「読み」と「書き」がぶつかったと書かれているか
4. 課題3を、`sync.Mutex` で直す。`-race` の報告が消えること、結果がいつも1000になることを確かめる。`Unlock` を書き忘れると、何が起きるか。`defer`（G6）と組み合わせる書き方も試す
5. 1つのmapに、複数のgoroutineから同時に書き込むプログラムを書いて、実行する。`-race` を付けない場合でも、何が起きるか。エラーメッセージを記録する
6. channelを試す。バッファなしのchannelに、`main` の中で値を送り、その後で受け取るプログラムを書く。何が起きるか。エラーメッセージを読む。バッファを1にすると、どうなるか。送る側が `close` したchannelを、`for range` で受け取るとどうなるか。`close` しないと、どうなるか
7. URLを1つ受け取り、GETして、「URL、ステータスコード、かかった時間、エラー」を1つの結果として返す関数を書く。1件の確認に上限時間（例：2秒）を付ける方法を、`go doc http.Client` のフィールドの一覧から探す（詳しくはG19）。`httptest.NewServer` で、すぐ200を返す相手、500を返す相手、3秒待たせる相手、すでに `Close` した相手を用意し、テーブル駆動テストを書く
8. 課題7の関数を、URLの一覧に対して、順番に1件ずつ呼ぶ版を書く。300ミリ秒待ってから応答する相手を20個ぶん並べた一覧で、全体にかかる時間を測る
9. **本題**：ワーカープール版を書く。仕事（URL）を流すchannelと、結果を流すchannelを用意し、決まった数（N）のワーカーが仕事を取り出して、課題7の関数を呼ぶ。Nは `flag`（G5）で変えられるようにする。次を、`notes.md` に書く
   - 仕事のchannelは、誰が、いつ `close` するか。結果のchannelは、誰が、いつ `close` するか
   - 全ワーカーの終了を、どこで待つか
   - 結果は、一覧と同じ順番で返ってくるか
10. 課題8の一覧を、N = 1、2、5、20 で実行し、かかった時間を記録する。Nを増やすほど速くなるか。Nを相手の数より大きくしても、意味があるか。相手を本物のサーバーだと考えたとき、Nを大きくしすぎると、相手には何が起きるか
11. 結果を「URL → 最新の結果」のmapにためる版を、2通り書く。(a) 各ワーカーが、`Mutex` で守ったmapに直接書く。(b) 結果はchannelで1つのgoroutineに集め、そのgoroutineだけがmapに書く。両方に `go test -race` をかけ、警告が出ないことを確かめる。次に、(a) から `Lock` を外してテストを実行し、レース検出器の報告が、その行を指すことを確かめてから、元に戻す
12. G12（またはG14）のディレクトリで、ストアに対するテストを1本足す：50個のgoroutineから、同時に登録と一覧取得を呼ぶ。`go test -race` の結果はどうなるか。`net/http` がリクエストをどう処理しているかを `go doc http.Server.Serve` の説明で確かめ、ストアを `Mutex` で守る。この変更は、元のコミットとは別のコミットにする

### 発展（任意）

- `for` ループの中で、ループ変数を使うgoroutineを起動する（例：0〜4を出力する）。`go.mod` の `go` の行を `1.21` に書き換えた場合と、今のバージョンの場合で、出力はどう変わるか。ブログ記事「Fixing For Loops in Go 1.22」を読んで、理由を書く。終わったら `go.mod` を元に戻す
- 読み込みが多く、書き込みが少ないmapを守るのに向いた型を、`go doc sync` の一覧から探し、課題11 (a) を置き換える
- 結果を、一覧と同じ順番で表示するようにする
- `runtime.NumCPU()` と `runtime.NumGoroutine()` の値を表示する。今回の仕事（ほとんどが通信待ち）で、Nの上限をCPUの数に合わせる意味はあるか

## 詰まりやすいところ

- `fatal error: all goroutines are asleep - deadlock!` で止まる → どのgoroutineが、どのchannelの送信か受信で待っているかを、スタックトレース（G7）の行番号から特定する。その相手になるgoroutineは、存在するか
- エラーは出ないが、プログラムがいつまでも終わらない → 結果を受け取る `for range` が、何をきっかけに終わるのかを考える
- `panic: send on closed channel` → そのchannelを `close` している場所が、1か所だけか。送る側が全員終わってから、閉じているか
- `WaitGroup` の `Wait` がすぐに返ってしまう、または `negative WaitGroup counter` でpanicする → 数を増やす呼び出しが、`go` 文の前にあるか、goroutineの中にあるかを見る。増やす回数と減らす回数が合っているか
- `-race` を付けても何も報告されないのに、結果がおかしい → レース検出器が見つけるのは、「その実行で実際に起きた」競合だけ。テストが、問題のコードを同時に通っているかを疑う
- ワーカーを増やしても速くならない → 本当に同時に動いているかを、各ワーカーが開始と終了の時刻を出力して確かめる。どこかで、`Mutex` を持ったまま通信していないか

## 完了条件の確かめ方

`go vet ./... && go test -race -cover ./...` を実行し、レース検出器の警告（`WARNING: DATA RACE`）が1つも出ずに、テストが通る。テストには、課題7の4種類の相手と、課題9のワーカープール（相手20個、Nは3以上）が含まれている。念のため `go test -race -count=5 ./...` でも、警告が出ないことを確かめる。課題11で、`Lock` を外すと警告が出ることも、確認済みであること。
