O8（引き継ぎ）の題材を、セッションの間の日にAIに作らせる。デバッグドリル（`debug-drill.md`）と同じ仕掛けで、答えは `answers/` に置いて開かない。**AIなしデーに、この答えを見ずに読み解く。**

```text
私が「引き継ぐ」練習をするための、小さなサービスを作ってください。CLAUDE.md の「学習を奪わない」に従い、
仕込んだ問題の説明はチャットに出さないでください。

作るもの：
- Go の HTTP API（標準ライブラリと pgx だけ。Go の版は手元の `go version` に合わせ、go.mod の go の行もそれにする）＋ PostgreSQL（postgres:18）。題材は「<題材。例：書籍の貸出記録>」
- 接続は環境変数 DATABASE_URL（テストは TEST_DATABASE_URL。無ければ Skip）。スキーマは schema/ に SQL で置き、アプリは自動で流さない。動かして確かめるための seed.sql も置く
- Dockerfile、docker-compose.yml、テスト（一部だけ。正常系が中心で、Go のコードの3割まで）
- README。ただし**わざと不完全に**：起動に必要な手順のうち1つを書かず、環境変数を1つ説明しないでください。書かない手順は、README のとおりに動かすと必ず症状が出るもの（起動しない、あるエンドポイントだけ失敗する）にし、ローカルでも compose でも同じ症状にしてください。説明しない環境変数は、無いと挙動が変わるものにしてください
- Go のコードが 1,200〜2,500 行。go.sum は数えず、vendor/ は作らない（ベンダリングは O7 の手順で私が行います）。置き場所は drills/infra/O08-handover/service/

仕込むもの（合計 5〜8 個。設計の問題とバグを混ぜる）：
- 境界での問題を必ず入れる：入力の検証の抜け、エラーの握り潰し、DB が止まったときの振る舞い。握り潰しは、grep 一発で見つかる書き方（`_ = err` の直書き）を避け、ログにだけ出して処理を続ける、戻り値を捨てる、など形を変えてください
- 設計の問題を必ず入れる：責務が混ざった関数、設定の直書き、時刻の扱い（タイムゾーンかどの時計を見るか）。時刻の問題は、ホストと DB のタイムゾーンが同じ（両方 UTC）でも症状が出る形にしてください（例：期限の計算が日付の境界で狂う）
- 明らかすぎるもの（コンパイルが通らない、起動しない）は入れない。動くが、おかしい、にしてください。ただし少なくとも4つは、「DB を止める」「不正な JSON を送る」「環境変数を消す」「大きな入力を送る」「同じ操作を同時に2つ送る」のどれかで、HTTP の応答かログに症状が出るものにし、残りは読んで見つけるものにしてください
- 問題どうしは独立させてください。1つ直すと別の問題が見えなくなる組み合わせ（README に書かなかった手順の症状が、エラー応答の漏れでしか分からない、など）にしないでください
- 問題の場所を示すコメントやヒントを、コードに一切書かないでください。TODO / FIXME / HACK は0件にし、関数名・ファイル名・seed のデータでもほのめかさないでください。問題のある挙動を「正しい」として固定するテストがあるのは構いません

答え：
- answers/handover-<今日の日付>.md（リポジトリ直下の answers/）に書く。冒頭に「設計 n 個・バグ n 個」、各問題に「場所・何が問題か・どう困るか・課題1〜4のどの手順で見つかるか・直し方の方向」
- チャットにはその内容を表示しないこと

足してほしい機能（課題7で使う。実装しない。引数名や空の分岐など、痕跡もコードに残さない）：
- 「<機能。例：貸出中の本だけを一覧する絞り込み>」。この機能に必要な列やデータは、スキーマに既にあること
```

## 作らせたあと

`service/` の中を**読まずに**、次だけを確かめてコミットする（`[ai] O8: 引き継ぎの題材`）。読むのはAIなしデーから。

- `go build ./... && go vet ./... && go test ./...` が通る（落ちたら、AI に直させる。自分で読まない）
- `docker compose build` が通る
- `grep -rn "TODO\|FIXME\|HACK" service/` が0件
- Dockerfile と compose が使うイメージ（golang、postgres:18 など）を、この日のうちに `docker pull` しておく。AIなしデーに取りに行くと、それだけで時間が消える

## 題材と機能の選び方

- 題材は、自分の仕事と無関係で、公開してよいもの。実在のデータは使わない
- 足す機能は、既存の構造を理解していないと正しく書けないもの（一覧に条件を足す、集計を足す）。新しい仕組みが要るもの（認証、通知）は避ける
- 2回目以降は、題材と仕込みの種類を変える。同じ癖に慣れるのを防ぐ
