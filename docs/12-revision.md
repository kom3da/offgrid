# 改訂の運用

このパッケージは数年単位で使うので、内容が古くならないよう定期的に改訂する。版はカレンダー形式（例：`v2026.09`）で付け、変更点は `CHANGELOG.md` に残す。

## 改訂のタイミング

| 種類 | タイミング | 範囲 |
| --- | --- | --- |
| 小改訂 | ステージを1つ通過したとき | 次のステージの教材とツールだけを見直す |
| 中改訂 | 1年に1回 | 全体を見直す |
| 全面改訂 | Goのメジャーな変更、主要ツールの置き換え、卒業時 | 構成から見直す |

## 改訂チェックリスト

- [ ] Go・Node.js・PostgreSQL・Dockerの現行バージョンを確認し、課題の記述（構文、標準ライブラリ、イメージ名）を合わせる
- [ ] 書籍の版が更新されていないか、絶版になっていないかを確認する
- [ ] 推奨ツール（静的解析、負荷試験、ローカルLLM、グラフライブラリ）が今も主流かを確認する
- [ ] オフライン化の手順（DevDocs、pkgsite、ローカルレジストリ）が今も動くかを試す
- [ ] `logs/` で繰り返し詰まったテーマを、ユニットや完了条件に反映する
- [ ] 卒業制作の要件が、実際に使いたい形とずれていないか見直す
- [ ] 変更点を `CHANGELOG.md` に書き、`git tag vYYYY.MM` を付ける

## 手順

1. AIを使ってよい日に、`prompts/revision.md` をClaude Codeに渡し、古くなった箇所を洗い出す
2. 提示された変更案を自分で確認し、採用するものだけ `docs/` に反映する
3. `CHANGELOG.md` に追記し、`[docs] vYYYY.MM 改訂` でコミットしてタグを付ける
4. `PROGRESS.md` のメモ欄に、改訂した旨を書く

## 改訂しないもの

- 過去の `logs/` と `drills/` のコード。当時の記録として残す
- 通過済みステージの完了条件。基準を後から変えると進捗の意味が変わる
