title: "評価とステージ通過"
---

各ステージの最後に、下の「確認項目」の8割以上をAIなしで満たし、実技を通過したら次へ進む。満たせなければ、できなかった項目のユニットに戻る。項目が5つ以下のステージは、8割以上＝全項目になる。

確認項目は、ステージの最後のAIなしデーに、その日の振り返り（`logs/`）へコピーし、1つずつ実際にやってみて、○か×を付ける。頭の中で「できるはず」と判定しない。

## 到達レベルの定義

| レベル | 状態 |
| --- | --- |
| 1 | ドキュメントを見ながらなら書ける |
| 2 | ドキュメントなしで書ける。エラーを自力で読める |
| 3 | 他人（AI含む）のコードの問題点を指摘し、代案を示せる |
| 4 | 設計判断を理由付きで説明し、他人に教えられる |

卒業時の目標は、Linux・Git・GoとTypeScriptがレベル3、SQLとネットワークがレベル2〜3、閉域運用がレベル2以上。

## 「説明できる」の確かめ方

完了条件や確認項目の「説明できる」は、自己申告にしない。

1. AIなしデーの中で、何も見ずに、課題ディレクトリの `explain.md` に文章で書く
2. 平日（水曜）に、AIに採点を頼む。観点は「正確か」「抜けがないか」「自分の言葉で書けているか」の3つ
3. 誤りや抜けを指摘されたら、次回のウォームアップで、何も見ずに書き直す

AIは誤りの場所を示すだけで、模範解答は書かない（CLAUDE.md の「採点を頼まれたとき」）。

## ステージ通過の実技

確認項目とは別に、各ステージの最後に1回行う。

1. そのステージで作った課題の中から、AIに1本選んでもらう（自分で選ばない）。メイン枠（3.5時間）で終わる大きさのものに限る。大きな課題（G11、T7、T10など）は、その一部を指定してもらう
2. AIなしデーの中で、時間を計り、ゼロから作り直す。見てよいのは、`man`、`--help`、`go doc`、公式ドキュメントのオフラインコピーだけ。自分の過去のコードとメモ、書籍、Web検索は使わない
3. 合否を下の表で判定し、かかった時間を `PROGRESS.md` のメモに残す

| ステージ | 合格の基準 |
| --- | --- |
| Stage 0 | 課題シートの「完了条件の確かめ方」を満たす。スクリプトは `shellcheck` の指摘がゼロ |
| Stage 1〜3 | 元のテストがすべて通る。SQLの課題は、元の解答と同じ結果になる |
| Stage 4 | そのユニットの完了条件を、新しい環境（作り直したコンテナやVM）で満たす |
| Stage 5 | 実技は行わない。卒業制作そのものが実技にあたる |

## Stage 0 の確認項目

- 2進数・16進数を変換でき、UTF-8の仕組みを説明できる
- ファイル操作とパーミッションの変更を、何も見ずにできる
- パイプを組み合わせて、ログから必要な情報を取り出せる
- プロセスの確認と停止、環境変数の設定ができる
- エラー時に止まるシェルスクリプトを書ける
- SSH鍵を作ってGitHubに登録し、ブランチを切ってコミットし、コンフリクトを解消してpushできる
- DNSからHTTPのレスポンスまでの流れを説明できる
- Dockerでコンテナを起動し、ログを見て、中に入れる

## Stage 1 の確認項目

- 条件分岐、ループ、スライス、マップ、構造体を使った処理を何も見ずに書ける
- エラーを返し、ラップし、`errors.Is`/`As`で判定できる
- テーブル駆動テストを何も見ずに書ける
- panicのスタックトレースから、原因の行を特定できる
- スタックとキューを自作し、計算量を説明できる
- 再現ドリルで50行の関数を8割以上再現できる
- `psql`で、SELECT・集約・JOINを何も見ずに書ける
- トランザクションを使って更新し、ROLLBACKで戻せる

## Stage 2 の確認項目

- `net/http`だけでCRUD APIとミドルウェアを書ける
- JavaScriptの非同期処理（`async`/`await`）を説明できる
- CORSエラーが起きる条件と、通す方法を説明できる
- TypeScriptで判別可能ユニオンと型ガードを使った設計ができる
- Vite＋Reactの環境をテンプレートなしで組める
- APIに接続した画面を作り、APIを止めても画面が壊れない
- 主キー・外部キー・制約を含むテーブルを設計し、正規化できる
- NULLとタイムゾーンを含むクエリの結果を、実行前に予想できる
- `EXPLAIN`で、インデックスが使われているかを見分けられる
- `pg_dump`のバックアップから復元できる
- ウィンドウ関数で「種別ごとの上位3件」を書ける

## Stage 3 の確認項目

- goroutineとchannelでワーカープールを書き、`-race`で問題がない
- contextでタイムアウトとキャンセルを伝播できる
- GoからPostgreSQLに接続し、プレースホルダとトランザクションを扱える
- `-mod=vendor`でビルドできる構成を組める
- リトライ付きのHTTPクライアントを書ける
- SSEでサーバーから値を流し、ブラウザで受けて表示できる
- 空のDBから、番号付きのSQLファイルで再構築できる
- 実行計画を読んで、遅い理由とインデックス案を説明できる
- 時系列データを時刻で区切って集約し、古いデータを削除できる

## Stage 4 の確認項目

- 新しいサーバーの状態（ディスク、メモリ、ポート、サービス、ログ）を、自作のスクリプトで確認できる
- アプリをsystemdで常駐させ、ログを追える
- 静的バイナリと軽量コンテナを作れる
- `docker compose up`だけで、API・PostgreSQL・リバースプロキシが動く
- 同じ構成を、Ansibleで何度でも作り直せる
- `ss`・`strace`・`pprof`で障害の原因を特定できる
- 負荷をかけてp95を測り、改善前後を比べられる
- ネットワーク遮断下で、ビルドから起動まで完了できる

## Stage 5 の確認項目（卒業）

- watchdeckの必須の機能要件・非機能要件がすべて動く
- 閉域での再構築と障害からの復帰を、試験結果で示せる
- runbookの手順だけで、新しい仮想マシンに閉域で再構築できる
- 設計と技術選定を30分でAIに説明し、質問に答えられる（平日に実施し、やり取りを `capstone/docs/` に残す）

## 定期的な見直し

AIなしデー4回ごとに、4回分の振り返り（`logs/`）を並べて見直す。繰り返し詰まったテーマは、次の4回で優先して扱う。[ロードマップ](03-roadmap.md)の目安回数と実績がずれていたら、自分の計画のほうを直す。ペースが落ちても、振り返りだけは続ける。

## 進捗の記録

ステージを通過したら、`PROGRESS.md` の該当行を更新する。テストアウトはユニット欄に、実技の課題とかかった時間はステージの表のメモに残す。
